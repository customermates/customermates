Customermates filters (used by the Model Context Protocol (MCP) tools, the REST API, and the app UI) are arrays of field-operator-value rules. Seventeen operators cover equality, text matching, comparison, set membership, range, recency, null checks, and relationship membership.

## Where do filters apply?

- The `list_records` MCP tool and the messaging filters on `get_messaging_threads` and `get_activities`.
- `entityFilters` and `dealFilters` on widgets.
- `timelineFilters` on activity widgets. Activity filters allow at most one rule per field; put OR alternatives in one `in` value array.
- Saved views in the UI (converted to the same shape under the hood).

## What does a filter rule look like?

```json
[
  { "field": "firstName", "operator": "startsWith", "value": "An" },
  { "field": "createdAt", "operator": "gte",        "value": "2024-01-01" }
]
```

Rules are AND-combined. For OR logic, run two queries and merge client-side, or use the `in` operator when comparing against a list.

## Which operators exist?

| Operator | Expects | Works on | Example value |
|---|---|---|---|
| `equals` | single | text fields (`name`, `firstName`, `lastName`, `url`) and currency, email, phone, plain and link custom columns; exact and case-sensitive | `"Acme"` |
| `contains` | single | text fields (`name`, `firstName`, `lastName`, `url`), email, phone, plain and link custom columns, and date-range custom columns; case-insensitive | `"acme"` |
| `startsWith` | single | `name`, `firstName`, `lastName`; case-insensitive | `"An"` |
| `gt` | single | numbers, dates | `"2024-01-01"` |
| `gte` | single | numbers, dates | `100` |
| `lt` | single | numbers, dates | `"2024-12-31"` |
| `lte` | single | numbers, dates | `"2024-12-31"` |
| `in` | array | relationship arrays, id, enum and select fields, and singleSelect custom columns | `["id1", "id2"]` |
| `notIn` | array | relationship arrays, id, enum and select fields, and singleSelect custom columns | `["id1"]` |
| `between` | array of 2 | numbers, dates | `["2024-01-01", "2024-12-31"]` |
| `inLastDays` | single (positive integer) | dates | `30` |
| `isNull` | no value | custom columns only | (none) |
| `isNotNull` | no value | custom columns only | (none) |
| `hasNone` | no value | relationship arrays, messaging-thread draft status | (none) |
| `hasSome` | no value | relationship arrays, messaging-thread draft status | (none) |
| `hasUnset` | no value | messaging-thread participants | (none) |
| `allSet` | no value | messaging-thread participants | (none) |

### Which date operators exist?

Date fields such as `createdAt` and `updatedAt` accept `gt`, `gte`, `lt`, `lte`, `between`, and `inLastDays`. Use `inLastDays` with a positive integer number of days for a rolling recency window, for example `{ "field": "createdAt", "operator": "inLastDays", "value": 7 }` for records created in the last week.

### Which operators work on text fields?

Text fields such as a contact's `firstName` and `lastName` or an organization's `name` accept `equals`, `startsWith`, and `contains`. `contains` and `startsWith` compare case-insensitively; `equals` is an exact, case-sensitive match.

### Which relationship operators exist?

Relationship arrays (`organizationIds`, `dealIds`, `userIds`, `contactIds`, `serviceIds`, `taskIds`) accept `in`, `notIn`, `hasNone`, and `hasSome`. The participants link-status field on `get_messaging_threads` uses `hasUnset` and `allSet` to filter threads by whether their participants are linked to records. The `draft` field on the same tool takes the value-less `hasSome` (the thread holds an unsent draft) and `hasNone` (it does not), which is how you list or exclude drafts.

## Which field names can I use?

The `field` value is whatever `get_record_schema` returns under `filterableFields` for that entity, with the operators each field allows. It includes:

- Default scalar fields (for example `createdAt`, `updatedAt`, and on contacts `firstName` and `lastName`).
- Relationship arrays (`organizationIds`, `dealIds`, `userIds`, `contactIds`). Pair these with `in`, `notIn`, `hasNone`, `hasSome`. Some relation fields need read permission on the related record type.
- Custom column ids. Use the column's UUID as the field; a singleSelect column accepts only `in`, `notIn`, `isNull` and `isNotNull` and filters on its option values.

Always call `get_record_schema` first if you are not sure what is filterable. The error for an unknown field lists every available field with its allowed operators.

## Examples

Contacts in any of three organizations:

```json
{ "field": "organizationIds", "operator": "in", "value": ["org_1","org_2","org_3"] }
```

Deals created in 2024 whose custom singleSelect column (identified by its UUID) is set to a chosen option value:

```json
[
  { "field": "createdAt", "operator": "between", "value": ["2024-01-01","2024-12-31"] },
  { "field": "col_uuid",  "operator": "in",      "value": ["option_value"] }
]
```

Contacts without any organization linked:

```json
{ "field": "organizationIds", "operator": "hasNone" }
```

Records created in the last 30 days:

```json
{ "field": "createdAt", "operator": "inLastDays", "value": 30 }
```

## Free-text search or a filter?

`list_records` also accepts `searchTerm`, which runs a free-text search against the entity's name fields plus related fields: for contacts `firstName`, `lastName`, channel identifier values and linked organization names; for organizations `name` plus linked contacts' first and last names; for deals, services and tasks `name`. Use `searchTerm` for "contacts whose name contains acme" when you do not care which name field matched; use a filter rule on `firstName` or `lastName` with `contains`, `startsWith`, or `equals` when the field matters or when you combine it with other rules.
