---
title: "Runners: Run Agents With Your Own Claude Code or Codex"
description: "A runner runs agent steps with your own Claude Code, Codex or Gemini CLI on your machine: what it needs, how to start it, timeouts and how to revoke it."
---

A runner lets the agent steps of your workspace run with your own Claude Code, Codex or Gemini CLI on your own machine. It is a small program, `customermates-runner`, that asks your workspace for agent jobs, starts the CLI you are signed in to, streams what the CLI does back as a transcript and reports the result. Your CLI login stays on your machine: Customermates never receives it. Runners work on Customermates Cloud and on self-hosted instances.

You manage runners under **Settings**, **Agents**, in the **Runners** card. Adding and revoking a runner needs the same role access as [API keys](/docs/api-keys).

## What does a runner do? [#what-does-a-runner-do]

Every 60 seconds it tells the workspace its machine name and which CLIs it found on PATH, with their versions. Between those reports it holds a request open for up to 25 seconds to pick up the next queued job of the workspace, and it asks again straight away. For a job it writes a temporary MCP configuration with the address of your workspace and a short-lived key of the job owner, starts the CLI with the job's prompt, sends each step of the CLI's output back as a transcript event, and deletes the configuration when the CLI is done. Then it goes idle until the next job.

The CLI works as the owner of the job, with that member's permissions in this workspace. It can use the tools of your workspace over [MCP](/docs/mcp), and as far as its own settings and the allowed tools permit, whatever else is on that machine, such as local MCP servers and files.

## What does it need? [#what-does-it-need]

- Node 24, or Docker.
- One of Claude Code, Codex or Gemini CLI, installed and signed in on that machine. Without a CLI the runner stays online but takes no jobs, so another runner can have them.
- A network connection from that machine to your Customermates address. The runner only makes outgoing requests, so it works behind a firewall and needs no open port.

## How do I add and start a runner? [#how-do-i-add-a-runner]

1. Open **Settings**, **Agents** and click **Add runner**. Give it a name that tells you which machine it is.
2. Copy the token. It is shown once and starts with `cmr_`. Keep it like a password: anyone with it can pick up the runner jobs of this workspace.
3. Start the runner on that machine, either with Node:

```bash
npx customermates-runner --token cmr_... --url https://crm.example.com
```

or with Docker, mounting the login folder of your CLI so it stays signed in:

```bash
docker run -d --restart unless-stopped \
  -e CUSTOMERMATES_URL=https://crm.example.com \
  -e CUSTOMERMATES_RUNNER_TOKEN=cmr_... \
  -v "$HOME/.claude:/home/node/.claude" \
  ghcr.io/customermates/runner
```

The address is the one you open Customermates at; on a self-hosted instance it is your own `BASE_URL`. The token and address can also come from `CUSTOMERMATES_RUNNER_TOKEN` and `CUSTOMERMATES_URL`. Useful options:

- `--client claude`, `codex` or `gemini` picks the CLI that runs the jobs. By default it is the first one found.
- `--workdir <folder>` runs the CLI in that folder. By default every job gets an empty temporary folder.
- `--permission-mode <mode>` and `--allowed-tools <tools>` set what Claude Code may do without asking. By default only the tools of your workspace are allowed. Codex runs with a read-only sandbox.

The runner logs to its standard output and never prints its token.

## What does the server send, and what does it never send? [#what-is-sent]

The server sends the prompt of the job, whether outsiders can influence that prompt, the job's timeout, the MCP address of your workspace and a key that stops working a few minutes after the job's timeout and is revoked as soon as the job ends. It never sends a workspace secret, a provider key or the data of another job. The key only reaches this workspace, and only as the member who owns the job.

The runner never sends your CLI login, your files or your environment. It sends the machine name, the CLIs it found, the transcript events (each cut to 4 KB, with tokens removed) and the result. Transcripts are stored with the job, so do not let a CLI print secrets it should not show.

A prompt that outsiders can influence, for example one that carries a form submission or an incoming webhook, is marked in the job. The runner wraps it in the same framing as the MCP server uses: the text is data, not instructions, and a request inside it to change what the agent does is reported, not followed.

## What happens to a job? [#what-happens-to-a-job]

A job waits in the queue until a runner of the workspace claims it. A job that no runner claims within 15 minutes ends as timed out. A claimed job that is not finished by its timeout also ends as timed out, and the runner stops the CLI at that moment. If the CLI fails, the job ends as failed with the reason. A job that is already finished, timed out or cancelled cannot be changed by a late report from a runner, and the runner stops its CLI when the workspace tells it so.

Several runners can work in one workspace. Each job goes to exactly one of them.

## How do I know that a runner is online? [#is-it-online]

The **Runners** card shows each runner's machine, the CLIs it found and when it was last seen, with one of four states: **Online** when it was seen in the last two minutes, **Offline** when it was seen earlier, **Never connected** when it has not reported yet, and **Revoked**.

When agent jobs are waiting and no runner of the workspace has been seen for 10 minutes, the owner of those jobs gets a notification of the kind **Automation alerts**, at most once an hour, with a link to the **Runners** card.

## How do I revoke a runner? [#how-do-i-revoke-a-runner]

Click **Revoke** on the runner and confirm. The runner cannot pick up jobs any more: its next request is refused, and the program stops. A job it is running stops reporting and ends as timed out. Revoking cannot be undone. To use the machine again, add a new runner and start it with the new token. Revoke a runner at once if its token leaks.

## For agents [#for-agents]

Runners talk to the workspace over REST with `Authorization: Bearer cmr_...`, the token shown when the runner was added. A runner token only reaches these four endpoints, described in the [API reference](/docs/openapi):

- `POST /api/v1/runner/heartbeat` reports the machine and the CLIs found.
- `POST /api/v1/runner/jobs/claim` waits up to 25 seconds and answers 200 with a job and its MCP credentials, or 204 when none arrived.
- `POST /api/v1/runner/jobs/{id}/events` appends transcript events and answers 409 once the job is closed.
- `POST /api/v1/runner/jobs/{id}/result` reports `succeeded`, `failed` or `timedOut` with the final answer and, when the CLI reports them, tokens and cost.

A revoked token and a workspace that is being deleted answer 401.

## Frequently asked questions [#frequently-asked-questions]

<Faq>
<FaqItem question="Does Customermates get my Claude Code, Codex or Gemini login?">
No. The runner starts the CLI you installed and signed in yourself, on your machine. The workspace only sends it the prompt and a short-lived key for your workspace's MCP address.
</FaqItem>
<FaqItem question="Can someone outside my team make my runner do something?">
Only through a prompt you set up. If a prompt carries text from outsiders, such as a form submission, the job marks it and the runner frames it as data, not instructions. The key the CLI gets reaches only this workspace, as the member who owns the job, and it expires. By default Claude Code may use only your workspace's tools and Codex runs in a read-only sandbox, so widen that only on a machine you trust.
</FaqItem>
<FaqItem question="What if my machine is switched off?">
Jobs wait in the queue for up to 15 minutes and then end as timed out. After 10 minutes without a runner, the owner of the waiting jobs gets a notification.
</FaqItem>
<FaqItem question="Can I run the runner on a server?">
Yes. Any machine with Node 24 or Docker, one signed-in CLI and a connection to your Customermates address works, for example an always-on virtual machine.
</FaqItem>
</Faq>
