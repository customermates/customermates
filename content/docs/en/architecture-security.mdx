Customermates enforces a single-tenant-per-company data model at every layer. Every record is scoped to a company, API keys carry the owning user's identity, and agents see only what that user can see.

## What is the stack?

- **Next.js 16** (App Router, Turbopack): web app and API.
- **PostgreSQL**: primary datastore. JSONB for custom column values and webhook payloads.
- **Prisma**: ORM and migrations.
- **better-auth**: sessions, social login, API keys, MCP OAuth.
- **mcp-handler**: Model Context Protocol endpoint.
- **TypeScript** end to end, Zod-validated at every boundary.

## How does multi-tenancy isolate workspaces?

Every record belongs to a **Company**. The company id is enforced in three places:

1. **App layer**: every interactor resolves the current user's company and filters by it.
2. **Prisma layer**: queries include `companyId` in every `where`.
3. **Decorator layer**: `@TenantInteractor` makes interactors that fail to scope throw at runtime.

Cross-tenant reads are not possible through the public surface. On the managed cloud a vendor operator console can read across tenants for support; it is limited to an allowlisted operator account, refuses to load outside cloud mode, and records every read and write in a separate internal log. A self-hosted deployment has no such console. The hosted assistant runs inside the same scope: it can read and change only what the asking user can.

## How do clients authenticate?

Three ways, all resolving to the same user and company context:

- **Session cookie** (UI): signed, http-only, `Secure` under HTTPS.
- **API key**: 64-character token of ASCII letters (`a-z`, `A-Z`) issued by the better-auth API key plugin, hashed at rest, tied to a user, optionally expiring. Sent in the `x-api-key` header. See [API keys](/docs/api-keys).
- **OAuth 2.1** (MCP): remote MCP clients authorize through better-auth with PKCE and send a Bearer token instead of an API key. Access tokens live one hour, refresh tokens thirty days.

## How is authorization decided?

Per user and role. A role, edited under **My Company** → **Roles**, sets two things for each resource (the five record types and the workspace features such as **Users & Roles**, **Company**, **API & Webhooks** and **Audit Log**): **Manage**, where **Yes** grants create, update and delete together, and **Read access**, which is **All**, **Assigned** or **None**. Not every resource offers every option. The system **Admin** role has every permission. Every operation checks the permission before acting. API keys inherit the permissions of their owning user; there is no per-key scoping.

The **API & Webhooks** permission controls the **API & Connectors**, **Webhooks** and **Recent Deliveries** pages and the key and webhook operations behind them (including `manage_webhooks`), not the use of a key. A call made with an existing key, or through an OAuth connection, is checked against the owner's permissions on the records it touches. Removing **API & Webhooks** from a role therefore hides its members' keys from them but leaves those keys working. To stop a member's keys, open the member under **My Company** → **Members** and set **Status** to **Inactive** (this needs **Manage** **Yes** and read access **All** on **Users & Roles**; you cannot deactivate yourself, and the last active member with the **Admin** role cannot be deactivated); every call with an inactive member's keys that reads or changes workspace data is refused.

## How does external AI access work?

MCP requests use the same authentication and authorization path. When an agent acts through MCP:

- It calls `/api/v1/mcp` with an API key or an OAuth Bearer token.
- The server resolves user and company from the credential.
- Every tool call runs inside a tenant-scoped context.
- Validation errors return structured messages with remediation hints and do not leak internal schema details.

The MCP surface adds input guardrails to keep tool calls safe:

- Relation arrays cannot be sent through the update tools at all; links change only through `manage_record_links`, so a `null` can never wipe a relation.
- Update tools targeting the wrong record type are rejected with a pointer to the correct tool.
- Destructive tools require an explicit list of record ids. There is no delete-by-filter shortcut.

See the [MCP tool catalog](/docs/mcp#tool-catalog) for the full list.

## How is data protected at rest and in transit?

- Postgres encryption depends on your provider. On the managed cloud, data lives in an EU region with disk-level encryption at rest.
- Secrets in `.env` are never logged. The logger redacts anything that looks like a key, token, or password.
- Webhook secrets and custom header values are stored in Postgres without hashing, because they must be retrievable to sign and send outgoing requests. The REST API and MCP never return them, but the webhook dialog shows them to the **Admin** role and to every role with **Read access** **All** on **API & Webhooks**. To keep them elsewhere, self-host with your own secret manager.
- HTTPS everywhere on the managed cloud. On self-host, you provide the TLS; see [self-hosting](/docs/self-hosting) for the Caddy example.
- A webhook URL may use plain `http://` for any host as long as the webhook has no custom headers. A webhook with custom headers must use `https://`, except for `localhost`, `127.0.0.1` and `::1`; this is checked when the webhook is saved and again before each delivery. See [Webhooks](/docs/webhooks).

## What does the audit log record?

Changes to records and to the workspace configuration around them are logged with the user, the event, the element id and the payload. Updates to records, roles, webhooks, custom fields, routines and connected accounts carry a field-level diff; creates, deletes and member or company-settings saves carry a snapshot instead, which is written even when nothing changed. User registrations, record exports and accepted legal documents are recorded as well. A failed write leaves no entry. Messaging events are not written to the audit log, and webhook secrets and header values are redacted. Authentication, API key lifecycle, subscription changes, saved views, widgets, agent conversations and vendor operator actions are not recorded either. An entry written by an automated process, such as removing a connected account when a trial ends, names the user it affected rather than someone who performed it. Read it under **My Company** → **Audit Logs** (see the [Company page](/docs/app-company)). Access needs **Read access** **All** on the **Audit Log** row of your role, which has no **Manage** option; the **Admin** role always has it. The page lists every entry in the workspace, including changes to records the reader's role cannot open otherwise, and the same permission shows the change history on record pages. It is included on every cloud plan and in the self-hosted edition alike. Entries are not deleted automatically; they are kept as long as the workspace exists. The screen has no export action; the activity timeline, its REST endpoint and the `get_activities` tool return the same entries under the same permission.

## Where do I report a vulnerability?

Write to `mail@customermates.com`. We aim to acknowledge within one business day. There is no bug bounty program.
