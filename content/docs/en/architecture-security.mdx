Customermates enforces a single-tenant-per-company data model at every layer. Every record is scoped to a company, API keys carry the owning user's identity, and agents see only what that user can see.

## What is the stack?

- **Next.js 16** (App Router, Turbopack): web app and API.
- **PostgreSQL**: primary datastore. JSONB for custom column values and webhook payloads.
- **Prisma**: ORM and migrations.
- **better-auth**: sessions, social login, API keys, MCP OAuth.
- **mcp-handler**: Model Context Protocol endpoint.
- **TypeScript** end to end, Zod-validated at every boundary.

## How does multi-tenancy isolate workspaces?

Every record belongs to a **Company**. The company id is enforced in three places:

1. **App layer**: every interactor resolves the current user's company and filters by it.
2. **Prisma layer**: queries include `companyId` in every `where`.
3. **Decorator layer**: `@TenantInteractor` makes interactors that fail to scope throw at runtime.

Cross-tenant reads are not possible through the public surface. On the managed cloud a vendor operator console can read across tenants for support; it is limited to an allowlisted operator account, refuses to load outside cloud mode, and records every read and write in a separate internal log. A self-hosted deployment has no such console. The hosted assistant runs inside the same scope: it can read and change only what the asking user can.

## How do clients authenticate?

Three ways, all resolving to the same user and company context:

- **Session cookie** (UI): signed, http-only, `Secure` under HTTPS.
- **API key**: 64-character base62 token issued by the better-auth API key plugin, hashed at rest, tied to a user, optionally expiring. Sent in the `x-api-key` header. See [API keys](/docs/api-keys).
- **OAuth 2.1** (MCP): remote MCP clients authorize through better-auth with PKCE and send a Bearer token instead of an API key. Access tokens live one hour, refresh tokens thirty days.

## How is authorization decided?

Per user and role. Roles carry permissions on resources (contacts, organizations, deals, services, tasks, and the workspace features) and actions (read, create, update, delete). Every interactor checks the permission before acting. API keys inherit the permissions of their owning user; there is no per-key scoping.

## How does external AI access work?

MCP requests use the same authentication and authorization path. When an agent acts through MCP:

- It calls `/api/v1/mcp` with an API key or an OAuth Bearer token.
- The server resolves user and company from the credential.
- Every tool call runs inside a tenant-scoped context.
- Validation errors return structured messages with remediation hints and do not leak internal schema details.

The MCP surface adds input guardrails to keep tool calls safe:

- Relation arrays cannot be sent through the update tools at all; links change only through `manage_record_links`, so a `null` can never wipe a relation.
- Update tools targeting the wrong record type are rejected with a pointer to the correct tool.
- Destructive tools require an explicit list of record ids. There is no delete-by-filter shortcut.

See the [MCP tool catalog](/docs/mcp#tool-catalog) for the full list.

## How is data protected at rest and in transit?

- Postgres encryption depends on your provider. On the managed cloud, data lives in an EU region with disk-level encryption at rest.
- Secrets in `.env` are never logged. The logger redacts anything that looks like a key, token, or password.
- Webhook secrets are stored in Postgres because they must be retrievable to sign outgoing requests. To keep them elsewhere, self-host with your own secret manager.
- HTTPS everywhere on the managed cloud. On self-host, you provide the TLS; see [self-hosting](/docs/self-hosting) for the Caddy example.
- Webhook deliveries that carry custom headers must go to HTTPS URLs; plain `http://` is accepted only for local testing without headers.

## What does the audit log record?

Changes to records and to the workspace configuration around them are logged with the user, the event, the element id and the payload. Updates to records, roles, webhooks, custom fields, routines and connected accounts carry a field-level diff; creates, deletes and member or company-settings saves carry a snapshot instead, which is written even when nothing changed. A failed write leaves no entry. Messaging events are not written to the audit log, and webhook secrets and header values are redacted. Authentication, API key lifecycle, subscription changes, saved views, widgets, agent conversations and vendor operator actions are not recorded either. An entry written by an automated process, such as removing a connected account when a trial ends, names the user it affected rather than someone who performed it. Read it on the [Company page](/docs/app-company) under **Audit logs**; access needs the audit-log read permission on your role. It is included on every cloud plan and in the self-hosted edition alike. The screen has no export action; the activity timeline, its REST endpoint and the `get_activities` tool return the same entries under the same permission.

## Where do I report a vulnerability?

Write to `mail@customermates.com`. We aim to acknowledge within one business day. There is no bug bounty program.
