---
title: "Self-Hosting Customermates with Docker Compose"
description: "Run Customermates on your own server with Docker Compose: install, .env values, email, sign-up, updates, backups and restore, and what differs from Cloud."
---

Self-hosting runs Customermates from two files, `docker-compose.yml` and `.env`, with `docker compose up -d`. You fetch both from the [Customermates repo](https://github.com/customermates/customermates) with `curl`; no `git clone` and no build step are needed. The Compose file starts two containers: PostgreSQL 16 (`postgres:16-alpine`) and the app image `ghcr.io/customermates/customermates:latest`, which applies pending database migrations every time it starts. The migrations create the `pg_trgm` extension: it is trusted on PostgreSQL 13 and later, but some managed providers require you to allow-list it first.

## Should I self-host or use the cloud? [#should-i-self-host-or-use-the-cloud]

| Decision factor | Managed cloud | Self-hosted |
|---|---|---|
| Application and database operations | Customermates operates them | You operate Docker, PostgreSQL, network access, TLS, updates and backups |
| Core CRM records and views | Included by plan | Starter baseline |
| Unified inbox and connected calendars | Available on entitled cloud plans | Not included |
| AI access | External MCP, plus the hosted assistant Mate with the hosted AI credits of your plan | External MCP with your own client and provider |
| Connected providers | Configured within the managed product | You configure and assess every external provider |
| Pricing | Per-user cloud subscription from [[commercial.price.starter.monthly]] per month | Your infrastructure, providers and operator time |

Self-hosting lets you choose where the application and database run. It does not create a security, compliance, privacy or air-gap guarantee by itself; your organization remains responsible for configuration, providers, contracts, retention and operating controls. Compare total operating cost rather than assuming one model is cheaper: infrastructure, backups, restore tests, monitoring, updates, incident response and external providers.

Records move between cloud and self-hosted as Excel workbooks, one list at a time. A whole-platform migration is a separately designed and validated project.

## Is self-hosting free, and do I need a license? [#is-self-hosting-free-and-do-i-need-a-license]

A self-hosted workspace has no subscription and no trial: it starts active, counts no seats and bills nothing. You pay only for your own infrastructure and providers.

Customermates is open core. Code outside `ee/`, and material in `ee/` that is served to the browser, is licensed under AGPL-3.0-only. The server-side code in `ee/` is under the Customermates Commercial License, which allows running the official image with `APP_MODE=self-hosted`, including in production, as a Community Build, as long as the cloud-only features stay off. The exact terms are in `LICENSE` and `ee/LICENSE.md`. Buying a cloud plan does not unlock anything in a self-hosted installation.

## Which features are not available when self-hosting? [#which-features-are-not-available-when-self-hosting]

Every self-hosted installation uses the Starter feature set. These cloud-only features stay off, even if you also pay for a cloud plan: connected messaging accounts (email, LinkedIn, WhatsApp, Instagram, Telegram), the unified Inbox, connected calendars and their events, the hosted assistant Mate with its hosted AI credits, and Routines, which Mate runs. External AI clients still work through MCP with your own AI provider. Enterprise SSO (SAML) and white-labeling are not implemented in either deployment model.

The app hides what does not apply: the sidebar shows no Inbox or Routines, Settings has no Billing or Channels page, and the role editor hides the **Inbox messages** and **Routines** rows. Opening one of those pages by URL returns you to the Dashboard.

Everything else works as in the cloud: lists and views, Excel import and export, Configure, dashboard widgets, members and roles, the Activity log, REST, webhooks and MCP.

## How do I install and self-host Customermates with Docker Compose? [#how-do-i-install-customermates-with-docker-compose]

You need Docker with Docker Compose v2; the image is built for `linux/amd64` and `linux/arm64`. A domain name is needed only for HTTPS.

<Steps>
<Step title="Fetch the two files">
```bash
mkdir customermates && cd customermates
curl -fsSL https://raw.githubusercontent.com/customermates/customermates/main/docker-compose.yml -o docker-compose.yml
curl -fsSL https://raw.githubusercontent.com/customermates/customermates/main/.env.selfhost.template -o .env
```
</Step>
<Step title="Fill in .env">
Replace the placeholder values in `.env` before the first start: at least `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET` (for example from `openssl rand -hex 32`), `BASE_URL`, `RESEND_API_KEY` and `RESEND_OPERATOR_EMAIL`. Without `RESEND_API_KEY`, nobody can finish registering.
</Step>
<Step title="Start">
```bash
docker compose up -d
docker compose logs -f app
```
The first start takes about a minute while the migrations run. Then open `<BASE_URL>/auth/signup`, by default `http://localhost:4000/auth/signup`.
</Step>
<Step title="Register">
Register, choose **Create a new workspace** and complete the wizard; your account becomes **Admin**. See [How do I create the first account on my instance?](#how-do-i-create-the-first-account-on-my-instance).
</Step>
</Steps>

## Which environment variables go into .env? [#env-values]

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`: database user, password and name (template: `postgres`, `change-this-password`, `customermates`). Set them before the first start. PostgreSQL applies them once, when it creates the database volume, so a later change in `.env` does not change the existing database, and the app can then no longer connect.
- `BETTER_AUTH_SECRET`: a long random string that signs sign-in sessions. Changing it later signs everyone out, so keep a copy with your backups.
- `BASE_URL`: the exact address people open in the browser, see [What must BASE_URL be set to?](#base-url).
- `APP_PORT`: the host port the app is published on, `4000` by default.
- `RESEND_API_KEY`, `RESEND_OPERATOR_EMAIL`: email delivery; `RESEND_API_KEY` must not be empty. See [How do I set up email with Resend?](#how-do-i-set-up-email-with-resend-and-can-i-use-smtp).
- `APP_MODE`: leave it at `self-hosted`; the Compose file sets this value for the app itself.
- `CRON_SECRET`: optional, commented out in the template; the secret for the scheduled maintenance calls, see [Which scheduled jobs must I run?](#scheduled-jobs).
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AZURE_AD_CLIENT_ID`, `AZURE_AD_CLIENT_SECRET`: optional, commented out in the template, see [Can users sign in with Google or Microsoft?](#can-users-sign-in-with-google-or-microsoft).
- `ADDRESS_LOOKUP_URL`: optional, commented out in the template; turns on address suggestions, see [How do I turn on address suggestions?](#address-lookup).
- `FILE_STORAGE_DRIVER`, `FILE_MAX_UPLOAD_BYTES` and the `S3_` variables: optional, commented out in the template; where file fields keep their files and how large one may be, see [Where are files stored when I self-host?](#file-storage).

Keep `.env` out of source control. Apply changes with `docker compose up -d`.

## What must BASE_URL be set to? [#base-url]

Set `BASE_URL` to exactly the address people type into the browser: scheme, host name and, unless it is 80 or 443, the port, with no path. Examples: `https://crm.example.com` or `http://192.168.1.20:4000`. The template value `http://localhost:4000` only works on the machine that runs Docker. The app refuses to start if `BASE_URL` contains a path, a query or credentials.

Customermates builds these addresses from `BASE_URL`:

- sign-in redirects, the links in invitation and other emails, and the MCP OAuth address;
- on a documentation page, the MCP address in the install snippets and behind **Copy MCP Config**, **Copy MCP Command**, **Connect to Cursor** and **Connect to VS Code**, and the page address that **Open in ChatGPT** and **Open in Claude** pass on;
- in the REST API reference, the **Server URL**, the code samples and the address that **Send** calls;
- the links in `llms.txt` and `llms-full.txt` (raw markdown pages), the addresses in `sitemap.xml` and `robots.txt`, and the canonical links of the public pages;
- the `url` that `search_docs`, `get_docs_page`, `search` and `fetch` return, whose origin agents put in front of an app route to build a full link.

A request that arrives under another host name, IP address or port still gets addresses that point to `BASE_URL`: after signing in, users can land on the wrong address, and **Send** in the REST API reference fails, because the browser does not let a page opened under another address call the API at `BASE_URL`.

Three addresses the app shows you to copy use the address the browser opened the app with instead: the **Invitation link** on the **Share link** tab of **Invite User** and of the onboarding invite step, the MCP address under **Quick connections** and in the onboarding step **Connect the AI you already use**, and links from **Copy link** on a saved view. Copy them from a browser that uses the public address.

When you change the domain or `APP_PORT`, update `BASE_URL` as well and run `docker compose up -d`. With an `https://` address, sign-in cookies are marked Secure, so the app must then be opened through HTTPS.

## How do I put Customermates behind a reverse proxy with HTTPS? [#how-do-i-put-customermates-behind-a-reverse-proxy-with-https]

Point a reverse proxy such as Caddy, nginx or Traefik at the app port (`4000`, or your `APP_PORT`) and set `BASE_URL` to the public `https://` address. Caddy obtains the TLS certificate itself:

```text
crm.example.com {
  reverse_proxy localhost:4000
}
```

The app takes the scheme and host for its links from `BASE_URL`, so forwarded headers such as `X-Forwarded-Proto` are not required. The proxy must pass on the original `Host` header, because the app rejects form submissions whose origin does not match it, including sign-in and sign-up. Caddy and Traefik do this by default; in nginx add `proxy_set_header Host $host;`. The Compose file publishes the app port on all network interfaces; if only the proxy should reach it, change the mapping in `docker-compose.yml` to `"127.0.0.1:${APP_PORT:-4000}:4000"` or block the port in your firewall.

## How do I set up email with Resend, and can I use SMTP? [#how-do-i-set-up-email-with-resend-and-can-i-use-smtp]

Customermates sends email only through [Resend](https://resend.com); there is no SMTP option. Verify your sending domain in Resend, create an API key, and set:

- `RESEND_API_KEY`: the Resend API key.
- `RESEND_OPERATOR_EMAIL`: the sender address, on a domain verified in Resend. Every email goes out as `Customermates <RESEND_OPERATOR_EMAIL>`. The same address receives a "New User Registration" email when someone saves the profile step of the wizard (see [Who can sign up](#who-can-sign-up-on-my-instance)) and the messages sent through **Send feedback** in the personal menu.

The app emails verification links, password resets and invitations. Without a key, saving the profile step fails, so nobody can finish registering or join a workspace. If Resend rejects the emails, new users can use their account for 24 hours and are then held on **Email Verification** until they verify, **Forgot password?** sends nothing, and email invitations fail; the **Share link** tab of **Invite User** still works. Rejected sends do not appear in the app logs, so if emails are not arriving, check that the sender domain is verified and look for rejected sends in the Resend dashboard.

## How do I create the first account on my instance? [#how-do-i-create-the-first-account-on-my-instance]

Open `<BASE_URL>/auth/signup` and register with email and password under **Create account**, or with Google or Microsoft if you configured them. On the next screen choose **Create a new workspace**. The wizard's first step asks for your first name, last name and country and creates the workspace; you can skip the remaining steps and close the wizard with **Finish**. The account that creates the workspace gets the built-in **Admin** role, which has every permission.

Click the verification link in the email within 24 hours. An account that is still unverified 24 hours after registering is held on **Email Verification**, where **Resend verification email** sends a fresh link.

Then open [Members](app:settings/members), invite teammates with [Add](app:settings/members?focus=add), approve them there once they have registered, and set what they may do in [Roles](app:settings/roles); see [Members and roles](/docs/app-company).

## Who can sign up on my instance? [#who-can-sign-up-on-my-instance]

Anyone who can reach your `BASE_URL` can register; registration cannot be switched off. A new user who chooses **Create a new workspace** gets a separate workspace with its own **Admin**, isolated from yours but stored in your database, and the app offers no way to delete a workspace. A "New User Registration" email goes to `RESEND_OPERATOR_EMAIL` when someone saves the wizard's profile step, and for a Google or Microsoft sign-in also when someone signs in before saving it. Someone who registers with email and password but never saves that step sends none, and the notification only arrives if Resend accepts it, so it is not a complete record of sign-ups.

If the instance should serve one team only, limit who can reach it, for example with a VPN, an IP allowlist or authentication at the reverse proxy; MCP and REST clients then need the same access.

Teammates join through an invitation: [Add](app:settings/members?focus=add) on [Members](app:settings/members) opens **Invite User** with a **Share link** tab and a **Send emails** tab. New members wait with status **Waiting for approval** until a member with **Edit** on **Users & Roles** opens them, gives them a **Role** and sets **Status** to **Active**.

## Can users sign in with Google or Microsoft? [#can-users-sign-in-with-google-or-microsoft]

Yes, once you configure them. Register an OAuth client with Google, or an app registration in Microsoft Entra ID, with the redirect URI `<BASE_URL>/api/auth/callback/google` or `<BASE_URL>/api/auth/callback/microsoft`. The Microsoft provider uses the `common` endpoint, so register the app for accounts in any organizational directory.

In `.env`, remove the `#` in front of the lines for the providers you use, fill in `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, or `AZURE_AD_CLIENT_ID` and `AZURE_AD_CLIENT_SECRET`, then run `docker compose up -d`. The Compose file passes all four values to the app; if your `docker-compose.yml` does not list them yet, fetch it again with the `curl` command from the installation steps. A provider appears only when both of its values are set: the sign-in page then shows **Continue with Google** or **Continue with Microsoft**, and the sign-up page **Register with Google** or **Register with Microsoft**. Enterprise SSO over SAML is not implemented.

## How do I connect an AI client to my self-hosted instance? [#how-do-i-connect-an-ai-client-to-my-self-hosted-instance]

The MCP endpoint is `<BASE_URL>/api/v1/mcp`, for example `https://crm.example.com/api/v1/mcp`. There are two ways to authenticate:

- **API key** in the `x-api-key` header, for clients that run on your machine: Claude Code, Claude Desktop, Codex, Cursor and Gemini CLI. Create the key with [Add](app:settings/api-keys?focus=generate) on [API keys](app:settings/api-keys); **Quick connections** there shows the setup snippet with the address you opened the app under. The client only has to reach the URL, so a local network address works. See [Connect CLI and editor clients](/docs/connect-cli).
- **OAuth sign-in**, for clients that connect from their provider's cloud, such as a Claude custom connector. These need a `BASE_URL` that is reachable from the internet over HTTPS. See [Connect Claude and ChatGPT](/docs/connect-custom-connector).

The hosted in-app Assistant is cloud-only: Mate is not available on self-hosted instances. External MCP uses your own AI provider. Enterprise SSO and white-labeling are not implemented in either deployment model.

## How do I turn on address suggestions? [#address-lookup]

Address fields work without any setup: people enter street, postal code, city and country themselves, and nothing leaves your server. Set `ADDRESS_LOOKUP_URL` to a [Photon](https://github.com/komoot/photon) service to add **Search address** and **Check address** to address fields: the suggestions come from OpenStreetMap, and an address picked from them is stored as verified. Your server sends the service only the search text or the address being checked and the person's language, so the service never sees people's IP addresses or sessions. Each app container allows each person 30 lookups in 10 seconds and answers identical lookups from its own cache for 10 minutes.

- **komoot's public service:** `ADDRESS_LOOKUP_URL=https://photon.komoot.io` uses the free Photon service of komoot GmbH in Germany, meant for moderate use. Your server then sends the search texts to komoot.
- **Your own Photon:** download the Photon jar from its [releases](https://github.com/komoot/photon/releases/latest), save it as `photon.jar`, and download a search index for the whole planet or one country from [download1.graphhopper.com/public](https://download1.graphhopper.com/public/) that matches the Photon version. Photon needs Java 21 or later and memory to match the index: for the planet index, about 95 GB on disk, Photon recommends at least 64 GB of RAM, while a country index needs far less. Unpack the index so that `photon_data` sits next to the jar in `/srv/photon`, then start Photon in the network of the Compose project, which is named after its folder, here `customermates`, with a Java heap (`-Xmx`) that fits your index:

```bash
docker run -d --name photon --restart unless-stopped \
  --network customermates_default \
  -v /srv/photon:/photon -w /photon \
  eclipse-temurin:21-jre \
  java -Xmx4g -jar photon.jar serve -listen-ip 0.0.0.0
```

Then set `ADDRESS_LOOKUP_URL=http://photon:2322` in `.env` and run `docker compose up -d`. Customermates calls only the configured host and never follows a redirect. A host name that resolves to a private address is accepted only when the configured host is itself private: an IP address in a private range, `localhost`, a name without a dot such as `photon`, or a name under `.local`, `.internal`, `.lan` or `.home.arpa`. When the service does not answer within 2 seconds, people see that address search is unavailable and can still type the address. Unset `ADDRESS_LOOKUP_URL` to turn the suggestions off again; stored addresses keep their verification.

## How do I update a self-hosted installation? [#how-do-i-update-a-self-hosted-installation]

Take a backup first, then pull the new images and recreate the containers:

```bash
docker compose pull
docker compose up -d
docker compose ps
```

The `latest` tag is rebuilt from the main branch whenever it changes, so every pull can bring new features and database migrations. Migrations run at every start and only move forward: starting an older image after a migration is not a safe rollback. To roll back, restore the backup taken before the update and start the previous image by its `sha-` tag. `docker compose pull` also refreshes `postgres:16-alpine` within PostgreSQL 16.

To decide when updates happen, pin the image in `docker-compose.yml` to a build tag instead of `latest`. Every image is also tagged `sha-` followed by the short commit id, for example `ghcr.io/customermates/customermates:sha-<commit>`.

## How do I apply .env changes? [#apply-env-changes]

Run `docker compose up -d`. It recreates the containers whose configuration changed, so they start with the new `.env` values. `docker compose restart` keeps the old environment and does not apply `.env` changes.

## Where are the logs, and how do I troubleshoot? [#where-are-the-logs-and-how-do-i-troubleshoot]

```bash
docker compose logs -f app
docker compose logs -f postgres
docker compose ps
docker compose exec app sh
```

On a self-hosted instance, the app writes its logs to the container output. Background jobs such as webhook deliveries run inside the app container through a PostgreSQL-backed queue in the same database; there is no separate worker service. The published image turns off Next.js telemetry and sets no error-reporting address. Errors the app writes to its output appear only in these logs. Errors it only reports to an error-reporting service, such as an email Resend rejected, are not recorded anywhere, so check the Resend dashboard for failed sends.

## Where are files stored when I self-host? [#file-storage]

File fields keep their files in the PostgreSQL database by default, so the `pg_dump` backup includes them. A file can be at most `FILE_MAX_UPLOAD_BYTES` bytes, 26214400 (25 MB) when unset; beyond that, a self-hosted workspace has no storage limit other than your disk. For many or large files, keep them in an S3-compatible bucket such as AWS S3, MinIO, Cloudflare R2 or the object storage of Hetzner or OVH:

- `FILE_STORAGE_DRIVER=s3`, plus `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` of a private bucket.
- `S3_ENDPOINT` for every provider other than AWS, for example `https://fsn1.your-objectstorage.com`, and `S3_REGION` when the provider needs one (`us-east-1` when unset).
- `S3_FORCE_PATH_STYLE=true` for MinIO and other servers that address the bucket in the path instead of the host name.

Browsers send new files straight to the bucket, so its CORS rules must allow `PUT` with the `Content-Type` header from your `BASE_URL`. Downloads always pass through the app, which checks access first. A file stays where it was uploaded: after a switch to `s3`, earlier files remain in the database and still open, and the S3 variables must stay set as long as the bucket holds files. Back up the bucket together with the database. The daily `/api/cron/lifecycle` call deletes files that were removed from records 30 days ago and uploads that were never saved, see [Which scheduled jobs must I run?](#scheduled-jobs).

## How do I create and restore database backups? [#backups]

All data lives in the PostgreSQL database: records, users, settings, the Activity log and the background job queue, and the files of file fields unless `FILE_STORAGE_DRIVER` is `s3` (then back up the bucket as well). The app container keeps no data. Back up the database with `pg_dump` through the Postgres container, whose port the Compose file does not publish:

```bash
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  | gzip > backups/customermates-$(date +%Y%m%d).sql.gz
```

Run it daily from a scheduler such as cron and copy the files to separate or off-site storage. Keep a copy of `.env` with them, stored securely and out of source control: restoring with a different `BETTER_AUTH_SECRET` signs everyone out.

To restore, stop the app, replace the database with an empty one, load the dump and start again:

```bash
docker compose stop app
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
gunzip -c backups/customermates-20260923.sql.gz \
  | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose up -d
```

Test the restore regularly on a separate machine. Moving to a new PostgreSQL major version, which the Compose file pins at 16, also needs a dump and a restore into the new version.

## Which scheduled jobs must I run? [#scheduled-jobs]

The cloud calls two maintenance endpoints on a schedule; a self-hosted instance runs them only when you call them. Without the daily one, items in [Trash](/docs/app-trash) are never deleted permanently after their 30 days.

- `/api/cron/lifecycle`, once a day: deletes Trash items whose 30 days have passed, files removed from records 30 days ago and uploads that were never saved, and runs the other daily housekeeping. Its jobs for cloud trials and subscriptions find nothing on a self-hosted instance.
- `/api/cron/record-deliveries`, every 5 minutes (optional): starts due webhook deliveries, event processing, text extraction of attached files and other background record work that no running job picked up, for example after a container restart.

Both answer HTTP `401` unless the app has a `CRON_SECRET` and the request sends it as `Authorization: Bearer <secret>`. The template has a commented `CRON_SECRET` line next to `BETTER_AUTH_SECRET`, and the Compose file passes it to the app; if your `docker-compose.yml` does not list `CRON_SECRET` yet, download it again with the `curl` command from the installation steps. Uncomment the line, or add it to an `.env` created before it existed, set a long random value, for example from `openssl rand -hex 32`, run `docker compose up -d`, and schedule the calls on the host, for example with `crontab -e`:

```bash
0 3 * * * curl -fsS -H "Authorization: Bearer YOUR_CRON_SECRET" http://localhost:4000/api/cron/lifecycle
*/5 * * * * curl -fsS -H "Authorization: Bearer YOUR_CRON_SECRET" http://localhost:4000/api/cron/record-deliveries
```

Use your `APP_PORT` instead of `4000`. A successful call answers `{"ok":true,...}`.

## How do I reset all data? [#how-do-i-reset-all-data]

```bash
docker compose down -v
docker compose up -d
```

`-v` deletes the PostgreSQL volume with every workspace, user and record on the instance. This cannot be undone, so take a backup first if you might need the data. The next start creates an empty database, and the first person to register creates a new workspace.
