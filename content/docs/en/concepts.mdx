Customermates tracks five record types, lets each one carry user-defined fields, links them to each other through typed relationships, and emits webhooks whenever any of that changes.

## Which five record types exist?

| Record type | What it represents | Built-in fields |
|---|---|---|
| **Contact** | A person | firstName, lastName, channel identifiers (email, phone, LinkedIn, WhatsApp, Instagram, Telegram), notes |
| **Organization** | A company | name, notes |
| **Deal** | A sales opportunity | name, totalValue and totalQuantity (derived from linked services), weightedValue, notes |
| **Service** | A product or offering attached to a deal | name, amount, notes |
| **Task** | A todo item | name, assignees, notes |

Each record has `id`, `createdAt`, `updatedAt`, and supports markdown `notes`. Everything else is either a relationship to another record or a custom column value. There are no fixed status, stage, priority, or due-date fields on any record type; tasks have no built-in due date either. Use custom columns for those, and call `get_record_schema` to read the columns that exist in a given workspace.

## How do relationships link records?

Relationships are typed and many-to-many. A contact belongs to zero or more organizations, deals, and users. A deal belongs to zero or more contacts, organizations, and services (with quantities), plus assignees.

| From to | Example |
|---|---|
| Contact to Organization | "Max works at Initech" |
| Contact to Deal | "Max is a stakeholder on the Q2 contract" |
| Organization to Deal | "The Q2 contract is with Initech" |
| Deal to Service (with quantity) | "5 hours consulting plus 1 setup fee" |
| Contact / Organization / Deal / Service / Task to User | "Assigned to Julia" |
| Task to Contact / Organization / Deal / Service | "Follow up on the Q2 contract" |

Tasks link to users, contacts, organizations, deals, and services. Over MCP, links change through `manage_record_links`, with one exception: `update_deals` keeps `services` (deal-to-service links with quantities) on its update schema. Every other relation changes only through `manage_record_links`; the other update tools never touch links. Over REST, sending a relation array replaces that whole set, and `null` or `[]` clears it.

## What are custom columns?

The default schema covers the basics. For anything else, add a custom column.

Ten types:

| Type | Use for |
|---|---|
| **Text** (`plain`) | Free-text values |
| **Date** (`date`) | Calendar dates (renewal, next touch, a task's due date) |
| **Date Range** (`dateRange`) | A start and end date |
| **Date & Time** (`dateTime`) | Timestamps |
| **Date & Time Range** (`dateTimeRange`) | A start and end timestamp |
| **Currency** (`currency`) | Money amounts, stored with an ISO currency code |
| **Single Select** (`singleSelect`) | A value from a fixed option list |
| **Link** (`link`) | One or more URLs |
| **Email** (`email`) | One or more email addresses |
| **Phone** (`phone`) | One or more phone numbers |

Single Select columns are how you model your own workflows. A deal "Stage" or a task "Priority" is a Single Select column you define, with the options you choose, per workspace. A board view can then group records by any Single Select column, and the value is what filters and tools compare against.

Custom columns are first-class in filters, widgets, and the MCP surface: `manage_custom_columns` creates and updates them, and every record tool reads and writes their values through `customFieldValues` with the column id from `get_record_schema`.

### How does a weighted pipeline work?

A workspace can mark one Single Select deal column as the weighting column and give each of its options a weight in percent, for example Qualified 20 and Proposal 60. Each deal then carries `weightedValue` = its total value multiplied by the weight of its current option, or no weighted value when the option carries no weight. `list_records` returns the sum of both values across every matching deal, and a dashboard chart can aggregate by deal weighted value.

You set this up on **My Company › Settings**. Choose the Single Select deal field in **Deal stage field** (named after your term for deals, for example **Project stage field**; **Not configured** turns weighting off), then enter a win probability from 0 to 100 percent next to each of its options. Below, **Total pipeline** and **Weighted pipeline** preview the result with the probabilities you entered, over the deals you can read; when some of those deals have no stage selected, a line starting **Not weighted · no** followed by your field's name shows their value. Saving recalculates the weighted value of every deal. A new workspace starts with its deal **Stage** field selected and probabilities already filled in. On **My Company › Settings**, choosing the field and entering probabilities needs a role with **Manage** set to **Yes** on the **Company** row, or the **Admin** role. The same probabilities appear in the **Probability** column when you edit the stage field's options, where they are editable only with **Manage** set to **Yes** on both the **Company** and **Deals** rows, or with the **Admin** role. Over MCP, `manage_custom_columns` sets them as each option's `weight` on the stage field; like any field update, this needs **Manage** set to **Yes** on the **Deals** row (send a weight with every option, because an update replaces the whole option list). No tool chooses which field is the stage field. See [My Company](/docs/app-company).

## What are widgets?

Widgets are dashboard charts driven by live data. You pick a record type, a group-by axis (a linked record type, a custom column, or none), an aggregation (count, deal value, deal quantity, or deal weighted value), and a display type (vertical or horizontal bars with or without labels, doughnut, or radar). Filters narrow the data set. An activity-timeline widget shows a feed instead of a chart. See the [Dashboard](/docs/app-dashboard).

## What are webhooks?

Every write emits a domain event: `contact.created`, `deal.updated`, `task.deleted`, and so on. You subscribe by URL and event list. Each update delivery includes the changed record plus a `changes` map showing what moved from what to what, so subscribers can act on diffs without polling.

See [Webhooks](/docs/webhooks) for the full event catalog and payload shape.

## What are notes?

Notes are per-record markdown. They render through a Tiptap editor in the UI and are plain markdown everywhere else. You can replace them or append to them via `update_record_notes` with the matching `mode`.

## Who are users, roles, and the company?

Users are your teammates, listed under **My Company › Members**. Roles are defined per workspace under **My Company › Roles** and control what each user can read and write: each row of the role editor sets **Manage** (**Yes** covers creating, updating and deleting) and **Read access** (**All**; **Assigned**, which limits a member to what is assigned to them or owned by them; or **None**), where the row offers them. The built-in **Admin** role has full access and cannot be edited or deleted. The company is the tenant. Every record lives inside one company, and cross-tenant access is not possible.
