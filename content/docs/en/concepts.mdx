---
title: "CRM data model: records, links, and calculations"
description: "How starting and custom record types, fields, links, deal totals, permissions, widgets, and webhooks work together."
---

Customermates stores CRM information as configured record types. Contacts, Organizations, Deals, Services, and Tasks are the five starting configurations. A workspace can add Projects, Applications, or other types without a new database table or application release. Each record has a stable type ID and record ID; labels can change without changing references. A saved view presents records of a type and does not duplicate them.

## Which record types exist, and which does a workspace start with? [#which-five-record-types-exist]

| Starting type | Purpose | Initial behavior |
| --- | --- | --- |
| Contact | Person | Name, indexed channels, notes, assignments |
| Organization | Company or account | Name, notes, assignments |
| Deal | Sales opportunity | Name, service line items, calculated value and quantity, optional weighted value |
| Service | Offering or catalog item | Name, live unit price |
| Task | Work item | Name, assignments, status option field; membership-approval tasks retain protected actions |

The starting templates and custom types use the same engine. Fields, relationships, and presentation defaults can be extended. Enable Channels on any type to link indexed identifiers to its records; one identifier can link to several records. Ordinary phone and email fields do not participate in matching. Membership-approval actions remain protected. Read the current type and field IDs with `discover_record_types` and `get_record_model`.

## How is a deal's total value calculated? [#how-is-a-deals-total-value-calculated]

A deal has embedded service line items. Each line has a service, quantity, pricing mode, and an effective unit price. **Line amount = quantity × effective unit price**. Deal value is the sum of line amounts, and deal quantity is the sum of line quantities. The same service can appear in more than one line. Live pricing follows changes to the linked service price; saved pricing keeps the captured unit price. Money uses decimal arithmetic, and amounts in different currencies are not silently added.

The total is a configured rollup and formula, so a schema manager can change it or make a value manual after previewing dependent widgets and records. A missing input, a restricted result, zero, and a calculation error are different states. See [weighted pipeline](#how-does-a-weighted-pipeline-work).

## How do relationships link records, for example a contact to several organizations? [#how-do-relationships-link-records]

Relationships are definitions between configured types. Each direction has its own label, and cardinality can permit one or several records at either end. For example, one contact can link to several organizations, and a project can link to contacts and deals. Both record pages show a permitted link. A deal's service lines are embedded records linked to both their deal and service; they also carry quantity and pricing fields.

The link between a deal and a service is stored as a line record with its own quantity. The same service can appear twice on one deal with different quantities or saved prices.

In the record form, a relationship appears as a labeled relation field. Pick the records, then save.

The backend enforces endpoint types, workspace ownership, cardinality, duplicate prevention, and deletion behavior. A multi-record lookup or rollup must choose an aggregation such as sum or count. MCP clients use `mutate_crm_record` with stable relation IDs from `get_record_model` to link or unlink. Every record reference contains both `typeId` and `recordId`.

## What are fields, and which field types are there? [#what-are-custom-columns]

Every type starts with seeded fields, and a workspace can add its own custom fields; table views show fields as columns. A field has a **value type** and a **behavior**. The value types are text, rich text, number, currency, boolean, date, date and time, date range, date and time range, select, email, phone, URL, and member. Text, email, phone, and URL fields can allow multiple values. A select field is either a **single choice** or a **multiple choice**, which stores an ordered list of option IDs, each at most once. Select options have stable IDs and editable labels. Switching a single choice to a multiple choice keeps every value; switching back is only allowed while every record holds at most one option.

Behaviors are manually entered input, formula, lookup through a relationship, rollup over linked records, and snapshot captured at a configured event. Formulas use a validated, deterministic expression language with typed operations; they cannot run arbitrary JavaScript or SQL. The engine rejects cycles, incompatible values, and excessive work before accepting a definition. Custom fields can participate in filters, sorting, views, widgets, routines, and assistant operations where access permits it.

## How do I add, change or delete fields, including the deal stage field? [#how-do-i-add-change-or-delete-a-custom-column]

Open **Configure** (`/configure`), select a list in the left rail, and add or edit its fields; **Add** in the top bar also creates calculations, relationships and activity connections, and **Map** shows how lists connect. The field editor opens beside the list and offers the value type, entered or calculated behavior, options, formatting, and a readable calculation editor. A change previews its affected records, views, widgets, routines, and other formulas before it is applied. Incompatible changes are blocked until their dependencies are resolved. Archiving a type removes it from ordinary use without silently deleting its records. Only an archived list or field can be deleted permanently, from the list menu or the field editor: the confirmation counts the records, values, links, relationships, saved views and role grants it removes, lists any definitions that still depend on it, and asks you to type its name.

To add a custom field to contacts, select the **Contacts** list in **Configure** and choose **Add** → **Field**; every other type works the same way. To edit or delete a custom field, open it in the field editor and change its settings or switch on **Archive field**.

Schema editing is separate from record editing. Administrators can delegate it; expanding role access still requires role-management authority. Over MCP, `get_record_model` reads the schema and `configure_record_model` previews and applies a change with an expected revision and idempotency key. A stale revision requires a fresh preview.

**Link:** `/configure`. **Mate:** navigate to `nav-configure-records`; the assistant can use `configure_record_model` for the same validated change.

## How does a weighted pipeline work? [#how-does-a-weighted-pipeline-work]

A configured select field can represent deal stages. Each stage option can carry a probability from 0 to 100 percent. **Weighted deal value = deal value × stage probability / 100**. A 2,600 deal at 60 percent contributes 1,560; a zero-percent stage contributes zero, while a missing probability leaves the weighted value absent. A changed live service price recalculates dependent values; a saved quote price does not.

A schema manager edits stage options, their probability metadata, or the weighted-value formula in **Configure**. The dependency preview shows the effect on existing deals and widgets. A published summary of restricted inputs requires explicit administrator approval; otherwise readers who cannot access the inputs see a restricted value rather than a leaked total.

**Link:** `/configure`. **Mate:** use `get_record_model` and `configure_record_model` after reviewing the change preview.

## What are widgets? [#what-are-widgets]

A chart widget selects a source type, an aggregation and value field, optional filters, grouping, and display style. For example, it can sum the calculated Deal Value field by Stage or count Projects by Owner. A measure sums once at its declared record grain; a deal linked to two organizations may be fully attributed to both groups, so grouped totals can exceed the distinct overall total. Service contribution charts use line items as their grain. Widgets honor the same record and calculated-value permissions as the list. Activity widgets show a feed instead of an aggregate. See [Dashboard](/docs/app-dashboard).

## What are webhooks? [#what-are-webhooks]

A workspace can subscribe a webhook or routine to record events from one or more configured types, optionally filtered by stable field and type IDs. Delivery is queued after the record transaction commits. A failed HTTP delivery can retry with the same event and delivery identity; external delivery is not guaranteed exactly once. Permissions are checked again at send time, and historical delivery previews are redacted for the reader. See [Webhooks](/docs/webhooks).

## What are notes, and are they markdown? [#what-are-notes]

Notes are rich text attached to a record. The editor stores a validated document rather than a plain markdown string. The generic record API reads the document and writes it as a typed rich-text field value. A plain-text or markdown representation in another surface is a conversion of that document, not a second source of truth.

## Who are users, roles, and the company, and what does Assigned read access mean? [#who-are-users-roles-and-the-company]

Users are workspace members. Roles grant create, read, update, and delete access per configured type. **All** read access covers every permitted record of that type; **Assigned** covers records assigned to that member; **None** grants no read access. Updating and deleting also require access to the specific record. Data-model management is a separate permission and does not grant record access or the right to administer roles. New types start with restricted access. Every query, calculation, export, widget, and assistant tool applies workspace and reader permissions.
