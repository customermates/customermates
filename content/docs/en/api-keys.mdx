API keys authenticate Model Context Protocol (MCP) and REST clients against your Customermates CRM. Create one key per client, store it in an environment variable, and delete it when the device or the teammate that held it goes away.

## How do I create an API key? [#how-do-i-create-an-api-key]

Open [API keys](app:settings/api-keys) in Settings and click [Add](app:settings/api-keys?focus=generate). The **Add an API key** dialog offers two routes:

- **Standard API key**: enter a **Name** that says where the key is used, for example `Claude Desktop, personal laptop` (up to 255 characters), optionally pick a date under **Expires in**, and click **Save**. The key is shown once under **API key created successfully**; copy it before you close the dialog.
- **Quick connections**: pick **Claude**, **ChatGPT & Codex**, **Cursor** or **Gemini**, then the setup that matches where you use it. For a local setup (**Claude Code or Desktop**, then **Claude Code** or **Claude Desktop**; **Codex CLI or IDE**; Cursor or Gemini), click **Create API key**: the dialog creates the key and shows that client's setup snippet with the key already filled in. **Claude account** and **ChatGPT App** connect through OAuth instead and create no key. Click **Done** when you are finished.

A key created by **Quick connections** is named after its client (`Claude Code`, `Claude Desktop`, `Codex`, `Cursor` or `Gemini`) and expires 365 days after creation; you cannot choose another name or date there. The dialog shows the expiry below the setup snippet. The AI step of the onboarding wizard creates its keys the same way. A key's name and expiry cannot be changed after it is created.

Keys belong to the user who created them and inherit that user's permissions.

## Who can create and see API keys? [#who-can-create-and-see-api-keys]

The API keys page follows the **API & Webhooks** row of your role, which a member with **Edit** on **Users & Roles** sets under [Roles](app:settings/roles):

- **Read access** **All** shows API keys in Settings and lists your own keys. With **None**, the entry is hidden and the page cannot be opened.
- **Create** adds the **Add** button, and **Delete** lets you delete keys. Without them, you can see keys you already have but cannot create or delete any.

A new role starts with no checkbox ticked and **Read access** **None**, so out of the box only members with the built-in **Admin** role can create API keys. The same row also opens [Webhooks](app:settings/webhooks) and its deliveries, so granting it for API keys also lets the member see every webhook of the workspace and, with **Create**, **Edit** or **Delete**, change them.

Everyone sees only their own keys. Nobody, including the **Admin** role, can list or delete another member's keys. No assistant or MCP tool creates, lists or deletes API keys; they are managed only on the API keys page, and the hosted assistant can at most open it for you.

The custom connector for Claude and ChatGPT signs in over OAuth and needs no API key. Like every MCP connection, it needs **Read access** **All** on **API & Webhooks** ([MCP endpoint](/docs/mcp#the-endpoint)). See [Connect with a custom connector](/docs/connect-custom-connector).

## Which permission does each API key action need? [#which-permission-does-each-api-key-action-need]

Every way of managing keys checks the **API & Webhooks** row of your role, including the requests the API keys page sends to `/api/auth/api-key/`: creating a key needs **Create**, changing one **Edit**, deleting one **Delete**, and reading or listing your keys **Read access** **All**. A request that is not signed in answers `401`, a role without the permission answers `403` with `PERMISSION_DENIED`, and a member whose **Status** is **Inactive** gets `403` with `USER_INACTIVE`. These checks cover managing keys only; what a call made with a key may do follows its owner's role, see [What permissions does a key have](#what-permissions-does-a-key-have).

## How do I use a key, and which header does it go in? [#how-do-i-use-a-key]

Send it in the `x-api-key` header on every request, here to the MCP endpoint `<BASE_URL>/api/v1/mcp`, where `<BASE_URL>` is the address you open Customermates at:

```bash
curl -H "x-api-key: $CUSTOMERMATES_API_KEY" \
     -H "Content-Type: application/json" \
     -H "Accept: application/json, text/event-stream" \
     <BASE_URL>/api/v1/mcp \
     -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

The `Accept: application/json, text/event-stream` header is required by the MCP streamable HTTP transport; without it the endpoint returns `406 Not Acceptable`. For MCP clients the key goes into the client's configuration, see [CLI and editor clients](/docs/connect-cli) and [ChatGPT with an API key](/docs/connect-custom-connector#chatgpt).

The REST API takes the same header. This call lists the record types you can access:

```bash
curl -H "x-api-key: $CUSTOMERMATES_API_KEY" \
     -H "Content-Type: application/json" \
     <BASE_URL>/api/v1/model/discover \
     -d '{}'
```

Every REST operation, with its request and response, is in the [API reference](/docs/openapi).

## What does a failed REST call return? [#what-does-a-failed-rest-call-return]

Every REST endpoint answers a refused call with the same JSON body: an `error` object holding the `kind` and the `issues` that MCP returns in `_meta.failure` (see [when a call is refused](/docs/mcp#when-a-call-is-refused)).

```json
{
  "error": {
    "kind": "not_found",
    "issues": [{ "code": "custom", "path": [], "message": "Webhook ID not found or not accessible.", "customCode": "webhookNotFound" }]
  }
}
```

The HTTP status follows `error.kind`: `validation` 400, `authentication` 401, `authorization` 403, `not_found` 404, `conflict` 409, `unavailable` 422 and `rate_limit` 429. Each issue names the field `path` it belongs to and, where one applies, a stable `customCode`. `error.retryable` is `true` when a messaging provider refused a call that can succeed later unchanged; a `429` without it can be retried as well, see [the next section](#what-should-a-client-do-on-429). Branch on `kind` and `customCode` rather than on `message`, which is text for people. An unexpected server error answers 500 without this body.

## What should a client do when a call returns 429? [#what-should-a-client-do-on-429]

`rate_limit` (HTTP `429`) means the call could not run now and can succeed later unchanged. A messaging channel at its provider's limit answers with `customCode` `unipileRateLimit` and says when to try again ([messaging rate limits](/docs/messaging-rate-limits)). When Customermates itself is overloaded, for example when a database transaction or the connection pool times out, or a write waits more than a few seconds behind another change to the workspace such as a large import, the call answers `429` without a `customCode` and with the message `The service is busy. Retry the request shortly.`. MCP tools return the same `rate_limit` kind in `_meta.failure`, and the app shows that the workspace is busy so you can try again.

A REST `429` carries a `Retry-After` header with the seconds to wait: honour it first and retry no earlier. Without one, retry after a pause that grows with each attempt, for example 1, 2, 4 and 8 seconds plus a little random jitter, and give up after a few attempts. Do not retry in a tight loop or send more calls in parallel, which keeps the service busy. Send a write again with the same `idempotencyKey`, so a change that went through is not applied twice.

## How long does a key last, and do keys expire? [#do-keys-expire]

A **Standard API key** expires only if you pick a date under **Expires in**; the default, **Never expires**, keeps it valid until you delete it. A date must lie between 1 and 365 days ahead. A key from **Quick connections** (a quick connection key), including those from the onboarding wizard, is valid for 365 days: it always expires 365 days after creation. Expiry cannot be extended: before it passes, create a new key and update the client. Each key card shows **Created at**, **Expires at** (**Never** when unset) and **Last used**.

## How do I revoke, delete or rotate a key? [#how-do-i-revoke-delete-or-rotate-a-key]

On [API keys](app:settings/api-keys), click the key's card and choose **Delete**; after you confirm, the key stops working immediately. Deleting needs **Delete** on **API & Webhooks**. There is no separate rotate or revoke action: to rotate, create a new key, update every client that used the old one, then delete the old key.

Rotate when a device that held the key is lost or compromised, when a teammate with access leaves, or when you suspect the key leaked. One key per client lets you delete one client without breaking the others; the activity log still names the user, not the key. Keep keys in an environment variable or a password manager, never in a config file you commit.

Only the owner can delete a key. To stop the keys of a member who leaves, open [Members](app:settings/members), open the member, set **Status** to **Inactive** and click **Save**. This needs **Edit** and read access **All** on **Users & Roles**; you cannot deactivate yourself or the last active **Admin**. Every call with that member's keys that reads or changes workspace data is then refused. Taking **Read access** **All** on **API & Webhooks** away from their role also stops their keys, for MCP and REST alike; see [What permissions does a key have](#what-permissions-does-a-key-have).

## What is the key format, and how long can a key name be? [#what-is-the-key-format]

A key's **Name** is 1 to 255 characters long. Keys are 64 characters of ASCII letters (`a-z A-Z`), generated by the better-auth API key plugin and stored hashed. The full key is shown only at creation and cannot be displayed again.

## What permissions does a key have, and can I restrict its scope to read-only? [#what-permissions-does-a-key-have]

Everything its owner can do, and nothing more. There is no per-key permission scoping, so a key cannot be limited to read-only access. Every call is checked against the owner's current role, so a change to that role, for example moving the member from the **Admin** role to a custom role with fewer rights, applies to their keys on the next call. If the owner's **Status** is **Inactive**, every call with their keys that reads or changes workspace data is refused.

A key, like an MCP OAuth token, also works only while its owner's role has **Read access** **All** on **API & Webhooks**, checked on every call, including for tokens refreshed later. Without it, MCP answers `403` with `error: insufficient_permissions`, and REST answers `403` with `kind` `authorization` and `customCode` `insufficientPermissions`. Signed-in use of the web app is not affected.
