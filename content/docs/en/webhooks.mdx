Customermates sends a JSON POST to your endpoint whenever subscribed data changes. You choose the events and provide the URL. Failed deliveries can be re-sent from the UI or through MCP. When the webhook has a secret, deliveries are signed with HMAC-SHA256 over the raw request body. Every event and its payload shape is listed in the catalog at the end of this page.

## What are webhooks for?

Webhooks let other systems react to CRM changes without polling.

- Push new contacts into an email sequencer.
- Open a ticket in a support tool when a deal changes state.
- Trigger a finance workflow when a deal is marked as closed.
- Sync records into a data warehouse in near real time.

## How do I add a webhook? [#how-do-i-create-a-webhook]

**UI:** In the sidebar, expand **My Company**, open **Webhooks** and click **Add** (on narrow screens the button shows only a plus icon). Fill in the **Webhook** dialog and click **Save**.

| Field | What it does |
|---|---|
| **URL** | Required. The endpoint that receives a `POST` for every subscribed event. A URL entered without a scheme is saved with `https://` in front. |
| **Description** | Optional, up to 500 characters. Shown in the list. |
| **Events** | Required. One or more events from the catalog at the end of this page. |
| **Secret** | Optional, 1 to 256 characters. When set, deliveries carry a signature made with it (see "How do I verify the signature?" below). If an older webhook points at the same URL, that webhook's secret applies instead, and without one deliveries go out unsigned (see "One URL, one configuration" below). |
| **Custom headers** | Optional. One `Name: value` per line (see "Custom headers and body templates" below). |
| **Body template** | Optional JSON document that replaces the standard envelope. |
| **Enabled** | On by default. A disabled webhook receives no deliveries and keeps its configuration, so you can pause it without deleting it. |

To change a webhook, click its row, edit the dialog and click **Save**. To remove it, click the trash icon (**Delete**) at the top of the dialog and confirm; its past deliveries stay under **Recent Deliveries**. The list shows each webhook's **URL**, **Description**, **Events**, **Status** (**Enabled** or **Disabled**), **Created at** and **Updated at**. The search box matches the URL, and the filters cover the creation and update dates.

**MCP:** `manage_webhooks` with `action: "create"`, plus `url`, `events[]`, and optional `description`, `secret`, `headers`, `bodyTemplate`, `enabled`. The hosted assistant uses the same tool, and it can also open **Webhooks** or **Recent Deliveries** for you and point at the **Add** button.

```json
{
  "url": "https://hooks.example.com/customermates",
  "events": ["contact.created", "contact.updated", "deal.updated"],
  "secret": "use-a-random-string-from-a-password-manager",
  "enabled": true
}
```

Use an HTTPS endpoint. A plain `http://` URL is accepted for any host as long as the webhook has no custom headers. A webhook with custom headers must use `https://`, or `http://` on `localhost`, `127.0.0.1` or `::1`, because headers usually carry a credential. This rule is checked when you save and again before every delivery.

## Who can see and change webhooks?

Access is set by the **API & Webhooks** row of the role editor under **My Company** → **Roles**. The same row also controls **My Profile** → **API & Connectors**, so a role that may manage its own API keys may also manage every webhook in the workspace.

| Role setting on **API & Webhooks** | What members with that role can do |
|---|---|
| **Read access** **None** (the default for a new role) | **Webhooks** and **Recent Deliveries** are hidden in the sidebar. Opening their address directly leads to the Dashboard. |
| **Read access** **All**, **Manage** **No** | Open both pages, open every webhook's dialog read-only (including its **Secret** and **Custom headers** values), and open **Event Details** for every delivery. |
| **Read access** **All**, **Manage** **Yes** | Everything above, plus add, edit and delete webhooks and resend deliveries. |

The **Admin** role can do everything. Webhooks have no plan restriction: they work on every Cloud plan and in a self-hosted installation. The same permissions apply to `manage_webhooks` through MCP and in the hosted assistant. In the hosted assistant, deleting a webhook or resending a delivery asks for your approval first.

## What does the payload look like?

Every delivery is a `POST` with `Content-Type: application/json` and the same envelope:

```json
{
  "event": "<event-name>",
  "data": {
    "userId": "<who-triggered-it>",
    "companyId": "<workspace>",
    "entityId": "<affected-record>",
    "payload": { /* event-specific */ }
  },
  "timestamp": "<iso-8601>"
}
```

`userId` is the user who caused the write, including a user acting through an API key. For messaging events, which are triggered by inbound provider activity rather than a user action, `userId` is `null`.

For `*.updated` events, `payload` wraps the full record together with a `changes` object. For `*.created` and `*.deleted` events, `payload` is the record itself.

Example, `contact.updated`:

```json
{
  "event": "contact.updated",
  "data": {
    "userId": "u_123",
    "companyId": "c_abc",
    "entityId": "ct_xyz",
    "payload": {
      "contact": {
        "id": "ct_xyz",
        "firstName": "Max",
        "lastName": "Mustermann",
        "notes": { /* Tiptap JSON */ },
        "organizations": [{ "id": "org_1", "name": "Example GmbH" }],
        "users": [],
        "deals": [{ "id": "deal_1" }, { "id": "deal_2" }],
        "customFieldValues": [
          { "columnId": "col_abc", "value": "Won" }
        ]
      },
      "changes": {
        "organizations": {
          "previous": [],
          "current": [{ "id": "org_1", "name": "Example GmbH" }]
        }
      }
    }
  },
  "timestamp": "2026-04-22T10:00:00.000Z"
}
```

The record fields depend on the entity type. Custom columns appear under `customFieldValues` as `columnId` and `value` pairs. Use `get_record_schema` to see the columns configured for a given entity in your workspace.

## The `changes` object

`changes` is present only on `*.updated` events. Each key is a record field whose value moved. `previous` is the value before the write, `current` is the value after.

Scalar and object fields report their complete value before and after, compared by deep equality. Arrays whose items carry an `id`, `columnId` or `key` (related records, custom-field values) report only the items that moved: `previous` holds the items that changed or were removed, `current` holds the items that changed or were added, and unchanged items are omitted. An added item therefore appears only under `current` and a removed one only under `previous`. Arrays without such a key report the whole array on both sides. `createdAt` and `updatedAt` are never reported as changes.

If a write does not change any field, the event is suppressed. No-op `*.updated` events are not delivered.

## Custom headers and body templates

Some receivers will not accept the standard delivery. Two optional settings cover that, and a webhook that sets neither delivers exactly as described above.

**Custom headers** are sent with every delivery, for endpoints that require their own authentication. Set them in the **Custom headers** field one per line as `Name: value` (a line without a colon is ignored, and emptying the field removes all headers), or pass a `headers` object through MCP and the API. Six names are reserved and rejected when you save: `Connection`, `Content-Length`, `Content-Type`, `Host`, `Transfer-Encoding` and `X-Webhook-Signature`. Header names must be valid HTTP tokens, values must be Latin-1 text without line breaks, and a webhook may carry up to 20 headers with names up to 128 characters, values up to 2,048 characters, and 8,192 characters in total. Because headers usually carry a credential, a webhook that has them must use an HTTPS endpoint; plain HTTP is accepted only for `localhost`, `127.0.0.1` and `::1`.

Header values and the signing secret are never returned by the REST API or by MCP, which report `headerNames` and `hasSecret` instead. The **Webhook** dialog does show them: everyone whose role can open the **Webhooks** page, meaning **API & Webhooks** Read access **All** or the **Admin** role, can read both there, whether or not the role may manage webhooks. The secret stays masked until revealed with the eye icon. An API or MCP update that omits `headers` keeps the stored values, and one that passes `null` clears them.

**A body template** replaces the standard envelope for endpoints that expect a fixed shape. Write a JSON document and reference envelope values with placeholders:

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

Available placeholders are `{{event}}`, `{{timestamp}}` and any path under `{{data}}`, including `{{data.entityId}}`, `{{data.companyId}}`, `{{data.userId}}` and `{{data.payload}}`. A placeholder must sit inside a JSON string; `{"count": {{data.payload.count}}}` is rejected. A placeholder that resolves to an object is inserted as a JSON string, and a missing path becomes an empty string. Substituted values are escaped, so record content cannot alter the structure of the document.

The template may be up to 8,192 characters and must produce a JSON object. It is checked when you save the webhook. A delivery whose template fails to render, or whose rendered body is longer than 131,072 characters, is recorded as failed rather than sent and is not retried. The signature is always computed over the body actually sent, so verify it against the rendered body rather than the envelope.

**Removing a secret or a template.** The dialog cannot remove a saved **Secret** or **Body template**: saving either field empty is rejected. To remove one, update the webhook through `manage_webhooks` or the REST API with `secret: null` or `bodyTemplate: null`, or delete the webhook and create it again.

**One URL, one configuration.** The secret, the headers and the body template are matched to a delivery by workspace and URL, not by webhook. When several webhooks in the same workspace point at the same URL, disabled ones included, every delivery to that URL is signed with the secret of the oldest of them, or sent unsigned if that one has no secret. If any of them carries headers or a body template, every delivery to that URL fails and is not retried, including deliveries from the webhook that has no overrides. Give each subscription its own URL, by adding a path or a query string, before adding a secret, headers or a template.

Deliveries are recorded with the event payload rather than the rendered body, so **Event Details** shows the event that fired and not the exact bytes sent.

## How do I send to Slack, Discord or n8n?

Each recipe is the URL, the custom headers, and the body template to paste into the **Webhook** dialog under **My Company** → **Webhooks** → **Add**. Set a signing secret in every case; a receiver that cannot verify it simply ignores the header.

### Claude Code routines

Start a Claude Code routine when a record changes. Create the routine at [claude.ai/code/routines](https://claude.ai/code/routines) first.

<Steps>
<Step title="Add an API trigger">
Open the routine, click **Add another trigger**, choose **API**, then **Generate token**. Copy the URL and the token; the token is shown once and cannot be retrieved later.
</Step>
<Step title="Create the webhook">
Paste the URL, select your events, and add the headers and template below.
</Step>
<Step title="Reference the payload in the routine prompt">
The text arrives wrapped in a `routine-fire-payload` block that the routine treats as untrusted data. The routine's own prompt has to refer to it, for example "act on the event described in the routine-fire-payload block", or the text is ignored.
</Step>
</Steps>

The URL is `https://api.anthropic.com/v1/claude_code/routines/<routine-id>/fire`, and the routine id is prefixed `trig_`.

```
Authorization: Bearer <routine-token>
anthropic-beta: experimental-cc-routine-2026-04-01
anthropic-version: 2023-06-01
```

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

The endpoint reads only `text` and ignores every other field, so the template is required; without it the routine starts with no context. Every delivery starts a separate run against your routine allowance, and a retry starts another, so subscribe to the narrowest set of events that does the job.

### Slack

Post to a channel with an incoming webhook. The URL carries the authentication, so no custom headers are needed.

Use the incoming webhook URL from **Slack → Apps → Incoming Webhooks**.

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

### Discord

The same shape under a different key.

Use the webhook URL from **Channel → Edit Channel → Integrations → Webhooks**.

```json
{ "content": "{{event}} for {{data.entityId}}" }
```

### n8n

An n8n Webhook node accepts the standard envelope, so leave both settings empty unless the node uses header authentication. If it does, add the header the node expects and leave the template empty:

```
X-N8N-Header-Auth: <value>
```

See [n8n](/docs/n8n) for the full pattern.

### Anything else

A receiver that needs neither its own authentication nor a fixed body needs neither setting. Leave both empty and verify the signature as described below.

## How do I verify the signature?

If the webhook has a **Secret**, every request includes:

```
X-Webhook-Signature: <hex>
```

`<hex>` is `HMAC-SHA256(secret, rawRequestBody)`, lowercase hex, no prefix. Recompute it on your side and compare in constant time. When several webhooks share a URL, the secret of the oldest one applies, as described under "One URL, one configuration" above.

Node.js example:

```ts
import crypto from "crypto";

function verify(rawBody: string, received: string, secret: string) {
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
}
```

## How do retries and failed deliveries work?

Every delivery is recorded. In the sidebar, expand **My Company** and open **Recent Deliveries**, or call `manage_webhooks` with `action: "list_deliveries"`. The page lists the newest deliveries first with their **URL**, **Event**, **Element** (the affected record), **Status**, **Status Code** and **Created at**. The search box matches the event and the URL, and the filters cover the event, the URL and the creation date. Delivery records are not deleted automatically; they are kept as long as the workspace exists.

Click a row to open **Event Details**. It shows the status (**Pending** until the first attempt finishes, then **Delivered** or **Failed**), **URL**, **Event**, **Element**, **Created At**, **Status Code**, **Response Message** and the **Event payload**. The payload is shown in full, including records that the reader's role cannot open elsewhere.

A delivery is marked failed if the HTTP status is outside the 2xx range, the request times out, or no response arrives. The request timeout is 5 seconds. A delivery also fails before any request is sent, with status code 422, when its URL is shared with another webhook and one of them carries headers or a template, when headers would go to an address that does not allow them, or when the body template cannot be rendered.

Customermates automatically retries failed deliveries: up to 5 retries for timeouts, network errors, 5xx responses, and 408, 425, and 429. Permanent 4xx responses (for example 400, 401, 403, 404) and the 422 failures above are not retried, because a repeat would fail the same way. Retries happen inside the delivery run, so they do not create extra delivery records; each record shows the latest outcome, so it can show **Failed** while retries are still pending and change to **Delivered** when one succeeds.

You can also resend a delivery yourself. In **Event Details**, the circular-arrows icon (**Resend**) appears at the top once the delivery is **Delivered** or **Failed**, for roles with **Manage** **Yes** on **API & Webhooks**. Through MCP, use `manage_webhooks` with `action: "resend_delivery"` plus the delivery id. A resend posts the stored event to the same URL with that URL's current secret, headers and template, and creates a new delivery record; the original is unchanged. It is sent even if the webhook has since been disabled or deleted; after a deletion, if no other webhook uses that URL, it goes out unsigned, without custom headers, in the standard envelope.

## Are deliveries ordered?

Deliveries are not strictly ordered across events. Two `contact.updated` events milliseconds apart can arrive out of order. Use the `timestamp` in the payload to resolve order, or treat deliveries as idempotent messages keyed by `entityId`.

## Notes are JSON, not markdown

The `notes` field in payloads is Tiptap JSON, the same structure the editor stores. To render it as markdown on your side, run it through a Tiptap-compatible serializer. In MCP, `get_records` with `include: "withNotes"` returns notes already serialized to markdown.

## What do delete payloads contain?

Delete events carry the full record as it was before deletion, under `payload`, not just the id. The affected record id is also available as `data.entityId`.

## How do I debug a delivery?

- Use [webhook.site](https://webhook.site) as a throwaway receiver during integration testing.
- The delivery log (`manage_webhooks`, `action: "list_deliveries"`) supports `searchTerm` on url and event name.
- For each delivery, Customermates records only the HTTP status code and the status text your receiver returned (for example `404` and `Not Found`), shown as **Status Code** and **Response Message** in **Event Details**. The response body is not stored, so log it on the receiving side. When no response arrives, **Status Code** shows a dash (the list column stays empty) and **Response Message** names the cause, such as the timeout.

## Which events exist?

[[derived.webhooks.events.total]] events are available to subscribe to: [[derived.webhooks.events.records]] record events across the five entity types, and [[derived.webhooks.events.messaging]] messaging events. All use the envelope above. Routines can be triggered by the same events except the two message-deleted events; see [Routines](/docs/app-routines#how-do-event-triggers-work).

### Record events

| Event | When it fires | `payload` |
|---|---|---|
| `contact.created` | A contact is created via UI, API, MCP, or import | full contact |
| `contact.updated` | Any contact field changes | `contact`, `changes` |
| `contact.deleted` | A contact is deleted | full contact |
| `organization.created` | An organization is created | full organization |
| `organization.updated` | Any organization field changes | `organization`, `changes` |
| `organization.deleted` | An organization is deleted | full organization |
| `deal.created` | A deal is created | full deal |
| `deal.updated` | Any deal field changes | `deal`, `changes` |
| `deal.deleted` | A deal is deleted | full deal |
| `service.created` | A service is created | full service |
| `service.updated` | Any service field changes | `service`, `changes` |
| `service.deleted` | A service is deleted | full service |
| `task.created` | A task is created | full task |
| `task.updated` | Any task field changes | `task`, `changes` |
| `task.deleted` | A task is deleted | full task |

### Messaging events

Messaging events fire on inbound provider activity on connected accounts. The **Events** list offers them in every workspace, but they fire only where connected accounts exist, which requires Cloud and a plan that includes messaging. `userId` is `null`. Payloads reference provider records by id (`connectedAccountId`, `provider`, `providerMessageId`, `threadId`, and similar) rather than embedding CRM records.

| Event | When it fires |
|---|---|
| `messaging.message.received` | A chat message or email is ingested |
| `messaging.message.updated` | An ingested message is updated |
| `messaging.message.deleted` | An ingested message is deleted |
| `messaging.message.reaction` | A reaction is added to a message |
| `messaging.email.received` | An email is ingested |
| `messaging.email.deleted` | An ingested email is deleted |
| `messaging.chat.updated` | A chat thread is updated |
| `messaging.chat.deleted` | A chat thread is deleted |
| `messaging.calendar.changed` | A connected calendar changes |
| `messaging.calendar_event.changed` | A calendar event changes |
| `messaging.relation.created` | A new provider relation is created |
