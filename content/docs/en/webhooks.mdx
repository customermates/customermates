Customermates sends a JSON POST to your endpoint whenever subscribed data changes. You choose the events and provide the URL. Failed deliveries can be re-sent from the UI or through MCP. When the webhook has a secret, deliveries are signed with HMAC-SHA256 over the raw request body. Every event and its payload shape is listed in the catalog at the end of this page.

## What are webhooks for?

Webhooks let other systems react to CRM changes without polling.

- Push new contacts into an email sequencer.
- Open a ticket in a support tool when a deal changes state.
- Trigger a finance workflow when a deal is marked as closed.
- Sync records into a data warehouse in near real time.

## How do I add or create a webhook, and where do I enter its URL? [#how-do-i-create-a-webhook]

**UI:** To create a webhook, expand **My Company** in the sidebar, open **Webhooks** and click **Add** (on narrow screens the button shows only a plus icon). Fill in the **Webhook** dialog and click **Save**.

| Field | What it does |
| --- | --- |
| **URL** | Required. The endpoint that receives a `POST` for every subscribed event. A URL entered without a scheme is saved with `https://` in front. |
| **Description** | Optional, up to 500 characters. Shown in the list. |
| **Events** | Required. One or more events from the catalog at the end of this page. |
| **Secret** | Optional, 1 to 256 characters. When set, deliveries carry a signature made with it (see [How do I verify the signature?](#how-do-i-verify-the-signature)). |
| **Custom headers** | Optional. One `Name: value` per line (see [Custom headers and body templates](#custom-headers-and-body-templates)). |
| **Body template** | Optional JSON document that replaces the standard envelope. |
| **Enabled** | On by default. A disabled webhook receives no deliveries and keeps its configuration, so you can pause it without deleting it. |

To change a webhook, click its row, edit the dialog and click **Save**. To remove it, click the trash icon (**Delete**) at the top of the dialog and confirm; its past deliveries stay under **Recent Deliveries**. The list shows each webhook's **URL**, **Description**, **Events**, **Status** (**Enabled** or **Disabled**), **Created at** and **Updated at**. The search box matches the URL, and the filters cover the creation and update dates.

**MCP:** `manage_webhooks` with `action: "create"`, plus `url`, `events[]`, and optional `description`, `secret`, `headers`, `bodyTemplate`, `enabled`. The hosted assistant uses the same tool, and it can also open **Webhooks** or **Recent Deliveries** for you and point at the **Add** button.

Use an HTTPS endpoint. A plain `http://` URL is accepted for any host as long as the webhook has no custom headers. A webhook with custom headers must use `https://`, or `http://` on `localhost`, `127.0.0.1` or `::1`, because headers usually carry a credential. This rule is checked when you save and again before every delivery.

**Link:** `/settings/webhooks`. **Mate:** `navigate` and `highlight_element` with `nav-settings-webhooks`, then `highlight_element` with `settings-webhooks-add` for **Add** (present only with **Create** on **API & Webhooks**). In the **Webhook** dialog, opened with **Add** (prerequisite `settings-webhooks-add`) or a row, `webhook-modal-url`, `webhook-modal-description`, `webhook-modal-events`, `webhook-modal-secret`, `webhook-modal-headers`, `webhook-modal-body-template` and `webhook-modal-enabled` highlight the fields in the table above, read-only without **Edit** (or **Create** for a new webhook); `webhook-modal-save` and `webhook-modal-cancel` highlight **Save** and **Cancel** for roles with **Create** on a new webhook or **Edit** on a saved one, and `webhook-modal-delete` highlights **Delete** for roles with **Delete**. The list controls are on [My Company](/docs/app-company#webhooks-tab).

## Which records trigger a webhook, and whose access does a delivery use? [#record-event-sources]

For record events, choose the source type under **Records from**, then optionally select watched fields, search text, and field or relationship filters. Delivery uses the record access of the selected owner; the creator is the default. Only an administrator can select another owner. Existing migrated subscriptions can retain several sources.

**MCP:** record subscriptions in `manage_webhooks` also require `expectedSchemaRevision` from `get_record_model`. Set `recordTrigger` to a query with stable type and field IDs and optional `changedFieldIds`; null selects all accessible types. `recordOwnerUserId` optionally selects the delivery owner. On update, omit these settings to preserve them; changing a trigger or owner requires the current schema revision.

```json
{
  "url": "https://hooks.example.com/customermates",
  "events": ["record.created", "record.updated"],
  "expectedSchemaRevision": 3,
  "recordTrigger": {
    "query": { "typeId": "<project-type-id>" },
    "changedFieldIds": []
  },
  "secret": "use-a-random-string-from-a-password-manager",
  "enabled": true
}
```

**Link:** `/settings/webhooks`. **Mate:** reads the type and field IDs with `get_record_model`, then uses `manage_webhooks`.

## Who can see and change webhooks?

Access is set by the **API & Webhooks** row of the role editor under **My Company** → **Roles**. Saved **Secret** and **Custom headers** values are visible in the dialog only to the **Admin** role or roles with **Edit** on **API & Webhooks**. **Read access** **All** alone shows `********`.

| Role setting on **API & Webhooks** | What members with that role can do |
| --- | --- |
| **Read access** **None** (the default for a new role) | **Webhooks** and **Recent Deliveries** are hidden in the sidebar. Opening their address directly leads to the Dashboard. |
| **Read access** **All**, no checkbox ticked | Open both pages, open every webhook's dialog read-only, and open **Event Details** for every delivery. In the dialog, a saved **Secret** and every **Custom headers** value appear as `********`; the header names stay visible. |
| **Read access** **All** plus **Create** | Add webhooks and resend deliveries. |
| **Read access** **All** plus **Edit** | Edit webhooks and see saved **Secret** and **Custom headers** values in the webhook dialog. |
| **Read access** **All** plus **Delete** | Delete webhooks. |

The same row also controls **My Profile** → **API & Connectors**, so a role that may create or delete its own API keys may also create or delete every webhook in the workspace.

The **Admin** role can do everything. Webhooks have no plan restriction: they work on every Cloud plan and in a self-hosted installation. The same permissions apply to `manage_webhooks` through MCP and in the hosted assistant. In the hosted assistant, deleting a webhook or resending a delivery asks for your approval first.

**Link:** `/settings/webhooks` and `/settings/webhooks/deliveries`, and for the role's **API & Webhooks** row `/settings/roles`. **Mate:** `navigate` and `highlight_element` with `nav-settings-webhooks`, `nav-settings-webhooks` or `nav-settings-roles`; in an open **Webhook** dialog `webhook-modal-secret` and `webhook-modal-headers` highlight **Secret** and **Custom headers**. The role rows are not highlight targets, so Mate names them.

## What does the payload look like?

Every delivery is a `POST` with `Content-Type: application/json` and the same envelope:

```json
{
  "event": "<event-name>",
  "id": "<event-id>",
  "timestamp": "<iso-8601>",
  "companyId": "<workspace>",
  "actorId": "<who-triggered-it>",
  "data": {
    /* event-specific */
  }
}
```

`id` identifies the event: a resend and every retry carry the same `id`, so use it to deduplicate. `actorId` is the user who caused the write, including a user acting through an API key or a routine run by its owner. For messaging events, which are triggered by inbound provider activity rather than a user action, `actorId` is `null`.

For record events, `data` holds the record change: `data.record` with the record reference (`typeId` and `recordId`, unambiguous even when a type is renamed) and the changes, `data.cause` with what caused the write, and `data.causeId`, shared by every event of the same write. Configure record sources on the webhook to select the types and fields that should trigger delivery.

Example, `record.updated` for a contact, with unrelated fields omitted:

```json
{
  "event": "record.updated",
  "id": "<event-id>",
  "timestamp": "2026-04-22T10:00:00.000Z",
  "companyId": "<workspace-id>",
  "actorId": "<actor-user-id>",
  "data": {
    "causeId": "<cause-id>",
    "cause": { "kind": "mutation" },
    "record": {
      "ref": { "typeId": "<contact-type-id>", "recordId": "<record-id>" },
      "schemaRevision": 3,
      "beforeVersion": 1,
      "afterVersion": 2,
      "fields": [
        {
          "fieldId": "<first-name-field-id>",
          "before": { "value": { "state": "value", "value": { "kind": "text", "value": "Max" } } },
          "after": { "value": { "state": "value", "value": { "kind": "text", "value": "Maximilian" } } }
        }
      ]
    }
  }
}
```

The actual record change also carries assignments, identities, link changes and related records. Field entries include display metadata and may show `missing`, `restricted`, or `error` instead of a value. Use `POST /api/v1/model/discover` or the `get_record_model` MCP tool to resolve stable type and field IDs.

## The `changes` object: changed fields [#the-changes-object]

`data.record.fields` lists changed fields with `before` and `after` values; `data.record.links`, `data.record.assignments`, and `data.record.identities` describe other changed connections. `data.record.beforeVersion` and `data.record.afterVersion` identify the record versions involved. A missing or restricted field is not the same as zero.

No-op updates do not produce `record.updated` events. The payload is redacted according to the webhook owner's current record and calculated-field access at delivery time.

## Custom headers and body templates

Some receivers will not accept the standard delivery. Two optional settings cover that, and a webhook that sets neither delivers the standard envelope from [What does the payload look like?](#what-does-the-payload-look-like).

**Custom headers** are sent with every delivery, for endpoints that require their own authentication. Set them in the **Custom headers** field one per line as `Name: value` (a line without a colon is ignored, and emptying the field removes all headers), or pass a `headers` object through MCP and the API. Six names are reserved and rejected when you save: `Connection`, `Content-Length`, `Content-Type`, `Host`, `Transfer-Encoding` and `X-Webhook-Signature`. Header names must be valid HTTP tokens, values must be Latin-1 text without line breaks, and a webhook may carry up to 20 headers with names up to 128 characters, values up to 2,048 characters, and 8,192 characters in total. Because headers usually carry a credential, a webhook that has them must use an HTTPS endpoint; plain HTTP is accepted only for `localhost`, `127.0.0.1` and `::1`.

Header values and the signing secret are never returned by the REST API or by MCP, which report `headerNames` and `hasSecret` instead. The **Webhook** dialog shows the values only to roles with **Edit** on **API & Webhooks** and to the **Admin** role; the secret stays masked there until revealed with the eye icon. A role with **Read access** **All** but without **Edit** sees `********` in place of the secret and of each header value, with the header names kept, so it can tell whether a secret and which headers are set. An API or MCP update that omits `headers` keeps the stored values, and one that passes `null` clears them.

**A body template** replaces the standard envelope for endpoints that expect a fixed shape. Write a JSON document and reference envelope values with placeholders:

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

Available placeholders are `{{event}}`, `{{id}}`, `{{timestamp}}`, `{{companyId}}`, `{{actorId}}` and any path under `{{data}}`, such as `{{data.record.ref.recordId}}` for a record event or `{{data.entityId}}` for a messaging event. A placeholder must sit inside a JSON string; `{"count": {{data.count}}}` is rejected. A placeholder that resolves to an object is inserted as a JSON string, and a missing path becomes an empty string. Substituted values are escaped, so record content cannot alter the structure of the document.

The template may be up to 8,192 characters and must produce a JSON object. It is checked when you save the webhook. A delivery whose template fails to render, or whose rendered body is longer than 131,072 characters, is recorded as failed rather than sent and is not retried. The signature is always computed over the body actually sent, so verify it against the rendered body rather than the envelope.

**Removing a secret or a template.** The dialog cannot remove a saved **Secret** or **Body template**: saving either field empty is rejected. To remove one, update the webhook through `manage_webhooks` or the REST API with `secret: null` or `bodyTemplate: null`, or delete the webhook and create it again.

Deliveries are recorded with the event payload rather than the rendered body, so **Event Details** shows the event that fired and not the exact bytes sent.

**Link:** `/settings/webhooks`. **Mate:** `navigate` and `highlight_element` with `nav-settings-webhooks`; in an open **Webhook** dialog `webhook-modal-headers` and `webhook-modal-body-template` highlight **Custom headers** and **Body template**, read-only without **Edit** on **API & Webhooks**.

## How do I send to Slack, Discord or n8n?

Use these recipes to post a message to a team chat channel, or start a workflow, whenever something happens in the CRM, for example when a new deal shows up. Each recipe is the URL, the custom headers, and the body template to paste into the **Webhook** dialog under **Settings** → **Webhooks** → **Add**. Set a signing secret in every case; a receiver that cannot verify it simply ignores the header.

### Claude Code routines

Start a Claude Code routine when a record changes. Create the routine at [claude.ai/code/routines](https://claude.ai/code/routines) first.

<Steps>
  <Step title="Add an API trigger">
    Open the routine, click **Add another trigger**, choose **API**, then **Generate token**. Copy the URL and the
    token; the token is shown once and cannot be retrieved later.
  </Step>
  <Step title="Create the webhook">Paste the URL, select your events, and add the headers and template below.</Step>
  <Step title="Reference the payload in the routine prompt">
    The text arrives wrapped in a `routine-fire-payload` block that the routine treats as untrusted data. The routine's
    own prompt has to refer to it, for example "act on the event described in the routine-fire-payload block", or the
    text is ignored.
  </Step>
</Steps>

The URL is `https://api.anthropic.com/v1/claude_code/routines/<routine-id>/fire`, and the routine id is prefixed `trig_`.

```
Authorization: Bearer <routine-token>
anthropic-beta: experimental-cc-routine-2026-04-01
anthropic-version: 2023-06-01
```

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

The endpoint reads only `text` and ignores every other field, so the template is required; without it the routine starts with no context. Every delivery starts a separate run against your routine allowance, and a retry starts another, so subscribe to the narrowest set of events that does the job.

### Slack

Post to a channel with an incoming webhook. The URL carries the authentication, so no custom headers are needed.

Use the incoming webhook URL from **Slack → Apps → Incoming Webhooks**.

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

### Discord

The same shape under a different key.

Use the webhook URL from **Channel → Edit Channel → Integrations → Webhooks**.

```json
{ "content": "{{event}} for {{data.record.ref.recordId}}" }
```

### n8n

An n8n Webhook node accepts the standard envelope, so leave both settings empty unless the node uses header authentication. If it does, add the header the node expects and leave the template empty:

```
X-N8N-Header-Auth: <value>
```

See [n8n](/docs/n8n) for the full pattern.

### Anything else

A receiver that needs neither its own authentication nor a fixed body needs neither setting. Leave both empty and verify the signature as described under [How do I verify the signature?](#how-do-i-verify-the-signature).

## How do I verify the signature?

If the webhook has a **Secret**, every request includes:

```
X-Webhook-Signature: <hex>
```

`<hex>` is `HMAC-SHA256(secret, rawRequestBody)`, lowercase hex, no prefix. Recompute it on your side and compare in constant time.

Node.js example:

```ts
import crypto from "crypto";

function verify(rawBody: string, received: string, secret: string) {
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
}
```

## How do retries and failed deliveries work?

Customermates retries a failed delivery automatically, up to 10 attempts in total with a growing pause of at most one hour between them, for timeouts, network errors, 5xx responses and 408, 425 and 429; other 4xx responses, such as 400, 401, 403, 404 and 422, are not retried, because a repeat would fail the same way. Every delivery is recorded on **My Company › Recent Deliveries** (`/settings/webhooks/deliveries`) and through `manage_webhooks` with `action: "list_deliveries"`. The page lists the newest deliveries first with their **URL**, **Event**, **Element** (the affected record), **Status**, **Status Code** and **Created at**. The search box matches the event and the URL, and the filters cover the event, the URL and the creation date. Delivery records are not deleted automatically; they are kept as long as the workspace exists.

Click a row to open **Event Details**. It shows the status (**Pending** until the first attempt finishes, then **Delivered** or **Failed**), **URL**, **Event**, **Element**, **Created At**, **Status Code**, **Response Message** and the **Event payload**. Every delivery is read from its event: a messaging event's payload is shown as it was sent, and a record event's payload is read again with your current access: values you cannot read appear as restricted, and the payload stays empty when you cannot read the record.

A delivery is marked failed if the HTTP status is outside the 2xx range, the request times out, or no response arrives. The request timeout is 5 seconds. A delivery also fails before any request is sent, with status code 422, when headers would go to an address that does not allow them or when the body template cannot be rendered.

Retries happen inside the delivery run, so they do not create extra delivery records; each record shows the latest outcome, so it can show **Failed** while retries are still pending and change to **Delivered** when one succeeds.

You can also resend a delivery yourself. In **Event Details**, the circular-arrows icon (**Resend**) appears at the top once the delivery is **Delivered** or **Failed**, for roles with **Create** on **API & Webhooks**. Through MCP, use `manage_webhooks` with `action: "resend_delivery"` plus the delivery id. A resend creates a new delivery record for the same webhook and sends it with the webhook's current URL, secret, headers and template; the original is unchanged. A messaging event is resent from its stored event. A record event is read again with the webhook owner's current access; only that owner or an administrator can resend it, and the resend is refused when the webhook's record sources changed since the original delivery. The webhook must still exist, be enabled and subscribe to the event; a delivery of a retired type-specific event cannot be resent.

**Link:** `/settings/webhooks/deliveries`. **Mate:** `navigate` and `highlight_element` with `nav-settings-webhooks` (highlightable only while **My Company** is expanded, which it is by default on its own pages unless the member collapsed it); `settings-webhooks-deliveries-search` and `settings-webhooks-deliveries-filter` highlight the search box and the filters. `settings-webhooks-deliveries-display-options` highlights the display options, and `settings-webhooks-deliveries-layout-table` and `settings-webhooks-deliveries-layout-board` the layout controls inside them (open display options first). Once the user has opened a delivery row, `webhook-delivery-modal-resend` highlights the **Resend** icon in **Event Details** (roles with **Create**, only on delivered and failed deliveries); the rows and the rest of the dialog are not highlight targets, so Mate names them.

## Are deliveries ordered, and do they arrive in the right order? [#are-deliveries-ordered]

Deliveries are not strictly ordered across events. Two `record.updated` events milliseconds apart can arrive out of order. Use the `timestamp` and record version to resolve order, or treat deliveries as idempotent messages keyed by `typeId`, `recordId`, and event ID.

## Why are notes Tiptap JSON in payloads? [#notes-are-json-not-markdown]

The `notes` field in payloads is Tiptap JSON, the same structure the editor stores. To render it as markdown on your side, run it through a Tiptap-compatible serializer. In MCP, `read_crm_record` returns the configured rich-text value with `documentJson`; convert that document with a compatible serializer when you need markdown.

## What do delete payloads contain?

For `record.deleted`, `data.record` carries the qualified `ref`, the authorized before-values and the removed relationships. Its `afterVersion` is null. Source filters match immediately before removal, while the owner’s current access is checked again before delivery.

## How do I debug a delivery?

- Use [webhook.site](https://webhook.site) as a throwaway receiver during integration testing.
- The delivery log (`manage_webhooks`, `action: "list_deliveries"`) supports `searchTerm` on url and event name.
- For each delivery, Customermates records only the HTTP status code and the status text your receiver returned (for example `404` and `Not Found`), shown as **Status Code** and **Response Message** in **Event Details**. The response body is not stored, so log it on the receiving side. When no response arrives, **Status Code** shows a dash (the list column stays empty) and **Response Message** names the cause, such as the timeout.

**Link:** `/settings/webhooks/deliveries`. **Mate:** `navigate` and `highlight_element` with `nav-settings-webhooks`; the rows and the fields in **Event Details** are not highlight targets, so Mate names them.

## Which events exist?

A webhook can subscribe to [[derived.webhooks.events.total]] events: [[derived.webhooks.events.records]] record events and [[derived.webhooks.events.messaging]] messaging events. Fifteen retired type-specific identifiers can still appear on older webhooks and in the delivery history, but they can no longer be selected and nothing emits them. For a new CRM webhook, select `record.created`, `record.updated`, or `record.deleted` and configure its record sources to choose types, fields, and filters. This also covers customer-created types. All use the envelope from [What does the payload look like?](#what-does-the-payload-look-like). Routines can be triggered by the same events except **Email Deleted** (`messaging.email.deleted`) and **Chat Deleted** (`messaging.chat.deleted`); **Message Deleted** (`messaging.message.deleted`) does trigger routines; see [Routines](/docs/app-routines#how-do-event-triggers-work).

### Messaging events

Messaging events fire on inbound provider activity on connected accounts. The **Events** list offers them in every workspace, but they fire only where connected accounts exist, which requires Cloud and a plan that includes messaging. `actorId` is `null`. `data` references provider records by id (`entityId` for the affected message, thread, calendar, calendar event or relation, plus `connectedAccountId`, `provider`, `providerMessageId`, `threadId`, and similar) rather than embedding CRM records. A messaging event is kept only while a webhook or an event routine subscribes to it.

| Event | When it fires |
| --- | --- |
| `messaging.message.received` | A chat message or email is ingested |
| `messaging.message.updated` | An ingested message is updated |
| `messaging.message.deleted` | An ingested message is deleted |
| `messaging.message.reaction` | A reaction is added to a message |
| `messaging.email.received` | An email is ingested |
| `messaging.email.deleted` | An ingested email is deleted |
| `messaging.chat.updated` | A chat thread is updated |
| `messaging.chat.deleted` | A chat thread is deleted |
| `messaging.calendar.changed` | A connected calendar changes |
| `messaging.calendar_event.changed` | A calendar event changes |
| `messaging.relation.created` | A new provider relation is created |
