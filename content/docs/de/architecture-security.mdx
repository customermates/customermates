Customermates erzwingt ein Single-Tenant-pro-Company-Datenmodell auf jeder Ebene. Jeder Datensatz ist auf eine Company begrenzt, API-Keys tragen die Identität des Owner-Users, und Agents sehen nur das, was dieser User sehen darf.

## Stack

- **Next.js 16** (App Router, Turbopack): Web-App und API.
- **PostgreSQL**: primärer Datastore. JSONB für Custom-Column-Werte und Webhook-Payloads.
- **Prisma**: ORM und Migrationen.
- **better-auth**: Sessions, Social-Login, API-Keys, MCP-OAuth.
- **mcp-handler**: Model-Context-Protocol-Endpoint.
- **TypeScript** durchgängig, Zod-validiert an jeder Grenze.

## Tenancy

Jeder Datensatz gehört zu einer **Company**. Die Company-ID wird an drei Stellen erzwungen:

1. **App-Layer**: jeder Interactor löst die Company des aktuellen Users auf und filtert danach.
2. **Prisma-Layer**: Queries enthalten `companyId` in jedem `where`.
3. **Decorator-Layer**: `@TenantInteractor` sorgt dafür, dass Interactors, die den Scope vergessen, zur Laufzeit werfen.

Cross-Tenant-Reads sind über die öffentliche Oberfläche nicht möglich. In der gehosteten Cloud kann eine Operator-Konsole des Anbieters für den Support mandantenübergreifend lesen; sie ist auf ein freigeschaltetes Operator-Konto beschränkt, verweigert den Dienst außerhalb des Cloud-Modus und schreibt jeden Read und Write in ein separates internes Log. Ein Self-Hosted-Deployment hat diese Konsole nicht.

## Authentifizierung

Drei Wege:

- **Session-Cookie** (UI): signiert, http-only, `Secure` unter HTTPS.
- **API-Key**: 64-Zeichen-Base62-Token (a-z, A-Z, 0-9), ausgestellt vom better-auth-apiKey-Plugin, at-rest gehasht, an einen User gebunden. Wird im Header `x-api-key` gesendet.
- **OAuth 2.1** (MCP): Remote-MCP-Clients können sich über better-auth autorisieren und statt eines API-Keys ein Bearer-Token senden.

Alle Methoden lösen auf denselben User- und Company-Kontext auf.

## Autorisierung

Pro User und rollenbasiert. Rollen tragen Permissions auf Resources (Contacts, Organizations, Deals, Services, Tasks, Users, Company, API, Audit-Log, Inbox-Messages, Routines) und Actions (Create, Read Own, Read All, Update, Delete). Jeder Interactor ruft `userService.hasPermissionOrThrow(resource, action)`, bevor er handelt.

API-Keys erben die Rechte ihres Owner-Users. Es gibt kein Scoping pro Key.

## Externer KI-Zugriff

MCP-Requests nutzen denselben Authentifizierungs- und Autorisierungspfad. Wenn ein Agent über MCP handelt:

- Er ruft `/api/v1/mcp` mit einem API-Key oder einem OAuth-Bearer-Token.
- Der Server löst User und Company aus dem Credential auf.
- Jeder Tool-Call läuft in einem Tenant-Scope.
- Validierungsfehler liefern strukturierte Meldungen mit Remediation-Hints und leaken keine internen Schema-Details.

Die MCP-Oberfläche fügt Input-Guardrails hinzu, die Tool-Calls absichern:

- `null` auf einem Relation-Array wird abgelehnt, bevor es die Datenbank erreicht.
- Update-Tools für den falschen Record-Typ werden mit einem Verweis auf das richtige Tool abgelehnt.
- Destruktive Tools verlangen eine explizite Liste von Record-IDs. Es gibt keinen Delete-by-Filter-Shortcut.

Den vollständigen Tool-Katalog finden Sie unter [MCP](/docs/mcp#tool-catalog).

## Daten at-rest

- Die Postgres-Verschlüsselung hängt vom Provider ab. In der Managed-Cloud liegen die Daten in einer EU-Region mit Disk-Level-Encryption at-rest.
- Secrets in `.env` werden nie geloggt. Der Logger redaktiert alles, was wie ein Key, Token oder Passwort aussieht.
- Webhook-Secrets liegen in Postgres, weil sie abrufbar sein müssen, um ausgehende Requests zu signieren. Wenn Sie sie woanders halten wollen, self-hosten Sie mit Ihrem eigenen Secret-Manager.

## Daten in-transit

- HTTPS überall in der Managed-Cloud.
- Bei Self-Host stellen Sie das TLS selbst bereit. Das Caddy-Beispiel finden Sie unter [Self-Hosting](/docs/self-hosting).
- Webhook-Deliveries gehen nur an HTTPS-URLs. HTTP wird auf Schema-Ebene abgelehnt.

## Audit-Logging

Das Audit-Log protokolliert Änderungen an CRM-Datensätzen und an der Workspace-Konfiguration darum herum: Kontakte, Organisationen, Deals, Services, Aufgaben, benutzerdefinierte Felder, Rollen, Mitglieder, Unternehmenseinstellungen, Webhooks, Routinen und verbundene Konten. Rechtliche Zustimmungen, rechtliche Hinweise und Datensatz-Exporte werden ebenfalls protokolliert. UI, REST-API und MCP laufen über dieselben Interactors, eine Änderung durch einen Agenten wird also wie eine Änderung durch eine Person protokolliert.

Ein Eintrag speichert das Ereignis, die Element-ID, die zugeordnete Person, den Zeitstempel und die Payload als JSON. Aktualisierungen an Datensätzen, Rollen, Webhooks, benutzerdefinierten Feldern, Routinen und verbundenen Konten enthalten ein feldweises Diff. Erstellungen, Löschungen sowie Aktualisierungen an Mitgliedern und Unternehmenseinstellungen enthalten stattdessen eine Momentaufnahme. Ein fehlgeschlagener Write hinterlässt keinen Eintrag, ebenso wenig eine Aktualisierung mit leerem Diff; das Speichern von Mitgliedern oder Unternehmenseinstellungen enthält eine Momentaufnahme statt eines Diffs und schreibt daher auch dann einen Eintrag, wenn sich nichts geändert hat. Webhook-Secrets und Header-Werte werden vor dem Speichern entfernt. Andere Payloads enthalten Datensatzinhalte, das Log hält also Kopien der Daten, die es beschreibt.

Eine Aktion landet nur im Log, wenn sie ein Domain-Event veröffentlicht und dieses Event nicht auf der Ausschlussliste steht. Nicht protokolliert werden:

- Posteingangs-Inhalte. Eingehende E-Mails, Chat-Nachrichten, Kalenderänderungen und soziale Verknüpfungen sind bewusst ausgenommen.
- Authentifizierung. Anmeldung, Abmeldung, Passwort-Reset und die Verknüpfung sozialer Konten.
- Erstellung und Widerruf von API-Keys. Writes mit einem Key werden der Besitzerin oder dem Besitzer zugeordnet, der Lebenszyklus des Keys selbst wird nicht protokolliert.
- Abo- und Tarifänderungen, gespeicherte Ansichten, Dashboard-Widgets und Agenten-Konversationen.
- Operator-Aktionen in der gehosteten Cloud, die in einem separaten internen Log liegen.

Einträge aus automatisierten Abläufen, etwa das Entfernen eines verbundenen Kontos bei Ablauf der Testphase, nennen die betroffene Person und nicht eine handelnde Person.

In der UI lässt sich nach Ereignis und Datum filtern, nach Element-ID suchen und nach Zeit sortieren. Der Screen bietet keinen Export; dieselben Einträge sind über die Aktivitäts-Timeline, ihren REST-Endpunkt und das Tool `get_activities` in [MCP](/docs/mcp) lesbar, mit derselben Berechtigung. Das Produkt bearbeitet oder löscht keine Einträge, sie liegen aber in derselben Datenbank wie Ihre Daten und werden mit dem zugehörigen Unternehmen oder Benutzer entfernt. Behandeln Sie dies als operatives Protokoll, nicht als manipulationssicheres Compliance-Archiv.

Audit-Logging ist kein Tarif-Feature. Jeder Cloud-Plan enthält es, ebenso die selbstgehostete Community-Edition: `features/audit-log/` ist AGPL-Code außerhalb von `ee/`. Wer es lesen darf, wird pro Rolle über die Berechtigung `auditLog` festgelegt.

## Vulnerabilities melden

Bitte melden Sie verantwortungsvoll an `security@customermates.com`. Der PGP-Key liegt im Repository. Wir bestätigen den Eingang innerhalb von 24 Stunden.
