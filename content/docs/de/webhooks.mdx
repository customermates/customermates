Customermates sendet einen JSON-POST an Ihren Endpunkt, sobald sich abonnierte Daten ändern. Sie wählen die Events und geben die URL an. Fehlgeschlagene Zustellungen können Sie aus der UI oder per MCP erneut senden. Hat der Webhook ein Secret, werden Zustellungen per HMAC-SHA256 über den rohen Request-Body signiert. Jedes Event und seine Payload-Struktur stehen im Katalog am Ende dieser Seite.

## Wofür sind Webhooks da? [#what-are-webhooks-for]

Webhooks lassen andere Systeme auf CRM-Änderungen reagieren, ohne zu pollen.

- Neue Contacts in einen E-Mail-Sequencer übergeben.
- Ein Ticket im Support-Tool öffnen, wenn ein Deal seinen Zustand ändert.
- Einen Finance-Workflow auslösen, wenn ein Deal als abgeschlossen markiert wird.
- Records nahezu in Echtzeit in ein Data Warehouse synchronisieren.

## Webhook anlegen: Wie lege ich einen Webhook an oder füge einen hinzu, und wo trage ich seine URL ein? [#how-do-i-create-a-webhook]

**UI:** Um einen Webhook anzulegen, klappen Sie in der Seitenleiste **Mein Unternehmen** auf, öffnen Sie **Webhooks** und fügen Sie mit **Hinzufügen** einen Webhook hinzu (auf schmalen Bildschirmen zeigt die Schaltfläche nur ein Plus-Symbol). Füllen Sie den Dialog **Webhook** aus, tragen Sie die URL ein und klicken Sie auf **Speichern**.

| Feld | Wirkung |
| --- | --- |
| **URL** | Pflichtfeld. Der Endpunkt, der für jedes abonnierte Ereignis einen `POST` erhält. Eine URL ohne Schema wird mit vorangestelltem `https://` gespeichert. |
| **Beschreibung** | Optional, bis zu 500 Zeichen. Erscheint in der Liste. |
| **Ereignisse** | Pflichtfeld. Ein oder mehrere Ereignisse aus dem Katalog am Ende dieser Seite. |
| **Secret** | Optional, 1 bis 256 Zeichen. Ist es gesetzt, tragen Zustellungen eine damit erstellte Signatur (siehe [Wie prüfe ich die Signatur?](#how-do-i-verify-the-signature)). |
| **Eigene Header** | Optional. Ein `Name: Wert` pro Zeile (siehe [Eigene Header und Body-Vorlagen](#custom-headers-and-body-templates)). |
| **Body-Vorlage** | Optionales JSON-Dokument, das den Standardumschlag ersetzt. |
| **Aktiviert** | Standardmäßig eingeschaltet. Ein deaktivierter Webhook erhält keine Zustellungen und behält seine Konfiguration, Sie können ihn also pausieren, ohne ihn zu löschen. |

Um einen Webhook zu ändern, klicken Sie auf seine Zeile, bearbeiten den Dialog und klicken auf **Speichern**. Zum Entfernen klicken Sie oben im Dialog auf das Papierkorb-Symbol (**Löschen**) und bestätigen; seine bisherigen Zustellungen bleiben unter **Letzte Zustellungen** erhalten. Die Liste zeigt für jeden Webhook **URL**, **Beschreibung**, **Ereignisse**, **Status** (**Aktiviert** oder **Deaktiviert**), **Erstellt am** und **Aktualisiert am**. Das Suchfeld durchsucht die URL, die Filter decken Erstellungs- und Änderungsdatum ab.

**MCP:** `manage_webhooks` mit `action: "create"`, dazu `url`, `events[]` und optional `description`, `secret`, `headers`, `bodyTemplate`, `enabled`. Der gehostete Assistent nutzt dasselbe Tool und kann außerdem **Webhooks** oder **Letzte Zustellungen** für Sie öffnen und auf die Schaltfläche **Hinzufügen** zeigen.

Verwenden Sie einen HTTPS-Endpunkt. Eine reine `http://`-URL wird für jeden Host akzeptiert, solange der Webhook keine eigenen Header hat. Ein Webhook mit eigenen Headern muss `https://` verwenden oder `http://` auf `localhost`, `127.0.0.1` oder `::1`, da Header in der Regel ein Credential tragen. Diese Regel wird beim Speichern und erneut vor jeder Zustellung geprüft.

**Link:** `/company/webhooks`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhooks`, danach `highlight_element` mit `company-webhooks-add` für **Hinzufügen** (nur vorhanden mit **Verwalten** **Ja** bei **API & Webhooks**). Im Dialog **Webhook**, geöffnet über **Hinzufügen** (Voraussetzung `company-webhooks-add`) oder eine Zeile, heben `webhook-modal-url`, `webhook-modal-description`, `webhook-modal-events`, `webhook-modal-secret`, `webhook-modal-headers`, `webhook-modal-body-template` und `webhook-modal-enabled` die Felder der Tabelle oben hervor, ohne **Verwalten** schreibgeschützt; `webhook-modal-save`, `webhook-modal-reset` und `webhook-modal-delete` heben **Speichern**, **Zurücksetzen** und **Löschen** für Rollen mit **Verwalten** hervor. Die Listen-Controls stehen unter [Mein Unternehmen](/docs/app-company#webhooks-tab).

## Welche Datensätze lösen einen Webhook aus, und mit wessen Zugriff wird zugestellt? [#record-event-sources]

Für Datensatzereignisse wählen Sie den Quelltyp aus und ergänzen bei Bedarf beobachtete Felder, Suchtext sowie Feld- oder Beziehungsfilter. Die Zustellung verwendet den Datensatzzugriff des ausgewählten Eigentümers; standardmäßig ist dies der Ersteller. Nur ein Administrator darf einen anderen Eigentümer auswählen. Migrierte Abonnements können mehrere Quellen behalten.

**MCP:** Datensatzabonnements in `manage_webhooks` benötigen außerdem `expectedSchemaRevision` aus `get_record_model`. `recordTrigger` enthält eine Abfrage mit stabilen Typ- und Feld-IDs und optionalen `changedFieldIds`; null wählt alle zugänglichen Typen. `recordOwnerUserId` legt optional den Eigentümer für die Zustellung fest. Lassen Sie diese Einstellungen bei einem Update weg, um sie zu erhalten; Änderungen an Quelle oder Eigentümer benötigen die aktuelle Schema-Revision.

```json
{
  "url": "https://hooks.example.com/customermates",
  "events": ["record.created", "record.updated"],
  "expectedSchemaRevision": 3,
  "recordTrigger": {
    "query": { "typeId": "<project-type-id>" },
    "changedFieldIds": []
  },
  "secret": "nutze-einen-random-string-aus-einem-password-manager",
  "enabled": true
}
```

**Link:** `/company/webhooks`. **Mate:** liest mit `get_record_model` die Typ- und Feld-IDs und nutzt dann `manage_webhooks`.

## Wer kann Webhooks sehen und ändern? [#who-can-see-and-change-webhooks]

Den Zugriff legt die Zeile **API & Webhooks** im Rolleneditor unter **Mein Unternehmen** → **Rollen** fest. Gespeicherte **Secret**- und **Eigene Header**-Werte sehen im Dialog nur die Rolle **Admin** oder Rollen mit **Verwalten** **Ja** bei **API & Webhooks**. **Lesen** **Alle** allein zeigt `********`.

| Einstellung bei **API & Webhooks** | Was Mitglieder mit dieser Rolle tun können |
| --- | --- |
| **Lesen** **Keine** (Standard für eine neue Rolle) | **Webhooks** und **Letzte Zustellungen** sind in der Seitenleiste ausgeblendet. Wer die Adresse direkt öffnet, landet auf dem Dashboard. |
| **Lesen** **Alle**, **Verwalten** **Nein** | Beide Seiten öffnen, den Dialog jedes Webhooks schreibgeschützt öffnen und **Ereignis-Details** zu jeder Zustellung öffnen. Im Dialog erscheinen ein gespeichertes **Secret** und jeder Wert unter **Eigene Header** als `********`; die Header-Namen bleiben sichtbar. |
| **Lesen** **Alle**, **Verwalten** **Ja** | Beide Seiten öffnen, gespeicherte **Secret**- und **Eigene Header**-Werte im Webhook-Dialog sehen; Webhooks anlegen, bearbeiten und löschen sowie Zustellungen erneut senden. |

Dieselbe Zeile steuert auch **Mein Profil** → **API & Konnektoren**. Eine Rolle, die ihre eigenen API-Keys verwalten darf, darf also auch jeden Webhook im Workspace verwalten.

Die Rolle **Admin** darf alles. Webhooks sind an keinen Tarif gebunden und funktionieren in jedem Cloud-Tarif sowie in einer selbstgehosteten Installation. Dieselben Berechtigungen gelten für `manage_webhooks` über MCP und im gehosteten Assistenten. Im gehosteten Assistenten fragt das Löschen eines Webhooks oder das erneute Senden einer Zustellung vorher nach Ihrer Freigabe.

**Link:** `/company/webhooks` und `/company/webhook-deliveries`, und für die Zeile **API & Webhooks** der Rolle `/company/roles`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhooks`, `nav-company-webhook-deliveries` oder `nav-company-roles`; in einem geöffneten Dialog **Webhook** heben `webhook-modal-secret` und `webhook-modal-headers` **Secret** und **Eigene Header** hervor. Die Zeilen der Rollen sind keine Highlight-Ziele, deshalb nennt Mate sie beim Namen.

## Wie sieht der Payload aus? [#what-does-the-payload-look-like]

Jede Zustellung ist ein `POST` mit `Content-Type: application/json` und demselben Umschlag:

```json
{
  "event": "<event-name>",
  "id": "<event-id>",
  "timestamp": "<iso-8601>",
  "companyId": "<workspace>",
  "actorId": "<verursacher>",
  "data": {
    /* event-spezifisch */
  }
}
```

`id` bezeichnet das Event: Ein erneutes Senden und jeder Wiederholungsversuch tragen dieselbe `id`, nutzen Sie sie also zum Deduplizieren. `actorId` ist der User, der den Write verursacht hat, inklusive User, die über einen API-Key handeln, und Routinen, die für ihren Eigentümer laufen. Bei Messaging-Events, die durch eingehende Provider-Aktivität statt durch eine User-Aktion ausgelöst werden, ist `actorId` gleich `null`.

Bei Datensatz-Events enthält `data` die Datensatzänderung: `data.record` mit der Referenz (`typeId` und `recordId`, auch nach einer Umbenennung eindeutig) und den Änderungen, `data.cause` mit der Ursache des Writes und `data.causeId`, die alle Events desselben Writes teilen. Legen Sie am Webhook Datensatzquellen fest, um Typen und Felder für die Zustellung auszuwählen.

Beispiel für `record.updated` bei einem Kontakt, ohne für die Erklärung unnötige Felder:

```json
{
  "event": "record.updated",
  "id": "<event-id>",
  "timestamp": "2026-04-22T10:00:00.000Z",
  "companyId": "<workspace-id>",
  "actorId": "<ausloesender-user-id>",
  "data": {
    "causeId": "<cause-id>",
    "cause": { "kind": "mutation" },
    "record": {
      "ref": { "typeId": "<kontakt-typ-id>", "recordId": "<record-id>" },
      "schemaRevision": 3,
      "beforeVersion": 1,
      "afterVersion": 2,
      "fields": [
        {
          "fieldId": "<vorname-feld-id>",
          "before": { "value": { "state": "value", "value": { "kind": "text", "value": "Max" } } },
          "after": { "value": { "state": "value", "value": { "kind": "text", "value": "Maximilian" } } }
        }
      ]
    }
  }
}
```

Die tatsächliche Datensatzänderung enthält außerdem Zuweisungen, Identitäten, Änderungen an Verknüpfungen und verknüpfte Datensätze. Feldeinträge tragen Anzeigedaten und können statt eines Werts `missing`, `restricted` oder `error` enthalten. Stabile Typ- und Feld-IDs liefert `POST /api/v1/model/discover` oder das MCP-Tool `get_record_model`.

## Das `changes`-Objekt: geänderte Felder [#the-changes-object]

`data.record.fields` listet geänderte Felder mit Werten für `before` und `after` auf. `data.record.links`, `data.record.assignments` und `data.record.identities` beschreiben weitere geänderte Verbindungen. `data.record.beforeVersion` und `data.record.afterVersion` bezeichnen die betroffenen Datensatzversionen. Ein fehlender oder eingeschränkter Wert ist nicht dasselbe wie der Zahlenwert 0.

Änderungen ohne Wirkung erzeugen kein `record.updated`-Event. Der Payload wird bei der Zustellung gemäß den aktuellen Datensatz- und Berechnungsfeldrechten des Webhook-Eigentümers redigiert.

## Eigene Header und Body-Vorlagen [#custom-headers-and-body-templates]

Manche Empfänger akzeptieren die Standardzustellung nicht. Dafür gibt es zwei optionale Einstellungen; ein Webhook, der keine davon setzt, stellt den Standardumschlag aus [Wie sieht der Payload aus?](#what-does-the-payload-look-like) zu.

**Eigene Header** werden bei jeder Zustellung mitgesendet, für Endpunkte mit eigener Authentifizierung. In der Oberfläche tragen Sie sie im Feld **Eigene Header** zeilenweise als `Name: Wert` ein (eine Zeile ohne Doppelpunkt wird ignoriert, und ein geleertes Feld entfernt alle Header), über MCP und API als `headers`-Objekt. Sechs Namen sind reserviert und werden beim Speichern abgelehnt: `Connection`, `Content-Length`, `Content-Type`, `Host`, `Transfer-Encoding` und `X-Webhook-Signature`. Header-Namen müssen gültige HTTP-Tokens sein, Werte müssen Latin-1-Text ohne Zeilenumbrüche sein, und ein Webhook darf bis zu 20 Header tragen, mit Namen bis 128 Zeichen, Werten bis 2.048 Zeichen und insgesamt 8.192 Zeichen. Da Header in der Regel ein Credential tragen, muss ein Webhook mit Headern einen HTTPS-Endpunkt verwenden; reines HTTP wird nur für `localhost`, `127.0.0.1` und `::1` akzeptiert.

Header-Werte und das Signaturgeheimnis werden von der REST-API und von MCP nie zurückgegeben, beide liefern stattdessen `headerNames` und `hasSecret`. Der Dialog **Webhook** zeigt die Werte nur Rollen mit **Verwalten** **Ja** bei **API & Webhooks** und der Rolle **Admin**; dort bleibt das Secret maskiert, bis Sie es über das Augensymbol einblenden. Eine Rolle mit **Lesen** **Alle** und **Verwalten** **Nein** sieht statt des Secrets und jedes Header-Werts `********`, die Header-Namen bleiben erhalten, sodass sie erkennt, ob ein Secret und welche Header gesetzt sind. Eine Aktualisierung über API oder MCP ohne `headers` behält die gespeicherten Werte, eine mit `null` löscht sie.

**Eine Body-Vorlage** ersetzt den Standardumschlag für Endpunkte mit fester Struktur. Schreiben Sie ein JSON-Dokument und verweisen Sie über Platzhalter auf Werte des Umschlags:

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

Verfügbar sind `{{event}}`, `{{id}}`, `{{timestamp}}`, `{{companyId}}`, `{{actorId}}` sowie jeder Pfad unterhalb von `{{data}}`, etwa `{{data.record.ref.recordId}}` bei einem Datensatz-Event oder `{{data.entityId}}` bei einem Messaging-Event. Ein Platzhalter muss innerhalb eines JSON-Strings stehen; `{"count": {{data.count}}}` wird abgelehnt. Ein Platzhalter, der ein Objekt liefert, wird als JSON-String eingesetzt, ein fehlender Pfad wird zu einem leeren String. Eingesetzte Werte werden escaped, sodass Datensatzinhalte die Struktur des Dokuments nicht verändern können.

Die Vorlage darf bis zu 8.192 Zeichen lang sein und muss ein JSON-Objekt ergeben. Sie wird beim Speichern geprüft. Eine Zustellung, deren Vorlage nicht gerendert werden kann oder deren gerenderter Body länger als 131.072 Zeichen ist, wird als fehlgeschlagen erfasst statt gesendet und nicht wiederholt. Die Signatur wird immer über den tatsächlich gesendeten Body berechnet, prüfen Sie sie also gegen den gerenderten Body und nicht gegen den Umschlag.

**Secret oder Vorlage entfernen.** Der Dialog kann ein gespeichertes **Secret** oder eine gespeicherte **Body-Vorlage** nicht entfernen: Das Speichern eines leeren Felds wird abgelehnt. Zum Entfernen aktualisieren Sie den Webhook über `manage_webhooks` oder die REST-API mit `secret: null` oder `bodyTemplate: null`, oder Sie löschen den Webhook und legen ihn neu an.

Zustellungen werden mit dem Ereignis-Payload erfasst, nicht mit dem gerenderten Body. **Ereignis-Details** zeigt also das ausgelöste Ereignis und nicht die exakt gesendeten Bytes.

**Link:** `/company/webhooks`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhooks`; in einem geöffneten Dialog **Webhook** heben `webhook-modal-headers` und `webhook-modal-body-template` **Eigene Header** und **Body-Vorlage** hervor, ohne **Verwalten** **Ja** bei **API & Webhooks** schreibgeschützt.

## Wie sende ich an Slack, Discord oder n8n? [#how-do-i-send-to-slack-discord-or-n8n]

Jedes Rezept nennt die URL, die eigenen Header und die Body-Vorlage zum Einfügen in den Dialog **Webhook** unter **Mein Unternehmen** → **Webhooks** → **Hinzufügen**. Setzen Sie in jedem Fall ein Signaturgeheimnis; ein Empfänger, der es nicht prüfen kann, ignoriert den Header einfach.

### Claude-Code-Routinen [#claude-code-routines]

Startet eine Claude-Code-Routine, wenn sich ein Datensatz ändert. Legen Sie die Routine zuerst unter [claude.ai/code/routines](https://claude.ai/code/routines) an.

<Steps>
  <Step title="API-Trigger hinzufügen">
    Öffnen Sie die Routine, klicken Sie auf **Add another trigger**, wählen Sie **API** und dann **Generate token**.
    Kopieren Sie URL und Token; das Token wird nur einmal angezeigt und lässt sich später nicht erneut abrufen.
  </Step>
  <Step title="Webhook anlegen">
    Fügen Sie die URL ein, wählen Sie Ihre Ereignisse und tragen Sie die Header und die Vorlage unten ein.
  </Step>
  <Step title="Payload im Routinen-Prompt referenzieren">
    Der Text kommt in einem `routine-fire-payload`-Block an, den die Routine als nicht vertrauenswürdige Daten
    behandelt. Der Prompt der Routine muss ihn ausdrücklich referenzieren, etwa "handle das im
    routine-fire-payload-Block beschriebene Ereignis ab", sonst bleibt der Text unbeachtet.
  </Step>
</Steps>

Die URL lautet `https://api.anthropic.com/v1/claude_code/routines/<routine-id>/fire`, die Routinen-ID beginnt mit `trig_`.

```
Authorization: Bearer <routine-token>
anthropic-beta: experimental-cc-routine-2026-04-01
anthropic-version: 2023-06-01
```

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

Der Endpunkt liest ausschließlich `text` und ignoriert jedes andere Feld. Die Vorlage ist deshalb zwingend; ohne sie startet die Routine ohne Kontext. Jede Zustellung startet einen eigenen Lauf auf Ihr Routinen-Kontingent, ein Retry einen weiteren. Abonnieren Sie deshalb möglichst wenige Ereignisse.

### Slack [#slack]

Beitrag über einen Incoming Webhook in einen Kanal posten. Die URL trägt die Authentifizierung, eigene Header sind nicht nötig.

Verwenden Sie die Incoming-Webhook-URL aus **Slack → Apps → Incoming Webhooks**.

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

### Discord [#discord]

Dieselbe Struktur unter einem anderen Schlüssel.

Verwenden Sie die Webhook-URL aus **Kanal → Kanal bearbeiten → Integrationen → Webhooks**.

```json
{ "content": "{{event}} for {{data.record.ref.recordId}}" }
```

### n8n [#n8n]

Ein n8n-Webhook-Node akzeptiert den Standardumschlag. Lassen Sie beide Einstellungen leer, sofern der Node keine Header-Authentifizierung verwendet. Tut er das, tragen Sie den erwarteten Header ein und lassen die Vorlage leer:

```
X-N8N-Header-Auth: <Wert>
```

Das vollständige Muster steht unter [n8n](/docs/n8n).

### Alles andere [#anything-else]

Ein Empfänger, der weder eigene Authentifizierung noch eine feste Body-Struktur braucht, benötigt keine der beiden Einstellungen. Lassen Sie beide leer und prüfen Sie die Signatur wie unter [Wie prüfe ich die Signatur?](#how-do-i-verify-the-signature) beschrieben.

## Wie prüfe ich die Signatur? [#how-do-i-verify-the-signature]

Hat der Webhook ein **Secret**, enthält jede Request:

```
X-Webhook-Signature: <hex>
```

`<hex>` ist `HMAC-SHA256(secret, rawRequestBody)`, Lowercase-Hex, ohne Präfix. Berechnen Sie den Wert auf Ihrer Seite neu und vergleichen Sie in konstanter Zeit.

Node.js-Beispiel:

```ts
import crypto from "crypto";

function verify(rawBody: string, received: string, secret: string) {
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
}
```

## Wie funktionieren Wiederholungen (Retries) und fehlgeschlagene Zustellungen? [#how-do-retries-and-failed-deliveries-work]

Customermates wiederholt eine fehlgeschlagene Zustellung automatisch, mit bis zu 10 Versuchen insgesamt und wachsenden Pausen von höchstens einer Stunde dazwischen, bei Timeouts, Netzwerkfehlern, 5xx-Responses und 408, 425 und 429; andere 4xx-Responses, etwa 400, 401, 403, 404 und 422, werden nicht wiederholt, weil ein erneuter Versuch genauso scheitern würde. Jede Zustellung wird unter **Mein Unternehmen › Letzte Zustellungen** (`/company/webhook-deliveries`) und über `manage_webhooks` mit `action: "list_deliveries"` protokolliert. Die Seite listet die neuesten Zustellungen zuerst, mit **URL**, **Ereignis**, **Element** (dem betroffenen Datensatz), **Status**, **Status-Code** und **Erstellt am**. Das Suchfeld durchsucht Ereignis und URL, die Filter decken Ereignis, URL und Erstellungsdatum ab. Zustellungen werden nicht automatisch gelöscht; sie bleiben erhalten, solange der Workspace besteht.

Ein Klick auf eine Zeile öffnet **Ereignis-Details**. Der Dialog zeigt den Status (**Ausstehend**, bis der erste Versuch abgeschlossen ist, danach **Zugestellt** oder **Fehlgeschlagen**), **URL**, **Ereignis**, **Element**, **Erstellt am**, **Status-Code**, **Antwort-Nachricht** und den **Ereignis-Payload**. Jede Zustellung wird aus ihrem Event gelesen: Der Payload eines Messaging-Ereignisses wird so angezeigt, wie er gesendet wurde, der Payload eines Datensatz-Ereignisses wird mit Ihren aktuellen Rechten neu gelesen: Werte, die Sie nicht lesen dürfen, erscheinen als eingeschränkt, und ohne Zugriff auf den Datensatz bleibt der Payload leer.

Eine Zustellung gilt als fehlgeschlagen, wenn der HTTP-Status außerhalb des 2xx-Bereichs liegt, die Request timeoutet oder keine Antwort eintrifft. Der Request-Timeout beträgt 5 Sekunden. Eine Zustellung schlägt außerdem schon vor dem Senden fehl, mit Status-Code 422, wenn Header an eine Adresse gehen würden, die sie nicht erlaubt, oder wenn die Body-Vorlage nicht gerendert werden kann.

Die Wiederholungen laufen innerhalb desselben Zustellvorgangs, erzeugen also keine zusätzlichen Zustellungseinträge; jeder Eintrag zeigt das jeweils letzte Ergebnis, kann also **Fehlgeschlagen** anzeigen, während noch Wiederholungen ausstehen, und zu **Zugestellt** wechseln, sobald eine gelingt.

Sie können eine Zustellung zusätzlich selbst erneut senden. In **Ereignis-Details** erscheint oben das Symbol mit den kreisförmigen Pfeilen (**Erneut senden**), sobald die Zustellung **Zugestellt** oder **Fehlgeschlagen** ist, für Rollen mit **Verwalten** **Ja** bei **API & Webhooks**. Über MCP nutzen Sie `manage_webhooks` mit `action: "resend_delivery"` und der Id der Zustellung. Ein erneutes Senden erzeugt einen neuen Zustellungseintrag für denselben Webhook und sendet ihn mit der aktuellen URL, dem aktuellen Secret, den aktuellen Headern und der aktuellen Vorlage des Webhooks; das Original bleibt unverändert. Ein Messaging-Ereignis wird aus seinem gespeicherten Event erneut gesendet. Ein Datensatz-Ereignis wird mit den aktuellen Rechten des Webhook-Eigentümers neu gelesen; nur dieser Eigentümer oder ein Administrator kann es erneut senden, und das erneute Senden wird abgelehnt, wenn sich die Datensatzquellen des Webhooks seit der ursprünglichen Zustellung geändert haben. Der Webhook muss noch existieren, aktiviert sein und das Ereignis abonnieren; Zustellungen stillgelegter typspezifischer Ereignisse lassen sich nicht erneut senden.

**Link:** `/company/webhook-deliveries`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhook-deliveries` (hervorhebbar nur, solange **Mein Unternehmen** aufgeklappt ist, standardmäßig auf jeder seiner Seiten, sofern das Mitglied es nicht zugeklappt hat); `company-webhook-deliveries-search` und `company-webhook-deliveries-filter` heben das Suchfeld und die Filter hervor. `company-webhook-deliveries-display-options` hebt die Anzeigeoptionen hervor, `company-webhook-deliveries-layout-table` und `company-webhook-deliveries-layout-board` die Layout-Controls darin (zuerst die Anzeigeoptionen öffnen). Ist eine Zustellungszeile geöffnet, hebt `webhook-delivery-modal-resend` das Symbol **Erneut senden** in **Ereignis-Details** hervor (Rollen mit Verwalten-Recht, nur bei zugestellten und fehlgeschlagenen Zustellungen); die Zeilen und der Rest des Dialogs sind keine Highlight-Ziele, deshalb nennt Mate sie beim Namen.

## Sind Zustellungen geordnet, und kommen Webhooks in der richtigen Reihenfolge an? [#are-deliveries-ordered]

Zustellungen sind über Ereignisse hinweg nicht strikt geordnet. Zwei `record.updated`-Events im Millisekundenabstand können in falscher Reihenfolge ankommen. Nutzen Sie `timestamp` und Datensatzversion zur Reihenfolge oder behandeln Sie Zustellungen als idempotente Nachrichten mit `typeId`, `recordId` und Event-ID als Schlüssel.

## Warum sind Notizen in Payloads Tiptap-JSON? [#notes-are-json-not-markdown]

Das `notes`-Feld in Payloads ist Tiptap-JSON, dieselbe Struktur, die der Editor speichert. Um es auf Ihrer Seite als Markdown zu rendern, nutzen Sie einen Tiptap-kompatiblen Serializer. In MCP liefert `read_crm_record` den konfigurierten Rich-Text-Wert mit `documentJson`; bei Bedarf konvertiert ein passender Serializer das Dokument in Markdown.

## Was enthalten Delete-Payloads? [#what-do-delete-payloads-contain]

Bei `record.deleted` enthält `data.record` die eindeutige `ref`, die zulässigen Vorher-Werte und die entfernten Beziehungen. `afterVersion` ist null. Quellfilter gelten unmittelbar vor der Entfernung; der aktuelle Zugriff des Eigentümers wird vor der Zustellung erneut geprüft.

## Wie untersuche ich eine fehlgeschlagene Zustellung? [#how-do-i-debug-a-delivery]

- Nutzen Sie [webhook.site](https://webhook.site) als Einweg-Receiver beim Integrationstest.
- Das Zustellprotokoll (`manage_webhooks`, `action: "list_deliveries"`) unterstützt `searchTerm` auf URL und Event-Name.
- Für jede Zustellung erfasst Customermates nur den HTTP-Status-Code und den Statustext, den Ihr Receiver zurückgegeben hat (zum Beispiel `404` und `Not Found`), angezeigt als **Status-Code** und **Antwort-Nachricht** in **Ereignis-Details**. Der Response-Body wird nicht gespeichert, protokollieren Sie ihn also auf der Empfängerseite. Trifft keine Antwort ein, zeigt **Status-Code** einen Strich (in der Liste bleibt die Spalte leer) und **Antwort-Nachricht** nennt die Ursache, etwa den Timeout.

**Link:** `/company/webhook-deliveries`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhook-deliveries`; die Zeilen und die Felder in **Ereignis-Details** sind keine Highlight-Ziele, deshalb nennt Mate sie beim Namen.

## Welche Ereignisse gibt es? [#which-events-exist]

Ein Webhook kann [[derived.webhooks.events.total]] Events abonnieren: [[derived.webhooks.events.records]] Datensatz-Events und [[derived.webhooks.events.messaging]] Messaging-Events. Fünfzehn stillgelegte typspezifische Bezeichner können noch an älteren Webhooks und im Zustellungsverlauf stehen, lassen sich aber nicht mehr auswählen und werden von nichts mehr ausgelöst. Für einen neuen CRM-Webhook wählen Sie `record.created`, `record.updated` oder `record.deleted` und legen Datensatzquellen mit Typen, Feldern und Filtern fest. Das funktioniert auch für selbst angelegte Typen. Alle nutzen den Umschlag aus [Wie sieht der Payload aus?](#what-does-the-payload-look-like). Routinen können durch dieselben Ereignisse ausgelöst werden, mit Ausnahme von **E-Mail gelöscht** (`messaging.email.deleted`) und **Chat gelöscht** (`messaging.chat.deleted`); **Nachricht gelöscht** (`messaging.message.deleted`) löst Routinen aus; siehe [Routinen](/docs/app-routines#how-do-event-triggers-work).

### Record-Events [#record-events]

| Event | Wann es feuert | `data` |
| --- | --- | --- |
| `record.created` | Ein Datensatz eines konfigurierten Quelltyps wird erstellt | die Datensatzänderung mit den neuen Werten |
| `record.updated` | Feld, Zuweisung, Identität oder Verknüpfung eines konfigurierten Quelltyps ändert sich | die Datensatzänderung mit vorherigen und neuen Werten |
| `record.deleted` | Ein Datensatz eines konfigurierten Quelltyps wird gelöscht | die Datensatzänderung mit den vorherigen Werten |

Die folgenden typspezifischen Bezeichner sind stillgelegt. Sie bleiben nur erhalten, damit ältere Konfigurationen und Zustellungseinträge lesbar bleiben; für Webhooks und Routinen lassen sie sich nicht auswählen, und keine Änderung löst sie aus. Ersetzen Sie sie durch ein generisches Event mit Datensatzquelle.

| Altes Event | Frühere Bedeutung | Alter `payload` |
| --- | --- | --- |
| `contact.created` | Ein Contact wird via UI, API, MCP oder Import erstellt | vollständiger Contact |
| `contact.updated` | Ein Contact-Feld ändert sich | `contact`, `changes` |
| `contact.deleted` | Ein Contact wird gelöscht | vollständiger Contact |
| `organization.created` | Eine Organization wird erstellt | vollständige Organization |
| `organization.updated` | Ein Organization-Feld ändert sich | `organization`, `changes` |
| `organization.deleted` | Eine Organization wird gelöscht | vollständige Organization |
| `deal.created` | Ein Deal wird erstellt | vollständiger Deal |
| `deal.updated` | Ein Deal-Feld ändert sich | `deal`, `changes` |
| `deal.deleted` | Ein Deal wird gelöscht | vollständiger Deal |
| `service.created` | Ein Service wird erstellt | vollständiger Service |
| `service.updated` | Ein Service-Feld ändert sich | `service`, `changes` |
| `service.deleted` | Ein Service wird gelöscht | vollständiger Service |
| `task.created` | Ein Task wird erstellt | vollständiger Task |
| `task.updated` | Ein Task-Feld ändert sich | `task`, `changes` |
| `task.deleted` | Ein Task wird gelöscht | vollständiger Task |

### Messaging-Events [#messaging-events]

Messaging-Events feuern bei eingehender Provider-Aktivität auf verbundenen Accounts. Die Liste **Ereignisse** bietet sie in jedem Workspace an, sie feuern aber nur, wo verbundene Accounts existieren, und das setzt die Cloud und einen Tarif mit Messaging voraus. `actorId` ist `null`. `data` referenziert Provider-Records per id (`entityId` für die betroffene Nachricht, den Thread, Kalender, Kalendertermin oder die Verbindung, dazu `connectedAccountId`, `provider`, `providerMessageId`, `threadId` und ähnliche), statt CRM-Records einzubetten. Ein Messaging-Event wird nur gespeichert, solange ein Webhook oder eine Event-Routine es abonniert.

| Event | Wann es feuert |
| --- | --- |
| `messaging.message.received` | Eine Chat-Nachricht oder E-Mail wird ingested |
| `messaging.message.updated` | Eine ingestete Nachricht wird aktualisiert |
| `messaging.message.deleted` | Eine ingestete Nachricht wird gelöscht |
| `messaging.message.reaction` | Eine Reaktion wird zu einer Nachricht hinzugefügt |
| `messaging.email.received` | Eine E-Mail wird ingested |
| `messaging.email.deleted` | Eine ingestete E-Mail wird gelöscht |
| `messaging.chat.updated` | Ein Chat-Thread wird aktualisiert |
| `messaging.chat.deleted` | Ein Chat-Thread wird gelöscht |
| `messaging.calendar.changed` | Ein verbundener Kalender ändert sich |
| `messaging.calendar_event.changed` | Ein Kalender-Event ändert sich |
| `messaging.relation.created` | Eine neue Provider-Relation wird erstellt |
