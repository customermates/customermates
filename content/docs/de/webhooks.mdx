Customermates sendet einen JSON-POST an Ihren Endpunkt, sobald sich abonnierte Daten ändern. Sie wählen die Ereignisse und die URL. Mit einem Secret wird jede Zustellung per HMAC-SHA256 über den rohen Request-Body signiert. Fehlgeschlagene Zustellungen werden automatisch wiederholt und lassen sich von Hand erneut senden. Der Ereigniskatalog steht am Ende dieser Seite.

## Wofür sind Webhooks da? [#what-are-webhooks-for]

Webhooks lassen andere Systeme auf CRM-Änderungen reagieren, ohne zu pollen, etwa um neue Kontakte an einen E-Mail-Sequencer zu übergeben, ein Support-Ticket zu öffnen, wenn ein Deal seinen Zustand ändert, einen Finance-Workflow beim Abschluss eines Deals zu starten oder Datensätze nahezu in Echtzeit in ein Data Warehouse zu synchronisieren.

## Wie lege ich einen Webhook an? [#how-do-i-create-a-webhook]

Öffnen Sie [Webhooks](app:company/webhooks), klicken Sie auf [Hinzufügen](app:company/webhooks?focus=add), füllen Sie den Dialog **Webhook** aus und klicken Sie auf **Speichern**.

| Feld | Wirkung |
| --- | --- |
| **URL** | Pflichtfeld. Der Endpunkt, der für jedes abonnierte Ereignis einen `POST` erhält. Eine URL ohne Schema wird mit vorangestelltem `https://` gespeichert. |
| **Beschreibung** | Optional, bis zu 500 Zeichen. Erscheint in der Liste. |
| **Ereignisse** | Pflichtfeld. Ein oder mehrere Ereignisse aus dem [Katalog](#which-events-exist). |
| **Secret** | Optional, 1 bis 256 Zeichen. Signiert jede Zustellung (siehe [Wie prüfe ich die Signatur?](#how-do-i-verify-the-signature)). |
| **Eigene Header** | Optional. Ein `Name: Wert` pro Zeile (siehe [Eigene Header und Body-Vorlagen](#custom-headers-and-body-templates)). |
| **Body-Vorlage** | Optionales JSON-Dokument, das den Standardumschlag ersetzt. |
| **Aktiviert** | Standardmäßig eingeschaltet. Ein deaktivierter Webhook erhält nichts und behält seine Konfiguration, Sie können ihn also pausieren, ohne ihn zu löschen. |

Um einen Webhook zu ändern, klicken Sie auf seine Zeile, bearbeiten ihn und klicken auf **Speichern**. Zum Entfernen klicken Sie oben im Dialog auf **Löschen** und bestätigen; seine bisherigen Zustellungen bleiben im Reiter [Zustellungen](app:company/webhook-deliveries) erhalten. Die Liste zeigt **URL**, **Beschreibung**, **Ereignisse**, **Status** (**Aktiviert** oder **Deaktiviert**), **Erstellt am** und **Aktualisiert am**. Die [Suche](app:company/webhooks?focus=search) durchsucht die URL, die [Filter](app:company/webhooks?focus=filter) decken Erstellungs- und Änderungsdatum ab.

Verwenden Sie einen HTTPS-Endpunkt. Reines `http://` wird für jeden Host nur akzeptiert, solange der Webhook keine eigenen Header hat. Mit eigenen Headern muss die URL `https://` verwenden oder `http://` auf `localhost`, `127.0.0.1` oder `::1`, da Header in der Regel ein Credential tragen. Das wird beim Speichern und erneut vor jeder Zustellung geprüft.

Über MCP nutzen Sie `manage_webhooks` mit `action: "create"`, dazu `url`, `events[]` und optional `description`, `secret`, `headers`, `bodyTemplate`, `enabled`.

## Welche Datensätze lösen einen Webhook aus, und mit wessen Zugriff wird zugestellt? [#record-event-sources]

Sobald Sie ein Datensatzereignis wählen, zeigt der Dialog die Datensatzquelle: Wählen Sie unter **Datensätze aus** die Liste (oder **Alle zugänglichen Typen**) und bei Bedarf **Geänderte Felder**, **Datensätze suchen** sowie **Datensatzfilter** auf Feldern und Beziehungen. Zugestellt wird mit dem Datensatzzugriff des Mitglieds unter **Zugriffsberechtigtes Mitglied**, standardmäßig des Mitglieds, das den Webhook anlegt; nur ein Administrator kann ein anderes Mitglied wählen. Ältere migrierte Webhooks können mehrere Quellen behalten, die als Chips erscheinen.

Über MCP benötigen Datensatzabonnements in `manage_webhooks` außerdem `expectedSchemaRevision` aus `get_record_model`. `recordTrigger` enthält eine Abfrage mit stabilen Typ- und Feld-IDs und optionalen `changedFieldIds`; `null` wählt alle zugänglichen Typen. `recordOwnerUserId` legt optional den Eigentümer für die Zustellung fest. Lassen Sie diese Einstellungen bei einem Update weg, um sie zu behalten; Änderungen an Quelle oder Eigentümer benötigen die aktuelle Schema-Revision.

```json
{
  "url": "https://hooks.example.com/customermates",
  "events": ["record.created", "record.updated"],
  "expectedSchemaRevision": 3,
  "recordTrigger": {
    "query": { "typeId": "<project-type-id>" },
    "changedFieldIds": []
  },
  "secret": "nutze-einen-random-string-aus-einem-password-manager",
  "enabled": true
}
```

## Wer kann Webhooks sehen und ändern? [#who-can-see-and-change-webhooks]

Den Zugriff legt die Zeile **API & Webhooks** einer Rolle unter [Rollen](app:company/roles) fest.

| Einstellung bei **API & Webhooks** | Was Mitglieder mit dieser Rolle tun können |
| --- | --- |
| **Lesen** **Keine** (Standard für eine neue Rolle) | Webhooks sind ausgeblendet; wer die Seite direkt öffnet, landet auf dem Dashboard. |
| **Lesen** **Alle**, keine Checkbox angehakt | Webhooks und die Zustellungen öffnen, jeden Webhook schreibgeschützt öffnen und **Ereignis-Details** zu jeder Zustellung öffnen. Ein gespeichertes **Secret** und jeder Wert unter **Eigene Header** erscheinen als `********`; die Header-Namen bleiben sichtbar. |
| **Lesen** **Alle** plus **Erstellen** | Webhooks anlegen und Zustellungen erneut senden. |
| **Lesen** **Alle** plus **Bearbeiten** | Webhooks bearbeiten und gespeicherte Werte von **Secret** und **Eigene Header** sehen. |
| **Lesen** **Alle** plus **Löschen** | Webhooks löschen. |

Dieselbe Zeile steuert auch [API-Schlüssel](app:profile/api-keys). Eine Rolle, die eigene API-Keys anlegen oder löschen darf, darf also auch jeden Webhook im Workspace anlegen oder löschen. Die Rolle **Admin** darf alles. Webhooks sind an keinen Tarif gebunden und funktionieren in jedem Cloud-Tarif sowie selbstgehostet. Dieselben Berechtigungen gelten für `manage_webhooks` über MCP und in Mate; dort fragt das Löschen eines Webhooks oder das erneute Senden einer Zustellung vorher nach Ihrer Freigabe.

## Wie sieht der Payload aus? [#what-does-the-payload-look-like]

Jede Zustellung ist ein `POST` mit `Content-Type: application/json` und demselben Umschlag:

```json
{
  "event": "<event-name>",
  "id": "<event-id>",
  "timestamp": "<iso-8601>",
  "companyId": "<workspace>",
  "actorId": "<verursacher>",
  "data": {
    /* event-spezifisch */
  }
}
```

`id` bezeichnet das Ereignis: Ein erneutes Senden und jeder Wiederholungsversuch tragen dieselbe `id`, nutzen Sie sie also zum Deduplizieren. `actorId` ist der User, der den Write verursacht hat, inklusive User, die über einen API-Key handeln, und Routinen, die für ihren Eigentümer laufen. Messaging-Ereignisse entstehen durch eingehende Provider-Aktivität, ihr `actorId` ist deshalb `null`.

Bei Datensatzereignissen enthält `data.record` die Referenz (`typeId` und `recordId`, auch nach einer Umbenennung eindeutig) und die Änderungen, `data.cause` die Ursache des Writes, und `data.causeId` teilen alle Ereignisse desselben Writes.

Beispiel für `record.updated` bei einem Kontakt, ohne für die Erklärung unnötige Felder:

```json
{
  "event": "record.updated",
  "id": "<event-id>",
  "timestamp": "2026-04-22T10:00:00.000Z",
  "companyId": "<workspace-id>",
  "actorId": "<ausloesender-user-id>",
  "data": {
    "causeId": "<cause-id>",
    "cause": { "kind": "mutation" },
    "record": {
      "ref": { "typeId": "<kontakt-typ-id>", "recordId": "<record-id>" },
      "schemaRevision": 3,
      "beforeVersion": 1,
      "afterVersion": 2,
      "fields": [
        {
          "fieldId": "<vorname-feld-id>",
          "before": { "value": { "state": "value", "value": { "kind": "text", "value": "Max" } } },
          "after": { "value": { "state": "value", "value": { "kind": "text", "value": "Maximilian" } } }
        }
      ]
    }
  }
}
```

Eine echte Datensatzänderung enthält außerdem Zuweisungen, Identitäten, Änderungen an Verknüpfungen und verknüpfte Datensätze. Feldeinträge tragen Anzeigedaten und können statt eines Werts `missing`, `restricted` oder `error` enthalten. Stabile Typ- und Feld-IDs liefert `POST /api/v1/model/discover` oder das MCP-Tool `get_record_model`.

## Das `changes`-Objekt: geänderte Felder [#the-changes-object]

`data.record.fields` listet geänderte Felder mit Werten für `before` und `after`; `data.record.links`, `data.record.assignments` und `data.record.identities` beschreiben weitere geänderte Verbindungen. `data.record.beforeVersion` und `data.record.afterVersion` bezeichnen die Datensatzversionen. Ein fehlender oder eingeschränkter Wert ist nicht dasselbe wie 0.

Änderungen ohne Wirkung erzeugen kein `record.updated`-Ereignis. Der Payload wird bei der Zustellung gemäß den aktuellen Datensatz- und Berechnungsfeldrechten des Webhook-Eigentümers redigiert.

## Eigene Header und Body-Vorlagen [#custom-headers-and-body-templates]

Zwei optionale Einstellungen decken Empfänger ab, die die Standardzustellung nicht akzeptieren. Ein Webhook ohne beide sendet den [Standardumschlag](#what-does-the-payload-look-like).

**Eigene Header** werden bei jeder Zustellung mitgesendet, für Endpunkte mit eigener Authentifizierung. Tragen Sie sie zeilenweise als `Name: Wert` ein (eine Zeile ohne Doppelpunkt wird ignoriert, ein leeres Feld entfernt alle Header) oder übergeben Sie über MCP und API ein `headers`-Objekt. Sechs Namen sind reserviert und werden abgelehnt: `Connection`, `Content-Length`, `Content-Type`, `Host`, `Transfer-Encoding` und `X-Webhook-Signature`. Namen müssen gültige HTTP-Tokens sein, Werte Latin-1-Text ohne Zeilenumbrüche. Ein Webhook darf bis zu 20 Header tragen, mit Namen bis 128 Zeichen, Werten bis 2.048 Zeichen und insgesamt 8.192 Zeichen. Ein Webhook mit Headern muss HTTPS verwenden; reines HTTP wird nur für `localhost`, `127.0.0.1` und `::1` akzeptiert.

REST-API und MCP geben Header-Werte und das Secret nie zurück; sie liefern `headerNames` und `hasSecret`. Der Dialog zeigt die Werte nur der Rolle **Admin** und Rollen mit **Bearbeiten** bei **API & Webhooks**, das Secret maskiert, bis Sie auf das Augensymbol klicken. Eine Aktualisierung über API oder MCP ohne `headers` behält die gespeicherten Werte, `null` löscht sie.

**Eine Body-Vorlage** ersetzt den Standardumschlag für Endpunkte mit fester Struktur. Schreiben Sie ein JSON-Dokument mit Platzhaltern:

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

Platzhalter sind `{{event}}`, `{{id}}`, `{{timestamp}}`, `{{companyId}}`, `{{actorId}}` sowie jeder Pfad unterhalb von `{{data}}`, etwa `{{data.record.ref.recordId}}` bei einem Datensatzereignis oder `{{data.entityId}}` bei einem Messaging-Ereignis. Ein Platzhalter muss innerhalb eines JSON-Strings stehen; `{"count": {{data.count}}}` wird abgelehnt. Ein Objektwert wird als JSON-String eingesetzt, ein fehlender Pfad als leerer String. Eingesetzte Werte werden escaped, sodass Datensatzinhalte die Struktur des Dokuments nicht verändern können.

Die Vorlage darf bis zu 8.192 Zeichen lang sein, muss ein JSON-Objekt ergeben und wird beim Speichern geprüft. Eine Zustellung, deren Vorlage nicht gerendert werden kann oder deren gerenderter Body 131.072 Zeichen überschreitet, wird als fehlgeschlagen erfasst, ohne gesendet zu werden, und nicht wiederholt. Die Signatur wird über den tatsächlich gesendeten Body berechnet, prüfen Sie sie also gegen den gerenderten Body.

**Secret oder Vorlage entfernen.** Ist **Secret** oder **Body-Vorlage** einmal gesetzt, lehnt der Dialog das Speichern mit leerem Feld ab. Aktualisieren Sie den Webhook über `manage_webhooks` oder die REST-API mit `secret: null` oder `bodyTemplate: null`, oder löschen Sie ihn und legen ihn neu an.

Zustellungen werden mit dem Ereignis-Payload erfasst, nicht mit dem gerenderten Body. **Ereignis-Details** zeigt also das ausgelöste Ereignis und nicht die exakt gesendeten Bytes.

## Wie sende ich an Slack, Discord oder n8n? [#how-do-i-send-to-slack-discord-or-n8n]

Jedes Rezept nennt URL, eigene Header und Body-Vorlage, die Sie nach [Hinzufügen](app:company/webhooks?focus=add) in Webhooks eintragen. Setzen Sie in jedem Fall ein Secret; ein Empfänger, der es nicht prüfen kann, ignoriert den Header.

### Claude-Code-Routinen [#claude-code-routines]

Startet eine Claude-Code-Routine, wenn sich ein Datensatz ändert. Legen Sie die Routine zuerst unter [claude.ai/code/routines](https://claude.ai/code/routines) an.

<Steps>
  <Step title="API-Trigger hinzufügen">
    Öffnen Sie die Routine, klicken Sie auf **Add another trigger**, wählen Sie **API** und dann **Generate token**.
    Kopieren Sie URL und Token; das Token wird nur einmal angezeigt und lässt sich später nicht erneut abrufen.
  </Step>
  <Step title="Webhook anlegen">
    Fügen Sie die URL ein, wählen Sie Ihre Ereignisse und tragen Sie die Header und die Vorlage unten ein.
  </Step>
  <Step title="Payload im Routinen-Prompt referenzieren">
    Der Text kommt in einem `routine-fire-payload`-Block an, den die Routine als nicht vertrauenswürdige Daten
    behandelt. Der Prompt der Routine muss ihn ausdrücklich referenzieren, etwa "handle das im
    routine-fire-payload-Block beschriebene Ereignis ab", sonst bleibt der Text unbeachtet.
  </Step>
</Steps>

Die URL lautet `https://api.anthropic.com/v1/claude_code/routines/<routine-id>/fire`, die Routinen-ID beginnt mit `trig_`.

```
Authorization: Bearer <routine-token>
anthropic-beta: experimental-cc-routine-2026-04-01
anthropic-version: 2023-06-01
```

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

Der Endpunkt liest ausschließlich `text`, die Vorlage ist deshalb zwingend; ohne sie startet die Routine ohne Kontext. Jede Zustellung und jeder Retry startet einen eigenen Lauf auf Ihr Routinen-Kontingent. Abonnieren Sie deshalb nur die Ereignisse, die die Aufgabe braucht.

### Slack [#slack]

Posten Sie über einen Incoming Webhook aus **Slack → Apps → Incoming Webhooks** in einen Kanal. Die URL trägt die Authentifizierung, eigene Header sind nicht nötig.

```json
{ "text": "{{event}} for {{data.record.ref.recordId}}" }
```

### Discord [#discord]

Verwenden Sie die Webhook-URL aus **Kanal → Kanal bearbeiten → Integrationen → Webhooks**. Dieselbe Struktur, anderer Schlüssel:

```json
{ "content": "{{event}} for {{data.record.ref.recordId}}" }
```

### n8n [#n8n]

Ein n8n-Webhook-Node akzeptiert den Standardumschlag. Lassen Sie beide Einstellungen leer, sofern der Node keine Header-Authentifizierung verwendet. Tut er das, tragen Sie den erwarteten Header ein und lassen die Vorlage leer:

```
X-N8N-Header-Auth: <Wert>
```

Das vollständige Muster steht unter [n8n](/docs/n8n).

### Alles andere [#anything-else]

Ein Empfänger, der weder eigene Authentifizierung noch eine feste Body-Struktur braucht, benötigt keine der beiden Einstellungen. Lassen Sie beide leer und [prüfen Sie die Signatur](#how-do-i-verify-the-signature).

## Wie prüfe ich die Signatur? [#how-do-i-verify-the-signature]

Hat der Webhook ein **Secret**, enthält jede Request:

```
X-Webhook-Signature: <hex>
```

`<hex>` ist `HMAC-SHA256(secret, rawRequestBody)`, Lowercase-Hex, ohne Präfix. Berechnen Sie den Wert auf Ihrer Seite neu und vergleichen Sie in konstanter Zeit.

Node.js-Beispiel:

```ts
import crypto from "crypto";

function verify(rawBody: string, received: string, secret: string) {
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
}
```

## Wie funktionieren Wiederholungen (Retries) und fehlgeschlagene Zustellungen? [#how-do-retries-and-failed-deliveries-work]

Eine Zustellung schlägt fehl, wenn der HTTP-Status außerhalb von 2xx liegt, die Request nach 5 Sekunden timeoutet oder keine Antwort eintrifft. Customermates wiederholt Timeouts, Netzwerkfehler, 5xx-Responses sowie 408, 425 und 429 automatisch, mit bis zu 10 Versuchen insgesamt und wachsenden Pausen von höchstens einer Stunde. Andere 4xx-Responses, etwa 400, 401, 403, 404 und 422, werden nicht wiederholt, weil ein erneuter Versuch genauso scheitern würde. Eine Zustellung schlägt außerdem schon vor dem Senden fehl, mit Status-Code 422, wenn Header an eine Adresse gehen würden, die sie nicht erlaubt, oder die Body-Vorlage nicht gerendert werden kann.

Jede Zustellung wird im Reiter [Zustellungen](app:company/webhook-deliveries) von Webhooks protokolliert, die neueste zuerst, mit **URL**, **Ereignis**, **Element** (dem betroffenen Datensatz), **Status**, **Status-Code** und **Erstellt am**. Die [Suche](app:company/webhook-deliveries?focus=search) durchsucht Ereignis und URL, die [Filter](app:company/webhook-deliveries?focus=filter) decken Ereignis, URL und Erstellungsdatum ab. Über MCP nutzen Sie `manage_webhooks` mit `action: "list_deliveries"`. Zustellungen bleiben erhalten, solange der Workspace besteht.

Wiederholungen laufen innerhalb derselben Zustellung und erzeugen keine weiteren Einträge: Jeder Eintrag zeigt das letzte Ergebnis, kann also **Fehlgeschlagen** zeigen, während noch Wiederholungen ausstehen, und zu **Zugestellt** wechseln, sobald eine gelingt.

Ein Klick auf eine Zeile öffnet **Ereignis-Details**: Status (**Ausstehend**, **Wird gesendet**, **Zugestellt** oder **Fehlgeschlagen**), **URL**, **Ereignis**, **Element**, **Erstellt am**, **Status-Code**, **Antwort-Nachricht** und **Ereignis-Payload**. Der Payload eines Messaging-Ereignisses erscheint so, wie er gesendet wurde. Der Payload eines Datensatzereignisses wird mit Ihren aktuellen Rechten neu gelesen: Werte, die Sie nicht lesen dürfen, erscheinen als eingeschränkt, und ohne Zugriff auf den Datensatz bleibt der Payload leer.

Zum erneuten Senden klicken Sie oben in **Ereignis-Details** auf **Erneut senden**. Die Aktion erscheint, sobald die Zustellung **Zugestellt** oder **Fehlgeschlagen** ist, für Rollen mit **Erstellen** bei **API & Webhooks**; über MCP nutzen Sie `manage_webhooks` mit `action: "resend_delivery"` und der Id der Zustellung. Ein erneutes Senden erzeugt einen neuen Zustellungseintrag mit der aktuellen URL, dem aktuellen Secret, den aktuellen Headern und der aktuellen Vorlage des Webhooks; das Original bleibt unverändert. Ein Messaging-Ereignis wird aus seinem gespeicherten Event erneut gesendet. Ein Datensatzereignis wird mit den aktuellen Rechten des Webhook-Eigentümers neu gelesen, nur dieser Eigentümer oder ein Administrator kann es erneut senden, und das erneute Senden wird abgelehnt, wenn sich die Datensatzquellen des Webhooks seit der ursprünglichen Zustellung geändert haben. Der Webhook muss noch existieren, aktiviert sein und das Ereignis abonnieren; Zustellungen stillgelegter typspezifischer Ereignisse lassen sich nicht erneut senden.

## Sind Zustellungen geordnet, und kommen Webhooks in der richtigen Reihenfolge an? [#are-deliveries-ordered]

Nein. Zwei `record.updated`-Ereignisse im Millisekundenabstand können in falscher Reihenfolge ankommen. Nutzen Sie `timestamp` und Datensatzversion zur Reihenfolge oder behandeln Sie Zustellungen als idempotente Nachrichten mit `typeId`, `recordId` und Ereignis-ID als Schlüssel.

## Warum sind Notizen in Payloads Tiptap-JSON? [#notes-are-json-not-markdown]

Das `notes`-Feld in Payloads ist Tiptap-JSON, die Struktur, die der Editor speichert. Ein Tiptap-kompatibler Serializer macht daraus Markdown. In MCP liefert `read_crm_record` den Rich-Text-Wert mit `documentJson`, der sich genauso umwandeln lässt.

## Was enthalten Delete-Payloads? [#what-do-delete-payloads-contain]

Bei `record.deleted` enthält `data.record` die eindeutige `ref`, die zulässigen Vorher-Werte und die entfernten Beziehungen; `afterVersion` ist null. Quellfilter gelten unmittelbar vor der Entfernung, der aktuelle Zugriff des Eigentümers wird vor der Zustellung erneut geprüft.

## Wie untersuche ich eine fehlgeschlagene Zustellung? [#how-do-i-debug-a-delivery]

- Suchen Sie die Zustellung unter [Zustellungen](app:company/webhook-deliveries) und öffnen Sie sie, um die **Ereignis-Details** zu sehen.
- Nutzen Sie [webhook.site](https://webhook.site) beim Testen als Einweg-Empfänger.
- `manage_webhooks` mit `action: "list_deliveries"` unterstützt `searchTerm` auf URL und Ereignisname.
- Customermates speichert nur den HTTP-Status-Code und den Statustext, den Ihr Empfänger zurückgegeben hat (zum Beispiel `404` und `Not Found`), angezeigt als **Status-Code** und **Antwort-Nachricht** in **Ereignis-Details**. Der Response-Body wird nicht gespeichert, protokollieren Sie ihn also auf der Empfängerseite. Ohne Antwort zeigt **Status-Code** einen Strich (in der Liste bleibt die Spalte leer) und **Antwort-Nachricht** nennt die Ursache, etwa den Timeout.

## Welche Ereignisse gibt es? [#which-events-exist]

Ein Webhook kann [[derived.webhooks.events.total]] Ereignisse abonnieren: [[derived.webhooks.events.records]] Datensatzereignisse und [[derived.webhooks.events.messaging]] Messaging-Ereignisse. Für einen CRM-Webhook wählen Sie **Datensatz erstellt**, **Datensatz aktualisiert** oder **Datensatz gelöscht** (`record.created`, `record.updated`, `record.deleted`) und legen die [Datensatzquelle](#record-event-sources) fest; das gilt auch für Listen, die Sie selbst angelegt haben. Alle nutzen den [Standardumschlag](#what-does-the-payload-look-like). Routinen können durch dieselben Ereignisse ausgelöst werden, mit Ausnahme von **E-Mail gelöscht** (`messaging.email.deleted`) und **Chat gelöscht** (`messaging.chat.deleted`); **Nachricht gelöscht** (`messaging.message.deleted`) löst Routinen aus. Siehe [Routinen](/docs/app-routines#how-do-event-triggers-work).

### Record-Events [#record-events]

| Event | Wann es feuert | `data` |
| --- | --- | --- |
| `record.created` | Ein Datensatz eines konfigurierten Quelltyps wird erstellt | die Datensatzänderung mit den neuen Werten |
| `record.updated` | Feld, Zuweisung, Identität oder Verknüpfung eines konfigurierten Quelltyps ändert sich | die Datensatzänderung mit vorherigen und neuen Werten |
| `record.deleted` | Ein Datensatz eines konfigurierten Quelltyps wird gelöscht | die Datensatzänderung mit den vorherigen Werten |

Fünfzehn typspezifische Bezeichner sind stillgelegt. Sie bleiben nur erhalten, damit ältere Webhooks und Zustellungseinträge lesbar bleiben: Für Webhooks und Routinen lassen sie sich nicht auswählen, und nichts löst sie aus. Ersetzen Sie sie durch ein generisches Ereignis mit Datensatzquelle.

| Altes Event | Frühere Bedeutung | Alter `payload` |
| --- | --- | --- |
| `contact.created` | Ein Contact wird via UI, API, MCP oder Import erstellt | vollständiger Contact |
| `contact.updated` | Ein Contact-Feld ändert sich | `contact`, `changes` |
| `contact.deleted` | Ein Contact wird gelöscht | vollständiger Contact |
| `organization.created` | Eine Organization wird erstellt | vollständige Organization |
| `organization.updated` | Ein Organization-Feld ändert sich | `organization`, `changes` |
| `organization.deleted` | Eine Organization wird gelöscht | vollständige Organization |
| `deal.created` | Ein Deal wird erstellt | vollständiger Deal |
| `deal.updated` | Ein Deal-Feld ändert sich | `deal`, `changes` |

### Messaging-Events [#messaging-events]

Messaging-Ereignisse feuern bei eingehender Provider-Aktivität auf verbundenen Konten. **Ereignisse** bietet sie in jedem Workspace an, sie feuern aber nur, wo [Kanäle](app:profile/connected-accounts) verbunden sind, und das setzt die Cloud und einen Tarif mit Messaging voraus. `actorId` ist `null`. `data` referenziert Provider-Records per id (`entityId` für die betroffene Nachricht, den Thread, Kalender, Kalendertermin oder die Verbindung, dazu `connectedAccountId`, `provider`, `providerMessageId`, `threadId` und ähnliche), statt CRM-Datensätze einzubetten. Ein Messaging-Ereignis wird nur gespeichert, solange ein Webhook oder eine Event-Routine es abonniert.

| Event | Wann es feuert |
| --- | --- |
| `messaging.message.received` | Eine Chat-Nachricht oder E-Mail wird ingested |
| `messaging.message.updated` | Eine ingestete Nachricht wird aktualisiert |
| `messaging.message.deleted` | Eine ingestete Nachricht wird gelöscht |
| `messaging.message.reaction` | Eine Reaktion wird zu einer Nachricht hinzugefügt |
| `messaging.email.received` | Eine E-Mail wird ingested |
| `messaging.email.deleted` | Eine ingestete E-Mail wird gelöscht |
| `messaging.chat.updated` | Ein Chat-Thread wird aktualisiert |
| `messaging.chat.deleted` | Ein Chat-Thread wird gelöscht |
| `messaging.calendar.changed` | Ein verbundener Kalender ändert sich |
| `messaging.calendar_event.changed` | Ein Kalender-Event ändert sich |
| `messaging.relation.created` | Eine neue Provider-Relation wird erstellt |
