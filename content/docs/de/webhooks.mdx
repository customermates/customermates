Customermates sendet einen JSON-POST an Ihren Endpunkt, sobald sich abonnierte Daten ändern. Sie wählen die Events und geben die URL an. Fehlgeschlagene Deliveries können Sie aus der UI oder per MCP erneut zustellen. Hat der Webhook ein Secret, werden Deliveries per HMAC-SHA256 über den rohen Request-Body signiert. Jedes Event und seine Payload-Struktur stehen im Katalog am Ende dieser Seite.

## Wofür sind Webhooks da?

Webhooks lassen andere Systeme auf CRM-Änderungen reagieren, ohne zu pollen.

- Neue Contacts in einen E-Mail-Sequencer übergeben.
- Ein Ticket im Support-Tool öffnen, wenn ein Deal seinen Zustand ändert.
- Einen Finance-Workflow auslösen, wenn ein Deal als abgeschlossen markiert wird.
- Records nahezu in Echtzeit in ein Data Warehouse synchronisieren.

## Wie füge ich einen Webhook hinzu? [#how-do-i-create-a-webhook]

**UI:** Klappen Sie in der Seitenleiste **Mein Unternehmen** auf, öffnen Sie **Webhooks** und klicken Sie auf **Hinzufügen** (auf schmalen Bildschirmen zeigt die Schaltfläche nur ein Plus-Symbol). Füllen Sie den Dialog **Webhook** aus und klicken Sie auf **Speichern**.

| Feld | Wirkung |
|---|---|
| **URL** | Pflichtfeld. Der Endpunkt, der für jedes abonnierte Ereignis einen `POST` erhält. Eine URL ohne Schema wird mit vorangestelltem `https://` gespeichert. |
| **Beschreibung** | Optional, bis zu 500 Zeichen. Erscheint in der Liste. |
| **Ereignisse** | Pflichtfeld. Ein oder mehrere Ereignisse aus dem Katalog am Ende dieser Seite. |
| **Secret** | Optional, 1 bis 256 Zeichen. Ist es gesetzt, tragen Zustellungen eine damit erstellte Signatur (siehe „Wie prüfe ich die Signatur?“ weiter unten). Zeigt ein älterer Webhook auf dieselbe URL, gilt stattdessen dessen Secret, und ohne Secret gehen Zustellungen unsigniert hinaus (siehe „Eine URL, eine Konfiguration“ weiter unten). |
| **Eigene Header** | Optional. Ein `Name: Wert` pro Zeile (siehe „Custom Headers und Body-Vorlagen“ weiter unten). |
| **Body-Vorlage** | Optionales JSON-Dokument, das den Standardumschlag ersetzt. |
| **Aktiviert** | Standardmäßig eingeschaltet. Ein deaktivierter Webhook erhält keine Zustellungen und behält seine Konfiguration, Sie können ihn also pausieren, ohne ihn zu löschen. |

Um einen Webhook zu ändern, klicken Sie auf seine Zeile, bearbeiten den Dialog und klicken auf **Speichern**. Zum Entfernen klicken Sie oben im Dialog auf das Papierkorb-Symbol (**Löschen**) und bestätigen; seine bisherigen Zustellungen bleiben unter **Letzte Zustellungen** erhalten. Die Liste zeigt für jeden Webhook **URL**, **Beschreibung**, **Ereignisse**, **Status** (**Aktiviert** oder **Deaktiviert**), **Erstellt am** und **Aktualisiert am**. Das Suchfeld durchsucht die URL, die Filter decken Erstellungs- und Änderungsdatum ab.

**MCP:** `manage_webhooks` mit `action: "create"`, dazu `url`, `events[]` und optional `description`, `secret`, `headers`, `bodyTemplate`, `enabled`. Der gehostete Assistent nutzt dasselbe Tool und kann außerdem **Webhooks** oder **Letzte Zustellungen** für Sie öffnen und auf die Schaltfläche **Hinzufügen** zeigen.

```json
{
  "url": "https://hooks.example.com/customermates",
  "events": ["contact.created", "contact.updated", "deal.updated"],
  "secret": "nutze-einen-random-string-aus-einem-password-manager",
  "enabled": true
}
```

Verwenden Sie einen HTTPS-Endpunkt. Eine reine `http://`-URL wird für jeden Host akzeptiert, solange der Webhook keine eigenen Header hat. Ein Webhook mit eigenen Headern muss `https://` verwenden oder `http://` auf `localhost`, `127.0.0.1` oder `::1`, da Header in der Regel ein Credential tragen. Diese Regel wird beim Speichern und erneut vor jeder Zustellung geprüft.

**Link:** `/company/webhooks`, Cloud-URL `https://customermates.com/de/company/webhooks`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhooks` (hervorhebbar nur, solange **Mein Unternehmen** aufgeklappt ist, standardmäßig auf jeder seiner Seiten, sofern das Mitglied es nicht zugeklappt hat); `company-webhooks-add` hebt **Hinzufügen** hervor (nur vorhanden mit **Verwalten** **Ja** bei **API & Webhooks**), `company-webhooks-search` und `company-webhooks-filter` heben das Suchfeld und die Filter hervor. `company-webhooks-display-options` hebt die Anzeigeoptionen hervor, `company-webhooks-layout-table` und `company-webhooks-layout-board` die Layout-Controls darin (zuerst die Anzeigeoptionen öffnen). Im Dialog **Webhook**, geöffnet über **Hinzufügen** (Voraussetzung `company-webhooks-add`) oder eine Zeile, heben `webhook-modal-url`, `webhook-modal-description`, `webhook-modal-events`, `webhook-modal-secret`, `webhook-modal-headers`, `webhook-modal-body-template` und `webhook-modal-enabled` die Felder der Tabelle oben hervor, ohne **Verwalten** schreibgeschützt. `webhook-modal-save` und `webhook-modal-reset` heben **Speichern** und **Zurücksetzen** hervor, nur für Rollen mit **Verwalten** **Ja** bei **API & Webhooks** (**Zurücksetzen** erst, wenn sich etwas geändert hat), und `webhook-modal-delete` hebt **Löschen** bei einem gespeicherten Webhook für dieselben Rollen hervor.

## Wer kann Webhooks sehen und ändern?

Den Zugriff legt die Zeile **API & Webhooks** im Rolleneditor unter **Mein Unternehmen** → **Rollen** fest. Dieselbe Zeile steuert auch **Mein Profil** → **API & Konnektoren**. Eine Rolle, die ihre eigenen API-Keys verwalten darf, darf also auch jeden Webhook im Workspace verwalten.

| Einstellung bei **API & Webhooks** | Was Mitglieder mit dieser Rolle tun können |
|---|---|
| **Lesen** **Keine** (Standard für eine neue Rolle) | **Webhooks** und **Letzte Zustellungen** sind in der Seitenleiste ausgeblendet. Wer die Adresse direkt öffnet, landet auf dem Dashboard. |
| **Lesen** **Alle**, **Verwalten** **Nein** | Beide Seiten öffnen, den Dialog jedes Webhooks schreibgeschützt öffnen (einschließlich der Werte von **Secret** und **Eigene Header**) und **Ereignis-Details** zu jeder Zustellung öffnen. |
| **Lesen** **Alle**, **Verwalten** **Ja** | Alles oben Genannte, dazu Webhooks anlegen, bearbeiten und löschen sowie Zustellungen erneut senden. |

Die Rolle **Admin** darf alles. Webhooks sind an keinen Tarif gebunden und funktionieren in jedem Cloud-Tarif sowie in einer selbstgehosteten Installation. Dieselben Berechtigungen gelten für `manage_webhooks` über MCP und im gehosteten Assistenten. Im gehosteten Assistenten fragt das Löschen eines Webhooks oder das erneute Senden einer Zustellung vorher nach Ihrer Freigabe.

## Wie sieht der Payload aus?

Jede Delivery ist ein `POST` mit `Content-Type: application/json` und demselben Envelope:

```json
{
  "event": "<event-name>",
  "data": {
    "userId": "<verursacher>",
    "companyId": "<workspace>",
    "entityId": "<betroffener-record>",
    "payload": { /* event-spezifisch */ }
  },
  "timestamp": "<iso-8601>"
}
```

`userId` ist der User, der den Write verursacht hat, inklusive User, die über einen API-Key handeln. Bei Messaging-Events, die durch eingehende Provider-Aktivität statt durch eine User-Aktion ausgelöst werden, ist `userId` gleich `null`.

Bei `*.updated`-Events umschließt `payload` den vollständigen Record zusammen mit einem `changes`-Objekt. Bei `*.created`- und `*.deleted`-Events ist `payload` der Record selbst.

Beispiel, `contact.updated`:

```json
{
  "event": "contact.updated",
  "data": {
    "userId": "u_123",
    "companyId": "c_abc",
    "entityId": "ct_xyz",
    "payload": {
      "contact": {
        "id": "ct_xyz",
        "firstName": "Max",
        "lastName": "Mustermann",
        "notes": { /* Tiptap-JSON */ },
        "organizations": [{ "id": "org_1", "name": "Example GmbH" }],
        "users": [],
        "deals": [{ "id": "deal_1" }, { "id": "deal_2" }],
        "customFieldValues": [
          { "columnId": "col_abc", "value": "Won" }
        ]
      },
      "changes": {
        "organizations": {
          "previous": [],
          "current": [{ "id": "org_1", "name": "Example GmbH" }]
        }
      }
    }
  },
  "timestamp": "2026-04-22T10:00:00.000Z"
}
```

Die Record-Felder hängen vom Entity-Typ ab. Custom-Columns erscheinen unter `customFieldValues` als `columnId`- und `value`-Paare. Mit `get_record_schema` sehen Sie die Columns, die für einen Entity-Typ in Ihrem Workspace konfiguriert sind.

## Das `changes`-Objekt

`changes` existiert nur bei `*.updated`-Events. Jeder Key ist ein Record-Feld, dessen Wert sich geändert hat. `previous` ist der Wert vor dem Write, `current` der Wert danach.

Skalare und Objekt-Felder melden ihren vollständigen Wert vor und nach der Änderung, verglichen per Deep-Equal. Arrays, deren Elemente eine `id`, `columnId` oder einen `key` tragen (verknüpfte Records, Custom-Column-Werte), melden nur die Elemente, die sich geändert haben: `previous` enthält die geänderten oder entfernten Elemente, `current` die geänderten oder hinzugefügten Elemente, und unveränderte Elemente entfallen. Ein hinzugefügtes Element erscheint deshalb nur unter `current`, ein entferntes nur unter `previous`. Arrays ohne einen solchen Key melden auf beiden Seiten das ganze Array. `createdAt` und `updatedAt` werden nie als Änderung gemeldet.

Wenn ein Write kein Feld ändert, wird das Event unterdrückt. No-op-`*.updated`-Events werden nicht zugestellt.

## Custom Headers und Body-Vorlagen

Manche Empfänger akzeptieren die Standardzustellung nicht. Dafür gibt es zwei optionale Einstellungen; ein Webhook, der keine davon setzt, stellt genau wie oben beschrieben zu.

**Custom Headers** werden bei jeder Zustellung mitgesendet, für Endpunkte mit eigener Authentifizierung. In der Oberfläche tragen Sie sie im Feld **Eigene Header** zeilenweise als `Name: Wert` ein (eine Zeile ohne Doppelpunkt wird ignoriert, und ein geleertes Feld entfernt alle Header), über MCP und API als `headers`-Objekt. Sechs Namen sind reserviert und werden beim Speichern abgelehnt: `Connection`, `Content-Length`, `Content-Type`, `Host`, `Transfer-Encoding` und `X-Webhook-Signature`. Header-Namen müssen gültige HTTP-Tokens sein, Werte müssen Latin-1-Text ohne Zeilenumbrüche sein, und ein Webhook darf bis zu 20 Header tragen, mit Namen bis 128 Zeichen, Werten bis 2.048 Zeichen und insgesamt 8.192 Zeichen. Da Header in der Regel ein Credential tragen, muss ein Webhook mit Headern einen HTTPS-Endpunkt verwenden; reines HTTP wird nur für `localhost`, `127.0.0.1` und `::1` akzeptiert.

Header-Werte und das Signaturgeheimnis werden von der REST-API und von MCP nie zurückgegeben, beide liefern stattdessen `headerNames` und `hasSecret`. Der Dialog **Webhook** zeigt sie dagegen an: Jede Person, deren Rolle die Seite **Webhooks** öffnen kann, also **Lesen** **Alle** bei **API & Webhooks** oder die Rolle **Admin**, kann beide dort lesen, unabhängig davon, ob die Rolle Webhooks verwalten darf. Das Secret bleibt maskiert, bis Sie es über das Augensymbol einblenden. Eine Aktualisierung über API oder MCP ohne `headers` behält die gespeicherten Werte, eine mit `null` löscht sie.

**Eine Body-Vorlage** ersetzt den Standardumschlag für Endpunkte mit fester Struktur. Schreiben Sie ein JSON-Dokument und verweisen Sie über Platzhalter auf Werte des Umschlags:

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

Verfügbar sind `{{event}}`, `{{timestamp}}` sowie jeder Pfad unterhalb von `{{data}}`, darunter `{{data.entityId}}`, `{{data.companyId}}`, `{{data.userId}}` und `{{data.payload}}`. Ein Platzhalter muss innerhalb eines JSON-Strings stehen; `{"count": {{data.payload.count}}}` wird abgelehnt. Ein Platzhalter, der ein Objekt liefert, wird als JSON-String eingesetzt, ein fehlender Pfad wird zu einem leeren String. Eingesetzte Werte werden escaped, sodass Datensatzinhalte die Struktur des Dokuments nicht verändern können.

Die Vorlage darf bis zu 8.192 Zeichen lang sein und muss ein JSON-Objekt ergeben. Sie wird beim Speichern geprüft. Eine Zustellung, deren Vorlage nicht gerendert werden kann oder deren gerenderter Body länger als 131.072 Zeichen ist, wird als fehlgeschlagen erfasst statt gesendet und nicht wiederholt. Die Signatur wird immer über den tatsächlich gesendeten Body berechnet, prüfen Sie sie also gegen den gerenderten Body und nicht gegen den Umschlag.

**Secret oder Vorlage entfernen.** Der Dialog kann ein gespeichertes **Secret** oder eine gespeicherte **Body-Vorlage** nicht entfernen: Das Speichern eines leeren Felds wird abgelehnt. Zum Entfernen aktualisieren Sie den Webhook über `manage_webhooks` oder die REST-API mit `secret: null` oder `bodyTemplate: null`, oder Sie löschen den Webhook und legen ihn neu an.

**Eine URL, eine Konfiguration.** Secret, Header und Body-Vorlage werden einer Zustellung über Workspace und URL zugeordnet, nicht über den Webhook. Zeigen mehrere Webhooks desselben Workspace auf dieselbe URL, deaktivierte eingeschlossen, wird jede Zustellung an diese URL mit dem Secret des ältesten von ihnen signiert, oder unsigniert gesendet, wenn dieser kein Secret hat. Trägt einer von ihnen Header oder eine Body-Vorlage, schlägt jede Zustellung an diese URL fehl und wird nicht wiederholt, auch die des Webhooks ohne Überschreibungen. Geben Sie jeder Subscription eine eigene URL, etwa über einen Pfad oder einen Query-String, bevor Sie ein Secret, Header oder eine Vorlage hinzufügen.

Zustellungen werden mit dem Ereignis-Payload erfasst, nicht mit dem gerenderten Body. **Ereignis-Details** zeigt also das ausgelöste Ereignis und nicht die exakt gesendeten Bytes.

## Wie sende ich an Slack, Discord oder n8n?

Jedes Rezept nennt die URL, die eigenen Header und die Body-Vorlage zum Einfügen in den Dialog **Webhook** unter **Mein Unternehmen** → **Webhooks** → **Hinzufügen**. Setzen Sie in jedem Fall ein Signaturgeheimnis; ein Empfänger, der es nicht prüfen kann, ignoriert den Header einfach.

### Claude-Code-Routinen

Startet eine Claude-Code-Routine, wenn sich ein Datensatz ändert. Legen Sie die Routine zuerst unter [claude.ai/code/routines](https://claude.ai/code/routines) an.

<Steps>
<Step title="API-Trigger hinzufügen">
Öffnen Sie die Routine, klicken Sie auf **Add another trigger**, wählen Sie **API** und dann **Generate token**. Kopieren Sie URL und Token; das Token wird nur einmal angezeigt und lässt sich später nicht erneut abrufen.
</Step>
<Step title="Webhook anlegen">
Fügen Sie die URL ein, wählen Sie Ihre Ereignisse und tragen Sie die Header und die Vorlage unten ein.
</Step>
<Step title="Payload im Routinen-Prompt referenzieren">
Der Text kommt in einem `routine-fire-payload`-Block an, den die Routine als nicht vertrauenswürdige Daten behandelt. Der Prompt der Routine muss ihn ausdrücklich referenzieren, etwa "handle das im routine-fire-payload-Block beschriebene Ereignis ab", sonst bleibt der Text unbeachtet.
</Step>
</Steps>

Die URL lautet `https://api.anthropic.com/v1/claude_code/routines/<routine-id>/fire`, die Routinen-ID beginnt mit `trig_`.

```
Authorization: Bearer <routine-token>
anthropic-beta: experimental-cc-routine-2026-04-01
anthropic-version: 2023-06-01
```

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

Der Endpunkt liest ausschließlich `text` und ignoriert jedes andere Feld. Die Vorlage ist deshalb zwingend; ohne sie startet die Routine ohne Kontext. Jede Zustellung startet einen eigenen Lauf auf Ihr Routinen-Kontingent, ein Retry einen weiteren. Abonnieren Sie deshalb möglichst wenige Ereignisse.

### Slack

Beitrag über einen Incoming Webhook in einen Kanal posten. Die URL trägt die Authentifizierung, eigene Header sind nicht nötig.

Verwenden Sie die Incoming-Webhook-URL aus **Slack → Apps → Incoming Webhooks**.

```json
{ "text": "{{event}} for {{data.entityId}}" }
```

### Discord

Dieselbe Struktur unter einem anderen Schlüssel.

Verwenden Sie die Webhook-URL aus **Kanal → Kanal bearbeiten → Integrationen → Webhooks**.

```json
{ "content": "{{event}} for {{data.entityId}}" }
```

### n8n

Ein n8n-Webhook-Node akzeptiert den Standardumschlag. Lassen Sie beide Einstellungen leer, sofern der Node keine Header-Authentifizierung verwendet. Tut er das, tragen Sie den erwarteten Header ein und lassen die Vorlage leer:

```
X-N8N-Header-Auth: <Wert>
```

Das vollständige Muster steht unter [n8n](/docs/n8n).

### Alles andere

Ein Empfänger, der weder eigene Authentifizierung noch eine feste Body-Struktur braucht, benötigt keine der beiden Einstellungen. Lassen Sie beide leer und prüfen Sie die Signatur wie unten beschrieben.

## Wie prüfe ich die Signatur? [#how-do-i-verify-the-signature]

Hat der Webhook ein **Secret**, enthält jede Request:

```
X-Webhook-Signature: <hex>
```

`<hex>` ist `HMAC-SHA256(secret, rawRequestBody)`, Lowercase-Hex, ohne Präfix. Berechnen Sie den Wert auf Ihrer Seite neu und vergleichen Sie in konstanter Zeit. Teilen sich mehrere Webhooks eine URL, gilt das Secret des ältesten, wie oben unter „Eine URL, eine Konfiguration“ beschrieben.

Node.js-Beispiel:

```ts
import crypto from "crypto";

function verify(rawBody: string, received: string, secret: string) {
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
}
```

## Wie funktionieren Retries und fehlgeschlagene Deliveries?

Jede Delivery wird protokolliert. Klappen Sie in der Seitenleiste **Mein Unternehmen** auf und öffnen Sie **Letzte Zustellungen**, oder rufen Sie `manage_webhooks` mit `action: "list_deliveries"` auf. Die Seite listet die neuesten Zustellungen zuerst, mit **URL**, **Ereignis**, **Element** (dem betroffenen Datensatz), **Status**, **Status-Code** und **Erstellt am**. Das Suchfeld durchsucht Ereignis und URL, die Filter decken Ereignis, URL und Erstellungsdatum ab. Zustellungen werden nicht automatisch gelöscht; sie bleiben erhalten, solange der Workspace besteht.

Ein Klick auf eine Zeile öffnet **Ereignis-Details**. Der Dialog zeigt den Status (**Ausstehend**, bis der erste Versuch abgeschlossen ist, danach **Zugestellt** oder **Fehlgeschlagen**), **URL**, **Ereignis**, **Element**, **Erstellt am**, **Status-Code**, **Antwort-Nachricht** und den **Ereignis-Payload**. Der Payload wird vollständig angezeigt, auch für Datensätze, die die Rolle der lesenden Person sonst nicht öffnen kann.

Eine Delivery gilt als fehlgeschlagen, wenn der HTTP-Status außerhalb des 2xx-Bereichs liegt, die Request timeoutet oder keine Antwort eintrifft. Der Request-Timeout beträgt 5 Sekunden. Eine Delivery schlägt außerdem schon vor dem Senden fehl, mit Status-Code 422, wenn ihre URL mit einem anderen Webhook geteilt wird und einer von ihnen Header oder eine Vorlage trägt, wenn Header an eine Adresse gehen würden, die sie nicht erlaubt, oder wenn die Body-Vorlage nicht gerendert werden kann.

Customermates wiederholt fehlgeschlagene Deliveries automatisch: bis zu 5 Wiederholungen bei Timeouts, Netzwerkfehlern, 5xx-Responses und 408, 425 und 429. Dauerhafte 4xx-Responses (zum Beispiel 400, 401, 403, 404) und die 422-Fehler oben werden nicht wiederholt, weil ein erneuter Versuch genauso scheitern würde. Die Retries laufen innerhalb des Delivery-Runs, erzeugen also keine zusätzlichen Delivery-Records; jeder Record zeigt das jeweils letzte Ergebnis, kann also **Fehlgeschlagen** anzeigen, während noch Retries ausstehen, und zu **Zugestellt** wechseln, sobald einer gelingt.

Sie können eine Delivery zusätzlich selbst erneut zustellen. In **Ereignis-Details** erscheint oben das Symbol mit den kreisförmigen Pfeilen (**Erneut senden**), sobald die Zustellung **Zugestellt** oder **Fehlgeschlagen** ist, für Rollen mit **Verwalten** **Ja** bei **API & Webhooks**. Über MCP nutzen Sie `manage_webhooks` mit `action: "resend_delivery"` und der Delivery-id. Ein erneutes Senden schickt das gespeicherte Ereignis an dieselbe URL, mit dem aktuellen Secret, den aktuellen Headern und der aktuellen Vorlage dieser URL, und erzeugt einen neuen Delivery-Record; das Original bleibt unverändert. Es wird auch dann gesendet, wenn der Webhook inzwischen deaktiviert oder gelöscht wurde; nach einem Löschen geht es, sofern kein anderer Webhook dieselbe URL nutzt, unsigniert, ohne eigene Header und im Standardumschlag hinaus.

**Link:** `/company/webhook-deliveries`, Cloud-URL `https://customermates.com/de/company/webhook-deliveries`. **Mate:** `navigate` und `highlight_element` mit `nav-company-webhook-deliveries` (hervorhebbar nur, solange **Mein Unternehmen** aufgeklappt ist, standardmäßig auf jeder seiner Seiten, sofern das Mitglied es nicht zugeklappt hat); `company-webhook-deliveries-search` und `company-webhook-deliveries-filter` heben das Suchfeld und die Filter hervor. `company-webhook-deliveries-display-options` hebt die Anzeigeoptionen hervor, `company-webhook-deliveries-layout-table` und `company-webhook-deliveries-layout-board` die Layout-Controls darin (zuerst die Anzeigeoptionen öffnen). Ist eine Zustellungszeile geöffnet, hebt `webhook-delivery-modal-resend` das Symbol **Erneut senden** in **Ereignis-Details** hervor (Rollen mit Verwalten-Recht, nicht bei ausstehenden Zustellungen); die Zeilen und der Rest des Dialogs sind keine Highlight-Ziele, deshalb nennt Mate sie beim Namen.

## Sind Deliveries geordnet?

Deliveries sind über Events hinweg nicht strikt geordnet. Zwei `contact.updated`-Events im Millisekundenabstand können in falscher Reihenfolge ankommen. Lösen Sie die Reihenfolge über den `timestamp` im Payload auf oder behandeln Sie Deliveries als idempotente Messages mit `entityId` als Schlüssel.

## Notes sind JSON, nicht Markdown

Das `notes`-Feld in Payloads ist Tiptap-JSON, dieselbe Struktur, die der Editor speichert. Um es auf Ihrer Seite als Markdown zu rendern, nutzen Sie einen Tiptap-kompatiblen Serializer. In MCP liefert `get_records` mit `include: "withNotes"` die Notes bereits als Markdown serialisiert.

## Was enthalten Delete-Payloads?

Delete-Events enthalten unter `payload` den vollständigen Record, wie er vor dem Löschen war, nicht nur die id. Die id des betroffenen Records steht zusätzlich in `data.entityId`.

## Wie debugge ich eine Delivery?

- Nutzen Sie [webhook.site](https://webhook.site) als Einweg-Receiver beim Integrationstest.
- Das Delivery-Log (`manage_webhooks`, `action: "list_deliveries"`) unterstützt `searchTerm` auf URL und Event-Name.
- Für jede Delivery erfasst Customermates nur den HTTP-Status-Code und den Statustext, den Ihr Receiver zurückgegeben hat (zum Beispiel `404` und `Not Found`), angezeigt als **Status-Code** und **Antwort-Nachricht** in **Ereignis-Details**. Der Response-Body wird nicht gespeichert, protokollieren Sie ihn also auf der Empfängerseite. Trifft keine Antwort ein, zeigt **Status-Code** einen Strich (in der Liste bleibt die Spalte leer) und **Antwort-Nachricht** nennt die Ursache, etwa den Timeout.

## Welche Ereignisse gibt es? [#which-events-exist]

[[derived.webhooks.events.total]] Events können Sie abonnieren: [[derived.webhooks.events.records]] Record-Events über die fünf Entity-Typen und [[derived.webhooks.events.messaging]] Messaging-Events. Alle nutzen den Envelope oben. Routinen können durch dieselben Ereignisse ausgelöst werden, mit Ausnahme von **E-Mail gelöscht** (`messaging.email.deleted`) und **Chat gelöscht** (`messaging.chat.deleted`); **Nachricht gelöscht** (`messaging.message.deleted`) löst Routinen aus; siehe [Routinen](/docs/app-routines#how-do-event-triggers-work).

### Record-Events

| Event | Wann es feuert | `payload` |
|---|---|---|
| `contact.created` | Ein Contact wird via UI, API, MCP oder Import erstellt | vollständiger Contact |
| `contact.updated` | Ein Contact-Feld ändert sich | `contact`, `changes` |
| `contact.deleted` | Ein Contact wird gelöscht | vollständiger Contact |
| `organization.created` | Eine Organization wird erstellt | vollständige Organization |
| `organization.updated` | Ein Organization-Feld ändert sich | `organization`, `changes` |

### Messaging-Events

Messaging-Events feuern bei eingehender Provider-Aktivität auf verbundenen Accounts. Die Liste **Ereignisse** bietet sie in jedem Workspace an, sie feuern aber nur, wo verbundene Accounts existieren, und das setzt die Cloud und einen Tarif mit Messaging voraus. `userId` ist `null`. Payloads referenzieren Provider-Records per id (`connectedAccountId`, `provider`, `providerMessageId`, `threadId` und ähnliche), statt CRM-Records einzubetten.

| Event | Wann es feuert |
|---|---|
| `messaging.message.received` | Eine Chat-Nachricht oder E-Mail wird ingested |
| `messaging.message.updated` | Eine ingestete Nachricht wird aktualisiert |
| `messaging.message.deleted` | Eine ingestete Nachricht wird gelöscht |
| `messaging.message.reaction` | Eine Reaktion wird zu einer Nachricht hinzugefügt |
| `messaging.email.received` | Eine E-Mail wird ingested |
| `messaging.email.deleted` | Eine ingestete E-Mail wird gelöscht |
| `messaging.chat.updated` | Ein Chat-Thread wird aktualisiert |
| `messaging.chat.deleted` | Ein Chat-Thread wird gelöscht |
| `messaging.calendar.changed` | Ein verbundener Kalender ändert sich |
| `messaging.calendar_event.changed` | Ein Kalender-Event ändert sich |
| `messaging.relation.created` | Eine neue Provider-Relation wird erstellt |
