# Connecting a CRM to an ERP without creating two sources of truth

A CRM ERP integration passes a small set of identifiers and statuses between the system where you sell and the system where you deliver and bill. The CRM owns people, relationships, deals and conversations. The ERP owns the customer account used for billing, items, orders, stock and payments. The integration fires on defined business events, such as "deal won", and writes each system's reference number back into the other.

Most small teams should start with one one-way flow: a won deal creates the customer and an order in the ERP, and the ERP order number comes back to the deal. Build that through a native connector if your two systems have one, otherwise through the ERP's REST API and webhooks, using an automation platform such as n8n or a small service you run.

Customermates, an AI-native CRM, publishes this guide. Customermates is a CRM only, with no ERP functions and no native ERP connector; the section on it below shows how it connects through its REST API and webhooks. ERP vendor details were checked on 8 October 2026 on the vendors' own pages, linked at the end.

## Which system owns which data

Write this table for your own systems before you compare tools. Ownership is decided per field, not per object: the organization can live in both systems while its billing address belongs to the ERP and its account notes belong to the CRM.

| Data | Usually owned by | What the other side keeps |
| --- | --- | --- |
| Contacts, relationship history, conversations | CRM | The ERP keeps a contact person only if its documents need one |
| Deal, stage, next step | CRM | Nothing, or a reference on the order |
| Customer account for billing (legal name, VAT ID, billing address, payment terms) | ERP | ERP customer number, read-only in the CRM |
| Items and prices | ERP | Item number on the CRM's product or service record |
| Orders, delivery, stock | ERP | Order number and one customer-facing status |
| Billing documents and payments | ERP | Document number and a coarse payment status, if account managers need it |

If two systems both write the same field, you have a conflict waiting to happen. Pick one owner, make the field read-only on the other side, and route corrections to the owner.

## Four ways to connect a CRM and an ERP

| Method | Fits when | Watch for |
| --- | --- | --- |
| Native connector | Both systems come from vendors that ship a connector for each other | Which objects, fields and directions it covers, which editions it needs, and who supports it when it breaks |
| Automation platform (iPaaS, n8n, Make, Zapier) | You need a few flows between two systems with REST APIs and want visual logic | Idempotency, error queues and secrets are still your job. A visual flow is production software |
| Direct API integration | One narrow, valuable flow between two stable APIs, and someone on the team writes code | You own authentication, retries, API version changes and monitoring |
| Middleware or integration service | Several systems or high volume, with a shared data model and queues | More moving parts. Too heavy for moving five fields |

There is a fifth answer that some readers searching "CRM ERP Komplettlösung" or "can CRM be part of ERP" are after: one suite. Odoo, for example, ships a CRM app alongside its ERP apps, so the customer record is shared and there is nothing to sync. The tradeoff is that you use the suite's CRM. Note that Odoo makes its external API available only on its Custom plan, so connecting any outside system to Odoo needs that plan.

## Sync patterns and when to use them

| Pattern | How it works | Use it for |
| --- | --- | --- |
| Event-driven, one way | A change in the owning system triggers a write in the other | The first flow. Direction and ownership stay obvious |
| Scheduled reconciliation | A job compares cross-references and lists or repairs gaps | A safety net under every event flow |
| Lookup at read time | One system asks the other for current data without storing a copy | Stock or payment status shown on demand |
| Bidirectional | Both systems update related data | Only when the business really changes the data in both places, with per-field ownership and conflict rules |

"Real time" is rarely the requirement it sounds like. An account manager who sees a payment status a minute late loses nothing; a duplicate order in the ERP costs real money. Design for retries and duplicates first, speed second.

## What your ERP's interface actually offers

The ERP side usually decides how hard the integration is. Four examples show how much the interfaces differ:

| ERP | Interface, according to the vendor | What it means for the integration |
| --- | --- | --- |
| Microsoft Dynamics 365 Business Central | REST API v2.0 with entities such as customers, items, salesQuotes, salesOrders and salesInvoices, plus webhook subscriptions | Subscriptions expire after three days unless renewed, and notifications wait 30 seconds after the first change. More than 1,000 changes in that window arrive as one "collection" notification that you must resolve with a query |
| Odoo | XML-RPC external API in version 18; version 19 documents the JSON-2 API and a migration path from XML-RPC and JSON-RPC | Available only on the Custom plan. Check which API your Odoo version runs before you build |
| Lexware Office | REST API for contacts, articles, quotations, order confirmations, delivery notes and other vouchers, with event subscriptions | Up to 2 requests per second per client, so batch jobs need throttling |
| Xentral | REST API for customers, products, sales orders, purchase orders, delivery notes and invoices, with webhooks and a list of webhook event types | Several API versions exist side by side, so pin the version in your mapping |

Two questions save the most time: is the API included in the plan you pay for, and does the ERP push changes by webhook or do you have to poll it?

## Events, idempotency and reconciliation

An integration that only handles the happy path will create duplicates within weeks. Webhooks get retried, people click twice, and a timeout can hide a write that actually succeeded.

- **Idempotency.** Before creating anything in the target, check whether it already exists. The simplest check is the cross-reference itself: if the deal already holds an ERP order number, do not create another order.
- **Stable IDs.** Store the other system's ID after the first match. Never match companies by name on every run; names change and subsidiaries share them.
- **Retries.** Retry timeouts, rate limits and server errors with backoff. Stop on validation errors and put the event in a repair queue with the reason.
- **Conflicts.** Decide them as business rules: the owner wins, or a person decides. Never apply "last write wins" across the board.
- **Reconciliation.** Run a scheduled check that lists records missing a cross-reference or showing different statuses on both sides. It catches whatever the event flow missed.
- **Logging.** Record event, source record, target reference, attempt count and result, without copying more customer data into logs than diagnosis needs.

## Building the first flow

<Steps>
  <Step title="Pick one business event">
    "Deal won creates the ERP customer and order" is a good first event. "Sync CRM and ERP" is not an event.
  </Step>
  <Step title="Define the preconditions">
    List the fields that must be filled before the event may fire: billing address, VAT ID, items, quantities. Decide what blocks the event and who fixes it.
  </Step>
  <Step title="Write the field map">
    For each field: source, target, type, owner, transformation, and what happens when it is missing or invalid. Keep the map versioned next to the integration.
  </Step>
  <Step title="Choose the method">
    Native connector if one covers the flow; otherwise an automation platform or a small service against both REST APIs.
  </Step>
  <Step title="Build idempotency and the write-back">
    Check the cross-reference before creating, then write the ERP number back to the CRM record in the same run.
  </Step>
  <Step title="Test the awkward cases">
    Existing customer, two companies with the same name, missing address, unknown item, ERP timeout, the same event delivered twice, deal reopened after "won".
  </Step>
  <Step title="Roll out with reconciliation">
    Start with one team or one deal type, compare both systems by hand for the first weeks, then switch on the scheduled reconciliation and name the person who handles failures.
  </Step>
</Steps>

## Example: won deal to ERP order with Customermates

This is the setup in Customermates for the first flow above. It uses the [REST API](/features/api) and [webhooks](/docs/webhooks), which work on every Customermates Cloud plan and in a self-hosted installation. The receiver in the middle is yours: an n8n workflow or a small service.

**Columns.** Add custom columns of type Text: "ERP customer no." on organizations, "ERP order no." on deals, and "ERP item no." on services. Deals carry linked services with per-deal quantities, so the services and their item numbers become the order lines. If account managers need delivery or payment state, add a Single Select column such as "ERP status" on deals and let only the integration write it.

**Trigger.** The default deal Stage column has a "Won" option. Under **My Company → Webhooks**, subscribe a URL to `deal.updated` and set a secret. Each delivery is signed with HMAC-SHA256 in the `X-Webhook-Signature` header, and for update events the payload carries a `changes` object with the previous and current value of each changed field. Your receiver acts only when the stage changed to "Won".

**Idempotency.** The standard webhook envelope has no unique event ID, so use the cross-reference: if the deal's "ERP order no." is already filled, stop.

**Customer match.** Look up the organization's "ERP customer no.". If it is empty, search the ERP by VAT ID or create the customer, then write the number back. To find a CRM organization by ERP number later, call `POST /api/v1/organizations/search` with an `equals` filter on that column's ID ([filter syntax](/docs/filter-syntax)).

**Write-back.** After the ERP accepts the order, call `PUT /api/v1/deals/{id}` with the new "ERP order no.". The update changes only the fields you send.

**Failures.** Customermates retries a failed delivery automatically for timeouts, network errors, 5xx responses and 408, 425 and 429. Other 4xx responses are not retried, because they would fail the same way. Every delivery appears under **Recent Deliveries**, where you can resend it after fixing the cause.

**Reconciliation.** Save a deal view filtered to Stage "Won" and "ERP order no." empty. Saved views are personal, so the person who handles integration failures keeps it. Anything that shows up there was missed by the event flow.

**The reverse direction.** If your ERP sends webhooks, point them at the same receiver, look up the deal by "ERP order no." and set "ERP status". If it does not, poll the ERP on a schedule. The [n8n guide](/docs/n8n) lists the REST calls an n8n workflow needs; a community node also exists.

In Customermates Cloud, Mate can work with these columns too, for example "list won deals from this month without an ERP order number". Mate uses hosted AI credits. An AI client of your own can do the same through [MCP](/docs/mcp).

## What drives cost and effort

No honest benchmark covers all CRM ERP integrations; a one-way event between two documented APIs and a two-way sync of orders and stock are different projects. Estimate from these drivers:

- whether the ERP's API is in your current plan, or needs an upgrade;
- whether both systems send webhooks, or one has to be polled;
- the number of objects, fields, directions and transformations;
- how messy existing customer data is, and how many duplicates need matching once;
- rate limits and volume;
- who runs the automation platform or service, and who answers its alerts.

On the CRM side, the API and webhooks need no particular Customermates plan. A three-person team on Starter pays [[commercial.price.starter.monthly.seats.3]] per month. The unified inbox, which brings email, LinkedIn and WhatsApp conversations to the same records, starts with Pro ([[commercial.price.pro.monthly]] per user per month).

## Common mistakes

- syncing every field before one event works end to end;
- letting both systems own the same field;
- matching companies by name instead of stored IDs;
- no repair queue, so failed events vanish into logs;
- ignoring cancellations, reopened deals and corrections;
- launching without a reconciliation check or a named person for alerts.

For the difference between the two system types, and when a small team needs an ERP at all, read [CRM and ERP compared](/blog/crm-and-erp).

## FAQ

<Faq>
<FaqItem question="What is CRM ERP integration?">
It is the automated exchange of selected identifiers and statuses between the CRM, where you manage relationships and deals, and the ERP, where you manage orders, items, stock and billing. Done well, it moves only what a defined business event needs and keeps one owner for every field.
</FaqItem>

<FaqItem question="How do you integrate a CRM and an ERP?">
Define field ownership, pick one business event such as "deal won", and choose a method: a native connector if your systems have one, otherwise the ERP's API and webhooks through an automation platform or a small service. Add idempotency checks, a write-back of the other system's ID, and a scheduled reconciliation before you go live.
</FaqItem>

<FaqItem question="Are CRM and ERP the same, and can a CRM be part of an ERP?">
They are different systems: CRM covers selling and customer relationships, ERP covers delivery, purchasing, stock and finance. Some suites include both. Odoo, for example, offers a CRM app next to its ERP apps, which removes the need for an integration between the two.
</FaqItem>

<FaqItem question="Should CRM and ERP sync in both directions?">
Usually not at first. A one-way event from CRM to ERP, plus a returned order number and one status field, covers most needs of a small team. Add a second direction only for fields that really change in both places, with per-field ownership.
</FaqItem>

<FaqItem question="Can you integrate CRM and ERP without code?">
Often yes, with a native connector or an automation platform such as n8n, Make or Zapier. You still have to decide field ownership, handle duplicates and failures, and check whether your ERP plan includes API access.
</FaqItem>

<FaqItem question="Does Customermates integrate with ERP systems?">
Through its REST API and webhooks, yes, using an automation platform or service you run. There is no native ERP connector, and Customermates itself holds no ERP data such as orders or payments. ERP references go into custom columns on organizations, deals and services.
</FaqItem>
</Faq>
