# n8n MCP: escolha uma rota e teste uma tarefa de CRM

n8n MCP pode significar um cliente de IA chamando o n8n ou um workflow do n8n chamando as ferramentas de outro aplicativo. Para uma consulta de cliente e uma tarefa interna no Customermates, a segunda direção serve: o exemplo testado abaixo usa o MCP Client independente do n8n, sem modelo de linguagem.

MCP é o protocolo de conexão; o n8n é o aplicativo de workflows. Comece pela direção da chamada e só depois escolha o nó ou o servidor. O [guia de workflows do n8n para iniciantes](/blog/n8n-for-beginners-build-your-first-workflow) cobre o editor visual; este guia cobre a escolha do MCP e uma rota datada, que foi executada.

## O que é MCP no n8n? [#o-que-e-mcp-no-n8n]

MCP é a sigla de Model Context Protocol, um protocolo aberto que permite a um aplicativo de IA descobrir e chamar as ferramentas de um servidor. No n8n, ele aparece de quatro formas: o n8n como servidor para um cliente de IA (acesso no nível da instância ou o nó MCP Server Trigger), o n8n como cliente de outro servidor (o MCP Client Tool de um agente e o MCP Client independente) e projetos da comunidade ao redor disso. Para a base do protocolo, veja [o que é um servidor MCP](/blog/what-is-an-mcp-server); para a diferença em relação a uma API comum, [MCP vs API](/blog/mcp-vs-api).

## Qual rota do n8n MCP combina com o seu trabalho?

A tabela separa quem mantém a rota de quem tem as credenciais que autorizam o trabalho. Um nome de produto conhecido não basta para identificar uma conexão.

| Rota e direção | Quem mantém | Identidade em ação e autenticação | Limite de versão |
| --- | --- | --- | --- |
| MCP no nível da instância: cliente externo → n8n | n8n | Usuário do n8n via OAuth ou token de acesso MCP | Criação de workflows a partir da 2.13.0; layout de configurações a partir da 2.33.0 |
| MCP Server Trigger: cliente externo → ferramentas de um workflow | n8n | Credencial bearer/header configurada, ou n8n User Auth | User Auth exige o nó v2+; a saída do usuário exige v2.1+ |
| MCP Client Tool: n8n AI Agent → servidor MCP externo | n8n | Credencial do serviço externo | Subnó do agente; não é o nó testado abaixo |
| MCP Client independente: workflow comum → servidor MCP externo | n8n | Credencial do serviço externo | Executado aqui: n8n 2.45.5, nó typeVersion 1.1 |
| Comunidade `czlonkowski/n8n-mcp`: cliente de programação → serviço MCP separado | Mantenedores de um projeto independente | Depende da implantação; acesso à API do n8n quando configurado | Fixe a versão desse projeto separadamente |

A [documentação oficial do MCP no nível da instância](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/) distingue o acesso à instância do Server Trigger de um workflow. Ativar o MCP não expõe todos os workflows. A visibilidade segue o acesso do usuário e as configurações de exposição ao MCP. A [referência de ferramentas](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference/) inclui a criação e a edição de workflows e de tabelas de dados. Descrever o servidor oficial de hoje como "só executa" é incompleto.

A [referência do MCP Server Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger/) descreve um ponto de entrada de servidor. A [referência do MCP Client Tool](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolmcp/) descreve as ferramentas externas de um agente. A [referência do MCP Client independente](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcpclient/) cobre chamadas explícitas em um workflow normal.

O [repositório n8n-mcp](https://github.com/czlonkowski/n8n-mcp), independente, oferece ajuda para montar workflows. É um projeto à parte, não o nome de todos os recursos MCP nativos. Você não precisa instalá-lo para a receita do cliente independente abaixo.

## Como habilitar o MCP no n8n e conectar um cliente de IA? [#habilitar-mcp-no-n8n]

Esta é a rota em que o n8n é o servidor e um cliente de IA, como o Claude ou o Cursor, é quem chama. Ela não foi executada neste guia: o exemplo testado abaixo é a rota inversa. O que segue é um mapa da [documentação oficial](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/), na ordem em que costuma ser útil lê-la.

| Etapa | O que a documentação cobre | O que conferir |
| --- | --- | --- |
| Habilitar | O acesso MCP no n8n Cloud e em instâncias self-hosted; no self-hosted também dá para desativá-lo por completo | Quem pode ligar o recurso e se a sua política permite |
| Conectar o cliente | OAuth, que a documentação indica como a opção recomendada, ou uma chave de acesso | O acesso é o do usuário n8n que autoriza; guarde chaves como credenciais |
| Expor workflows | Workflows individuais, projetos ou pastas, e a exposição automática de workflows novos | Ativar o MCP não expõe tudo; exponha só o necessário e escreva uma descrição clara de cada workflow, porque o cliente a usa para escolher |
| Expor agentes | Agentes individuais e o gerenciamento do acesso a eles | Quais agentes realmente devem ser chamados de fora |
| Restringir o OAuth | A lista de URLs de callback permitidas | Aceite só os clientes que você conhece |
| Ferramentas e recursos | A referência do que o cliente pode fazer, inclusive criar e editar workflows | Se o cliente precisa de escrita ou só de leitura |
| Solução de problemas | Permissões insuficientes na autorização e cabeçalhos de requisição MCP | O papel do usuário e o que passa entre o cliente e o n8n |

Um cliente de IA conectado vê apenas o que o usuário autorizado pode acessar e o que foi exposto ao MCP. Antes de ligar o recurso em uma instância com workflows de produção, teste em uma instância descartável e revise o que cada workflow exposto é capaz de alterar. O [repositório da comunidade](https://github.com/czlonkowski/n8n-mcp) é outra rota, voltada a ajudar um cliente de programação a montar workflows; fixe a versão dele e trate-o como um projeto à parte.

## Como montar o workflow manual de cinco chamadas?

Crie um Manual Trigger seguido de cinco nós **MCP Client independentes**, ligados pelas saídas normais. Mantenha o workflow sem publicar enquanto valida uma tarefa interna em um workspace descartável. O diagrama mostra a sequência executada, incluindo a requisição duplicada de propósito:

```text
Manual Trigger
  → get_workspace_context
  → get_record_model
  → query_crm_records
  → mutate_crm_record
  → mutate_crm_record (identical payload and key)
```

No workflow preservado, cada nó cliente usou o seguinte formato de parâmetros. É o endereço histórico do relay local, não um endpoint público nem uma configuração de CRM sem autenticação:

```json
{
  "serverTransport": "httpStreamable",
  "endpointUrl": "http://127.0.0.1:4053/mcp",
  "authentication": "none",
  "tool": {
    "__rl": true,
    "value": "get_workspace_context",
    "mode": "id"
  },
  "inputMode": "json",
  "jsonInput": {},
  "options": {
    "timeout": 60000,
    "convertToBinary": false
  }
}
```

Em cada nó seguinte, troque `tool.value` e `jsonInput` conforme os passos abaixo; mantenha Streamable HTTP, a entrada JSON e o timeout de 60 segundos. A sequência fixa não mapeia dinamicamente os resultados da descoberta para os nós seguintes.

1. **Confirme o workspace.** Chame `get_workspace_context` com `{}`. Confira o usuário e o workspace retornados antes de permitir uma escrita.
2. **Leia o esquema.** Chame `get_record_model` com `{}`. O ambiente de teste já tinha resolvido os tipos Task e Organization, os campos principais e a relação de saída antes de montar o workflow. A mutação registrada usou a revisão de configuração `2`.
3. **Encontre o cliente.** Chame `query_crm_records` com o JSON registrado abaixo. No seu workspace, resolva os IDs de novo e confira o resultado antes de escolher um cliente. A referência de registro conhecida da fixture foi fixada no nó seguinte; este não foi um teste de correspondência automática de entidades.

```json
{
  "typeId": "51d5e8d2-9468-8718-852d-aad6d1964282",
  "fields": [
    "b8b511f4-5de8-81ce-887f-880d80b0062c"
  ],
  "search": "Example organization",
  "page": 1,
  "pageSize": 25
}
```

4. **Crie a tarefa interna.** Chame `mutate_crm_record` com este payload registrado, exatamente como está. Todo UUID é um identificador de fixture, inclusive o do usuário atribuído. A relação liga a tarefa à organização fictícia; ela não envia nada a essa organização.

```json
{
  "expectedRevision": 2,
  "idempotencyKey": "seo-run340-n8n-mcp-manual-next-task-v1",
  "mutation": {
    "action": "create",
    "typeId": "0d70aff9-0fa9-8ce2-8e75-8bdddf0fdfd1",
    "assignedUserIds": [
      "eed148ca-b816-4db2-acac-186ca6f03043"
    ],
    "fields": [
      {
        "fieldId": "02960cb0-8976-81b2-82ce-6194a5bc90e3",
        "value": {
          "kind": "text",
          "value": "Fictional n8n manual proof: check the handover field list"
        }
      }
    ],
    "links": [
      {
        "relationId": "2f82adb2-ca57-8190-85ae-230cde69ff06",
        "direction": "outgoing",
        "record": {
          "typeId": "51d5e8d2-9468-8718-852d-aad6d1964282",
          "recordId": "16d88ab1-a440-4e42-b698-99a284940191"
        }
      }
    ]
  }
}
```

5. **Repita a requisição idêntica.** O último nó usou os mesmos argumentos de `mutate_crm_record`, um JSON equivalente byte a byte e a mesma chave de idempotência. Uma nova tentativa para o mesmo evento de negócio precisa manter o payload e a chave. Um evento ou payload diferente precisa de uma chave nova.

O teste original importou o workflow de ID `seoRun340McpProof` e o executou por ID dentro do runtime fixado:

```bash
n8n import:workflow --input /proof/workflow.json
n8n execute --id seoRun340McpProof --rawOutput
```

Esses comandos pressupõem que o workflow preservado e o relay já existem. Uma tentativa anterior com `execute --file` retornou código de saída zero sem executar o workflow. O teste a rejeitou porque nenhuma chamada de ferramenta tinha ocorrido. Um código de saída ou um arquivo JSON importável, sozinhos, não provam que a conexão funciona.

## Como diferem as credenciais e a configuração de produção?

Para uma conexão direta com o Customermates, use `<BASE_URL>/api/v1/mcp` e uma credencial Header Auth do n8n cujo nome de cabeçalho seja `x-api-key`. Guarde a chave nas credenciais, nunca no JSON exportado do workflow. O [guia de chaves de API do Customermates](/docs/api-keys) explica o vínculo com o workspace e as permissões herdadas do usuário. O Header Auth direto é uma configuração documentada; a execução preservada no n8n usou o relay.

Consulte o [contrato MCP do Customermates](/docs/mcp) para ver as ferramentas e os esquemas atuais. Troque os IDs da fixture e a revisão por valores do seu workspace, adicione uma verificação de que a correspondência do cliente é inequívoca e releia a tarefa resultante. Inspecione os erros das ferramentas, e não só o status do workflow. Não transforme uma escrita que falhou em uma nova chave de idempotência sem entender o resultado.

Um cliente MCP externo age como o usuário conectado. As instruções de perguntar antes de enviar ou excluir são orientação para o cliente, não uma barreira de aprovação imposta pelo servidor. Implemente a sua própria etapa de revisão para ações que tenham consequências. A política de aprovação do Mate é separada; este workflow não aciona o Mate nem comprova um processo de aprovação.

Se a sua tarefa é uma sincronização fixa de CRM, o [guia de integração do Customermates com o n8n](/docs/n8n) pode ser mais simples: o community node `@customermates/n8n-nodes-crm` v2, separado, usa a API genérica de registros. Os workflows da v1 apontam para endpoints removidos. REST e webhooks também são opções; compare os contratos em [MCP vs API](/blog/mcp-vs-api).

O Customermates self-hosted fornece o núcleo do CRM Starter, REST e acesso MCP externo. O Mate hospedado e a caixa de entrada na nuvem não estão incluídos. O Customermates não inclui um runtime nem uma assinatura do n8n, n8n hospedado gratuito ou sequências de envio. Se você só precisa conectar um CRM que já tem, o Customermates não é um intermediário obrigatório.

## Perguntas frequentes

<Faq>
<FaqItem question="O que é um MCP no n8n?">
É o suporte do n8n ao Model Context Protocol. O n8n pode funcionar como servidor, expondo workflows e ferramentas a um cliente de IA, ou como cliente, chamando as ferramentas de outro servidor MCP dentro de um workflow. A primeira coisa a decidir é a direção da chamada.
</FaqItem>
<FaqItem question="Como conecto o Claude ou o Cursor ao n8n por MCP?">
Habilite o acesso MCP na instância, autorize o cliente (a documentação do n8n indica o OAuth como opção recomendada), exponha os workflows que o cliente pode usar e teste com um workflow sem consequências. O mapa acima resume as etapas; os detalhes de cada passo estão na documentação oficial, e essa rota não foi executada neste guia.
</FaqItem>
<FaqItem question="Por que o cliente MCP não encontra os meus workflows?">
Ativar o MCP não expõe todos os workflows. O cliente vê o que o usuário autorizado pode acessar e o que foi exposto ao MCP. Confira a exposição de cada workflow, a descrição dele e o papel do usuário no n8n; a documentação oficial tem uma seção de solução de problemas para permissões insuficientes.
</FaqItem>
<FaqItem question="O n8n-mcp é o mesmo que o servidor MCP nativo do n8n?">
Não. O repositório da comunidade citado é mantido de forma independente. O MCP no nível da instância e os nós nativos pertencem ao n8n; confira o pacote exato e a direção antes de instalar qualquer coisa.
</FaqItem>
<FaqItem question="Quando uso o MCP Client Tool em vez do MCP Server Trigger?">
Use o Client Tool quando um n8n AI Agent deve chamar ferramentas externas. Use o Server Trigger quando um cliente externo deve chamar ferramentas expostas pelo seu workflow. Para chamadas fixas, sem modelo, use o MCP Client independente.
</FaqItem>
<FaqItem question="Um mesmo workflow do n8n pode ser cliente e servidor ao mesmo tempo?">
Os dois papéis podem coexistir em um projeto, mas continuam sendo conexões separadas, com credenciais separadas. O exemplo executado aqui testou apenas o caminho de saída do cliente independente.
</FaqItem>
<FaqItem question="O MCP exige aprovação automaticamente antes de cada ação?">
Não. Uma conexão por protocolo não estabelece a sua política de aprovação. Mantenha permissões, prevenção de duplicatas e revisão humana como partes explícitas do workflow.
</FaqItem>
<FaqItem question="Preciso do MCP se o nó do Customermates cobre a minha tarefa?">
Não. Um community node ou um workflow com HTTP Request pode bastar para operações conhecidas. Escolha o MCP quando a interface de ferramentas dele atender à sua tarefa de verdade.
</FaqItem>
</Faq>
